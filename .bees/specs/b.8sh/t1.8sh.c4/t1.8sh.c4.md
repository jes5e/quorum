## Problem Statement

The quorum orchestrator skills (`/quo-execute`, `/quo-breakdown-epic`, `/quo-fix-issue`) run long, boundary-crossing workflows: a single `/quo-execute` Mode 2 run walks every Epic in a Bee, `/quo-breakdown-epic` Mode 2 breaks down every drafted Epic, and `/quo-fix-issue all` works every open Issue. On a long run, the orchestrator session's context grows until Claude Code's automatic compaction fires at roughly 83% of the window — at an arbitrary point the operator does not control, frequently mid-Epic with work in flight. The model cannot see this coming (it has no native read of its own context usage) and cannot defer it (compaction is user-only). The companion defect-fix (Issue b.ja9) makes a mid-Epic compaction *lossless* by externalizing all state to durable carriers, but "lossless" is not the same as "well-timed": the operator still loses the clean narrative boundary and may be surprised by a summarization in the middle of a unit of work. Operators running large Bees have no way to be told "you are approaching the point where this session should hand off," so they either over-conservatively split runs by hand or get surprised by compaction.

## Goals

- On a boundary-crossing run, detect when the orchestrator session's context usage is approaching the auto-compaction threshold and **stop the run at the next clean Epic/Issue boundary**, recommending the operator resume in a fresh session — before compaction fires mid-unit.
- Base the stop decision on a **real, measured** context-usage reading, never on the model's estimate or narration.
- Make the mechanism work identically across every environment quorum runs in (ordinary developer machines and wrapper/pinned environments) through a single published file contract, with the environment-specific setup differences isolated to the producer side.
- When the guard is expected to be available but its reading is absent, **fail loudly with actionable guidance** (including a one-step offer to configure it) rather than silently proceeding unguarded.
- Add no friction to runs where the guard is not load-bearing (single-unit runs, or environments that genuinely cannot support it).

## Non-Goals / Out of Scope

- **Model-initiated compaction or native model-readable usage.** These are upstream Claude Code capabilities (tracked in Issue b.cj2); this feature must not assume they exist or design around their arrival.
- **Changes to the claude-secure-container repository.** The container's producer is delivered separately (already shipped and verified); this feature only publishes the contract that any such environment satisfies.
- **The b.ja9 honesty rewrite.** This feature assumes b.ja9 has landed and layers on its corrected framing; b.ja9's state-externalization and run-state-manifest work is not re-specified here.
- **Guarding single-unit runs.** When the operator is present at every boundary (a run that crosses no Epic/Issue boundary), the guard does not fire.
- **Preventing compaction, or changing when Claude Code compacts.** The guard changes when the *quorum run* stops, not when the *harness* compacts.

## Functional Requirements

- **FR1 — Usage reading.** At each Epic/Issue boundary of a boundary-crossing run, the orchestrator must obtain the current session's context-usage percentage from a durable, machine-written reading identified to the current session, not from its own estimate.
- **FR2 — Stop decision.** When the reading is at or above a configured stop threshold (set safely below the auto-compaction point so the next unit still fits), the orchestrator must stop at that boundary and tell the operator the run stopped for context headroom and how to resume in a fresh session. When the reading is below the threshold, the run continues normally.
- **FR3 — Producer setup.** The setup skill (`/quo-setup`) must offer to configure the usage-reading producer for the operator's environment, including the case where the operator already has a status display configured — in which case the operator's existing display must be preserved, not replaced.
- **FR4 — Missing-reading behavior.** On a boundary-crossing run, when the environment supports the mechanism but no valid reading is present (and the operator has not opted out per FR7), the orchestrator must stop and prompt the operator with (a) an explanation that their environment may override the usual configuration, (b) the published contract describing what a reading must contain and where, and (c) an offer to run the setup step immediately to configure it. Because a freshly-configured producer only takes effect next session (see Assumptions / the activation caveat), if the operator configures at this prompt the orchestrator must recommend resuming in a fresh session for the current work rather than implying the current run is now guarded.
- **FR5 — Unsupported-environment carve-out.** When the running Claude Code cannot support the mechanism at all (it does not expose the current session's identity to the workflow), the orchestrator must skip the guard silently — no stop, no prompt — because the operator has no way to satisfy it.
- **FR6 — Published contract.** The customer-facing documentation must publish the reading's location, its required fields, and its freshness/overwrite semantics, so that an operator of any environment (including one where `/quo-setup` cannot install the producer) can satisfy the contract themselves.
- **FR7 — Persistent opt-out.** An operator who wants to run without the guard must be able to express that once (a persistent opt-out), rather than being stopped at the first boundary of every boundary-crossing run. Setting the opt-out suppresses the missing-reading stop (FR4); it does NOT suppress a genuine over-threshold stop (FR2) when a reading is present, since an operator with a working reading still benefits. The setup step (FR3) and the FR4 prompt both offer to set the opt-out. This keeps the guard friction-free for operators who deliberately want to run unguarded (Goal 5) while preserving the FR4 discovery stop for the unconfigured-but-willing operator.

## Edge Cases and Error Handling

- **No-reading-yet.** A usage reading may legitimately be absent or unpopulated early in a session, and again immediately after a compaction until the session next makes progress. The orchestrator must treat "no reading" as "no information" — never as "0% used" — so a missing reading never reads as "plenty of headroom."
- **Another session's reading (identity keying).** A reading that exists but belongs to a *different* session must not be consumed; the identity check (each reading is keyed to its own session) prevents cross-session consumption. (This is a distinct mechanism from *staleness* below, which concerns a stalled producer for the *current* session — the two are handled separately: identity keying selects the right file, the freshness check judges whether that file's reading is still live.)
- **Parallel sessions.** Multiple quorum sessions may run concurrently in the same environment; each must consume only its own session's reading, with no cross-talk.
- **Producer not yet active.** A newly configured producer may not take effect until the operator's next session. Setup must state this so the operator is not surprised that the guard is inert in the session where they configured it.
- **Threshold vs. a single oversized unit.** If a single Epic/Issue is large enough to cross the compaction threshold on its own, the boundary guard cannot prevent a mid-unit compaction; b.ja9's lossless-compaction behavior is the backstop for that case, and this feature does not claim to cover it.

## Non-Functional Requirements

- **Portability.** The mechanism must work on every stack quorum supports (Rust, Node, Python, Go, Java, unknown) and on both POSIX and native Windows, consistent with quorum's cross-platform design rules. No language-specific or OS-specific assumption may be baked into the guard.
- **Non-intrusiveness.** Obtaining the reading must not itself meaningfully consume context or add per-boundary latency the operator would notice.
- **Fail-safe direction.** Every ambiguous condition (absent reading, unparseable reading, unsupported environment) must resolve toward either a safe stop-and-ask or a silent skip — never toward silently continuing an unguarded long run under the false belief that headroom exists. In particular a **stale** reading must not be trusted: because context grows monotonically within a session, staleness biases the reading low, and low routes to "continue" — the banned direction. The reading therefore carries a freshness signal (the gauge file's modification time), and a reading older than a short freshness window is treated as a **stalled-producer signal that stops the run at the boundary** (fail-safe, recommending a fresh session) — not as "no information" that would let the run continue, and never as a live low reading. (This is distinct from the transient early/post-compaction unpopulated state, which is safe to continue past because the producer is still actively writing.)
- **No new persistent background services.** The mechanism must not require a daemon or long-lived process beyond what the environment's status display already runs.

## UI/UX Requirements

- The stop and missing-reading interactions are the operator's only touchpoints. Each must state, in plain language, why the run is stopping, what the operator should do next (resume in a fresh session; or configure the producer now), and must offer configuration as a one-step action rather than a documentation pointer.
- The guard must be silent when it is not firing — no per-boundary chatter about context usage on runs that are comfortably within headroom.

## Acceptance Criteria

- On a boundary-crossing run whose measured usage is below the threshold at a boundary, the run continues with no guard-related output. *(Observable: run proceeds; no stop message.)*
- On a boundary-crossing run whose measured usage is at/above the threshold at a boundary, the run stops at that boundary and emits a resume-in-fresh-session recommendation naming how to continue. *(Observable: run halts at the boundary with the recommendation.)*
- With a supported environment but no valid current-session reading present, a boundary-crossing run stops and prompts the operator with the environment explanation, the published contract, and an offer to run setup immediately; accepting the offer configures the producer. *(Observable: prompt appears with all three elements and a working configure action.)*
- In an environment that cannot expose the current session's identity to the workflow, a boundary-crossing run proceeds with no guard stop and no prompt. *(Observable: no guard interaction at all.)*
- A reading that is absent or unpopulated is never interpreted as low usage: the guard does not "continue because 0%" on a missing reading. *(Observable: missing reading routes to the FR4 stop-and-ask, not to "continue.")*
- Configuring the producer against an environment that already has a status display preserves that display's output while adding the reading. *(Observable: existing display unchanged; reading now produced.)*
- The customer-facing docs contain the reading's location, required fields, freshness/overwrite semantics, and a restricted-environment note. *(Observable: doc section exists and is complete.)*
- Single-unit runs exhibit no guard behavior. *(Observable: no boundary stop on a run that crosses no boundary.)*
- Setting the persistent opt-out suppresses the missing-reading stop on subsequent boundary-crossing runs, while a present over-threshold reading still stops the run. *(Observable: opt-out set → no FR4 stop on a missing reading; gauge present and over threshold → still stops.)*
- A reading older than the freshness window stops the run at the boundary (stalled-producer signal), never routing to "continue" as if it were low usage. *(Observable: an artificially-aged gauge stops the run; it does NOT route to "continue".)*
- If the operator configures the producer at the missing-reading prompt, the guidance recommends resuming in a fresh session rather than implying the current run is now guarded. *(Observable: the prompt's configure path surfaces the fresh-session recommendation.)*

## Assumptions

- The running Claude Code exposes the current session's identity to the workflow's shell environment (this is what FR5's carve-out keys off — when absent, the guard is skipped).
- The environment's status display is invoked frequently enough during active work to keep the reading acceptably fresh for a boundary-time check.
- The auto-compaction threshold is high enough above the chosen stop threshold that a typical next unit fits within the remaining headroom.
- b.ja9 has landed, so that any compaction the guard does not prevent is lossless.

## Open Questions

- Whether the stop threshold should be operator-tunable, and its exact calibration — the SDD resolves the initial value to 50% (chosen so even a large ~30% unit stays under ~80% < ~83%; the guard reliably prevents compaction only for units up to ~30%, and oversized units degrade to b.ja9's lossless backstop rather than being prevented). This open question now covers only post-first-use recalibration against real long-run telemetry, owned by the post-first-use operator-feedback pass.
- Whether the guard should ever offer "continue anyway one more unit" in addition to "stop / configure," or keep the choice binary at the boundary — owned by the same post-first-use operator-feedback pass; decide once real-run experience exists.

## Background and rationale

This PRD came out of a multi-day investigation (2026-08-14 through 08-16) that began with the question of whether the workflow clears context between Epics in "work through all Epics" mode. It surfaced that the existing "Epic-boundary context-clear discipline" instructed the model to do something it cannot (clear its own context), which is being corrected separately as defect b.ja9. The guard specified here is the constructive follow-on: since the model cannot clear or observe its own context natively, the workflow instead reads a measured usage value that an out-of-band status display writes to a well-known file, and uses it to stop at a clean boundary. Every load-bearing fact behind this design was verified against official Claude Code documentation and by live probes on both a corporate-managed developer machine and a restricted container environment, rather than assumed — including that the session identity is available to the workflow, that the usage reading carries a pre-computed percentage, that an existing status display can be preserved while adding the reading, and that the "no reading yet" states occur in practice and must be handled as "no information."

## Decisions and rejected alternatives

- **Decision: producer/consumer split with a published file as the single contract.** The consumer (in the skills) is environment-agnostic; the producer (the status display) is where environment differences live. This is what lets one mechanism cover ordinary machines and restricted/wrapper environments without per-environment logic in the skills.
- **Decision: hard-stop, not silent-skip, when the guard is expected but its reading is absent.** A guard that silently does nothing is false comfort — the same failure class the b.ja9 defect fix addresses. The hard-stop doubles as the discovery mechanism for environments where the producer could not be auto-installed, and it offers one-step configuration.
- **Decision: exactly one silent carve-out** — an environment that cannot expose the session identity at all — because those operators have no way to satisfy the guard, so prompting them would be pure friction.
- **Rejected: silent-skip whenever unconfigured.** Rejected as false comfort; it would let long unguarded runs proceed under the illusion of protection.
- **Rejected: parsing the session transcript to compute usage.** Rejected because the transcript format is documented as internal and version-unstable, and the workflow cannot reliably locate its own transcript.
- **Rejected: relying on the model's own sense of remaining context.** Rejected as real but unverifiable — there is no measured value to threshold against.
- **Rejected: having setup force the producer into every environment.** Impossible by design where a higher-precedence configuration source pins the status-display slot; hence the published contract plus a per-environment producer rather than a single mandated installer.
