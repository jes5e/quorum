## Codebase exploration findings

Grounded by an Explore-agent pass over the repo (2026-08-16).

**Architecture / where the pieces land.** The feature has two runtime halves plus a setup half:
- **Producer** — a bundled cross-platform Python helper invoked by Claude Code's `statusLine` command on every status-line refresh. It writes the gauge file. It is installed/wired (not invoked at quorum runtime) by `/quo-setup`.
- **Consumer** — inline skill prose plus a small helper `read` path, invoked by the three execution skills at their Epic/Issue boundaries.
- **Setup** — a new optional step in `skills/quo-setup/SKILL.md` that writes/points the `statusLine` key at the producer.

**Bundled-helper conventions to match** (`skills/quo-setup/scripts/detect_fast_path.py`, `skills/quo-breakdown-epic/scripts/scoped_marker_resolver.py`, `skills/quo-execute/scripts/hive_commit.py`): stdlib-only Python 3, `#!/usr/bin/env python3`, `argparse`, `if __name__ == "__main__": sys.exit(main())`. Failure convention is a `fail()` helper printing one human-readable line to stderr and returning exit **2** (scoped_marker_resolver.py:96-98, hive_commit.py:114-116); argparse usage errors normalized to 2. `hive_commit.py` establishes the **argparse-subcommand** shape (`resolve-hive-paths` prints plain paths; `encode-commit` prints a one-line summary) — the new helper will use subcommands the same way. Output is stdout (JSON compact for `scoped_marker_resolver.py`, plain lines for `hive_commit.py resolve-hive-paths`).

**Runtime path resolution** (CLAUDE.md `## Contract keys …` note; `skills/quo-setup/SKILL.md` `### Resolve bundled helper script paths`): each skill resolves its own bundled scripts at runtime from the base directory in the skill invocation header — no committed absolute paths (the old `## Skill Paths` CLAUDE.md section was removed in b.963). Own-skill shape: `<this skill's base directory>/scripts/<name>.py` (quo-execute SKILL.md:377-385). Sibling shape: `<this skill's base directory>/../<other-skill>/scripts/<name>.py`, paired POSIX `/` + PowerShell `\` (quo-execute SKILL.md:327-343).

**Test harness** (`tests/conftest.py`): exports `load_script(relpath)` (importlib `spec_from_file_location`, unique module name to avoid `sys.modules` collision) for in-process unit tests of pure functions, and `script_path(relpath)` for subprocess CLI-contract tests; relpath constants `SCOPED_MARKER_RESOLVER`, `DETECT_FAST_PATH`, `HIVE_COMMIT`; `REPO_ROOT = Path(__file__).resolve().parent.parent`. Every test module has a two-layer pattern: (1) unit layer calling pure functions directly, (2) CLI-contract layer running `subprocess.run([sys.executable, str(SCRIPT), *args], capture_output=True, text=True)` and asserting on `returncode` + `json.loads(res.stdout)`/`stderr`. Test command per this repo's CLAUDE.md `## Build Commands`: `python -m pytest tests/`; lint: `python -m pyflakes skills/*/scripts/*.py`.

## Requirements

### SR-1 — Producer (gauge writer)
- **SR-1.1** A bundled cross-platform Python helper (proposed: `skills/quo-setup/scripts/context_gauge.py`, stdlib-only, matching the existing helper conventions) exposes a `produce` subcommand that reads the Claude Code status-line JSON from **stdin exactly once**, extracts `session_id` and the `context_window` object, and writes them as `{"session_id": ..., "context_window": {...}}` to `<tempdir>/.quorum/context-usage-<session_id>.json`, creating `.quorum` if absent. `<tempdir>` resolved via `tempfile.gettempdir()`.
- **SR-1.2** Write semantics are **overwrite-per-refresh** (truncate-and-write, a live gauge — never append), and the filename is keyed by `session_id` so concurrent sessions in one environment never collide.
- **SR-1.3** When `session_id` is absent from the stdin payload, the helper writes nothing and exits 0 (a status-line refresh with no session context is a no-op, not an error).
- **SR-1.4 (display passthrough / wrap-don't-replace)** `produce` accepts an optional `--wrap-command <cmd>`. When absent, it prints a minimal default display line (derived from the payload's `workspace.current_dir`/`cwd` basename). When present, after writing the gauge it invokes `<cmd>` feeding it the same captured stdin payload and prints that command's stdout verbatim as the status-line display — so an operator's existing status line is preserved, not replaced. Reading stdin once and reusing the captured bytes is mandatory (the container producer proved the stdin-once gotcha).
- **SR-1.5** The helper must never write outside `<tempdir>/.quorum/` and must never delete files (scratch-file convention).
- **SR-1.6 (freshness)** The consumer determines gauge freshness from the gauge file's modification time, which the overwrite-per-refresh write (SR-1.2) updates on every `produce`. No extra timestamp field is required; SR-2.2 rejects any reading whose file mtime is older than the freshness window. Because status lines refresh frequently during active work — and because the boundary check's own tool activity (`printenv`, then the `read` invocation) generates turns that themselves trigger a status-line refresh immediately before the read — the gauge mtime is normally sub-second-fresh at read time, and the ~120s window is generous. A gauge older than that window signals a stalled producer, not a healthy low reading. **False-positive note:** the one residual scenario is a single very long dispatched-subagent unit during which the main session is idle and the status line does not refresh for >120s; that would classify a legitimately-quiet-but-healthy session as `stale`→stop — a conservative extra stop (the fail-safe direction), not a lost guard. The freshness-window value is a named constant and is a post-first-use calibration input (same RESEARCH NEEDED owner as the threshold).
- **SR-1.7 (per-refresh cost, acknowledged)** `produce` spawns a Python interpreter on each status-line refresh, and under `--wrap-command` one additional short-lived spawn for the wrapped command. Status-line refreshes are throttled but frequent; this per-refresh cost is accepted as small and bounded (one or two short-lived process spawns) and is distinct from — and additional to — the per-boundary consumer latency the non-intrusiveness NFR reasons about. If it ever proves material on a hot UI path, the produce path is the place to optimize (e.g. a lighter-weight writer), not the read path.

### SR-2 — Consumer (boundary guard)
- **SR-2.1 (threshold)** A stop threshold is defined as a percentage of the context window. **Default: 50%.** Derivation: auto-compaction fires at ~83%; a single Epic's working set is budgeted at up to ~25-30% of the window (quo-execute SKILL.md:429), so stopping at 50% keeps even a large ~30% unit under ~80% < ~83%. **Honesty bound (do not overclaim):** a fixed boundary check reliably prevents compaction only for units up to ~30% of the window; an oversized single unit can still cross ~83% mid-unit, and that case degrades to b.ja9's lossless-compaction backstop rather than being prevented — the guard is a boundary tool, not a mid-unit one. The value is a single named constant in the consumer helper so it is tunable in one place, intentionally on the conservative side. (55% was the initial choice; lowered to 50% after plan review because 55% + a ~30% unit = ~85% > ~83% did not survive its own arithmetic. A smarter remaining-headroom-vs-recent-per-Epic-delta check is the post-first-use RESEARCH NEEDED direction.)
- **SR-2.2 (read path)** `context_gauge.py` exposes a `read --session-id <id>` subcommand that reads `<tempdir>/.quorum/context-usage-<id>.json` and prints exactly one of FOUR values: the integer `used_percentage`; `no-reading` when the file exists, is fresh, but `context_window.used_percentage` is null/absent (transient early-session or post-`/compact` state — the file IS being updated, the percentage just is not populated yet); `stale` when the file exists but its modification time (SR-1.6) is older than a freshness window (a named constant, default ~120s); or `missing` when the file does not exist. It never prints or implies `0` for an absent/null/stale reading. Exit 0 in all cases (they are normal states, not errors); exit 2 only on a genuinely malformed file per the `fail()` convention. **`stale` is distinct from `no-reading` on purpose** (plan-review re-review): a fresh-but-null reading is transient and safe to continue past, but a stale reading means the producer has stopped updating — we have no trustworthy current reading, and because context only grows within a session a stale reading biases LOW, so it must NOT route to "continue" (see SR-2.3).
- **SR-2.3 (boundary check shape)** At each boundary on a boundary-crossing run, the consumer mirrors the CLAUDE_EFFORT floor-check shape: (1) ONE literal command `printenv CLAUDE_CODE_SESSION_ID` (POSIX) / `Write-Output $env:CLAUDE_CODE_SESSION_ID` (PowerShell); (2) evaluate the result BEFORE creating any gate task; (3) branch:
  - **session id unset/empty (SR-2.4 carve-out)** — skip the guard entirely and silently; continue the run.
  - session id present — run `context_gauge.py read --session-id <id>` (one literal Bash call) and branch on its output:
    - integer **≥ threshold** → **stop** at this boundary (SR-2.5).
    - integer **< threshold** → continue the run, no output.
    - **`no-reading`** → continue the run (transient fresh-but-null; the producer is alive and the value repopulates next tick — at a boundary deep in a run the only null is post-`/compact`, when usage is genuinely low, so continuing is correct). Do NOT stop.
    - **`stale`** → **stop** at this boundary (SR-2.5), noting the producer appears to have stalled. A stalled producer in a supported environment yields an untrustworthy reading that biases low; the fail-safe direction requires stop-and-ask, never continue. This is the key distinction from `no-reading` (which continues): `stale` stops.
    - **`missing`** → **hard-stop** (SR-2.6) UNLESS the persistent opt-out marker (SR-2.8) is set, in which case skip the guard silently: the environment supports the guard (session id present) but no producer is writing the gauge.
- **SR-2.4 (unsupported-CLI carve-out)** When `CLAUDE_CODE_SESSION_ID` is unset/empty (an older CLI that cannot expose session identity), skip the guard silently — the operator has no way to satisfy it. This is the ONLY silent-skip branch. Mirrors the CLAUDE_EFFORT treat-as-unset rule.
- **SR-2.5 (threshold / stale stop)** On an over-threshold reading — or a `stale` reading per SR-2.3 — stop at the clean boundary and tell the operator the run stopped (for context headroom on an over-threshold reading, or because the context-usage producer appears stalled on a `stale` reading), report the current percentage where available, and give the exact fresh-session resume command for the active skill (`/quo-execute <bee-id>`, `/quo-breakdown-epic <bee-id>`, or `/quo-fix-issue all`/the remaining ids). On a stale reading, additionally note that if staleness recurs across fresh sessions the operator should check their status-line producer. No mid-unit continuation.
- **SR-2.6 (missing-reading hard-stop)** On a `missing` reading (and no SR-2.8 opt-out), fire a gate through the two-step `TaskCreate` → `AskUserQuestion` contract whose question (a) states the environment may override user status-line configuration, (b) publishes the file contract (path + required fields + overwrite-per-session semantics), and (c) offers to run `/quo-setup` inline via the Skill tool to install/wrap the producer now. Options at minimum: **Configure now (run /quo-setup)** / **Proceed without the guard (this run)** / **Never guard me (persistent opt-out)** / **Stop here**. `Configure now` dispatches `/quo-setup` inline; because a freshly-installed producer only activates NEXT session (SR-3.4), the current run cannot become guarded by configuring now — so after a successful configure, the gate **recommends resuming in a fresh session** (where the producer is live and the guard works) rather than silently continuing this run unguarded. Continuing the current run anyway is the operator's explicit choice via `Proceed without the guard`. `Never guard me` writes the SR-2.8 opt-out marker so this hard-stop never fires again for this operator.
- **SR-2.7 (load-bearing scope)** The guard fires only on runs that will cross at least one Epic/Issue boundary — quo-execute multi-Epic scope / Mode 2, quo-breakdown-epic Mode 2 multi-Epic, quo-fix-issue `all`/list. Single-unit runs (the operator is present at every boundary) never invoke the guard.
- **SR-2.8 (persistent opt-out)** The consumer checks for a persistent opt-out marker at a documented stable location (proposed `<tempdir>/.quorum/context-guard-opt-out`) BEFORE the missing-reading hard-stop (SR-2.6). When present, the missing-reading hard-stop is skipped silently — an operator who wants to run unguarded expresses it ONCE, not at the first boundary of every session. The opt-out suppresses only the missing-reading hard-stop; it does NOT suppress a genuine over-threshold stop (SR-2.5) when a gauge IS present, because an operator with a working gauge still benefits from the boundary stop. This resolves the tension between the setup step being optional (SR-3.1) and the hard-stop being mandatory-feeling: declining setup once and opting out is a supported, friction-free path, while the discovery hard-stop still fires for the unconfigured-but-willing operator who has not opted out. Note `<tempdir>` is not durable across all environments (it is on the container); the marker is "persistent" within an environment's tempdir lifetime — a fully durable location is a RESEARCH NEEDED refinement if per-tempdir persistence proves too weak.

### SR-3 — Setup (quo-setup producer install)
- **SR-3.1** quo-setup gains a new OPTIONAL, AskUserQuestion-gated step (modeled on the optional PRD/SDD bootstrap section) that offers to configure the producer by writing/updating the `statusLine` key in the user settings file to point at `context_gauge.py produce`.
- **SR-3.2 (wrap-don't-replace)** When a `statusLine` command already exists in the user settings, the step preserves it: it configures `context_gauge.py produce --wrap-command "<existing command>"` so the operator's current display is retained while the gauge is added. It never overwrites an existing status line's display output.
- **SR-3.3 (pinned-environment detection)** The step must recognize that in environments where a higher-precedence settings source pins `statusLine` (e.g. a `--settings` wrapper), a user-settings write cannot win, and must say so rather than silently writing an ineffective setting — pointing the operator at the published file contract so the environment owner can satisfy it directly. (Detecting this precisely may be limited; at minimum the step states the caveat.)
- **SR-3.4 (activation caveat)** The step states that status-line config loads at session start, so a freshly-installed producer takes effect from the NEXT session — mirroring the existing "restart Claude Code / run /agents to register subagents" caveat.
- **SR-3.5** The producer path is resolved and written using quo-setup's own base directory (own-skill resolution); the three execution skills resolve the same helper for the `read` path via sibling resolution (`<base>/../quo-setup/scripts/context_gauge.py`), paired POSIX/PowerShell.
- **SR-3.6 (opt-out offer)** Alongside install/wrap, the quo-setup step offers a "run unguarded" choice that writes the SR-2.8 persistent opt-out marker, so an operator who does not want the guard is not hard-stopped on every boundary-crossing run and does not have to decline at each session's first boundary.

### SR-4 — Cross-cutting
- **SR-4.1** All new shell snippets ship as paired POSIX bash + Windows PowerShell blocks; all multi-step/JSON logic lives in the Python helper, invoked as a single literal Bash call (bash-etiquette + design rule 2).
- **SR-4.2** The consumer gate, when it fires, obeys the two-step `TaskCreate` → `AskUserQuestion` contract and the `gate-askuserquestion-<short-suffix>` naming + yield-control discipline, exactly as the other gates in these skills.
- **SR-4.3** Sequenced after b.ja9: the guard check co-locates with b.ja9's rewritten boundary prose in quo-execute §4.2, quo-breakdown-epic Mode 2, and quo-fix-issue `all`/list; the two changes must compose (b.ja9 makes any compaction the guard does not prevent lossless).
- **SR-4.4 (session-identity equality — load-bearing invariant, live-verified)** The producer keys the gauge filename by the status-line payload's `session_id` (SR-1.1); the consumer reads by `$CLAUDE_CODE_SESSION_ID` (SR-2.3). The design REQUIRES these two identifiers to be the same string for the same session — if they diverge, every `read` returns `missing` and the feature perpetually hard-stops despite a healthy producer. **This equality was verified live** (2026-08-16, Claude Code 2.1.232, inside claude-secure-container): `printenv CLAUDE_CODE_SESSION_ID` returned `b42db875-bab7-4e32-82b2-5f058d0f7ae1`, and the container producer wrote `context-usage-b42db875-bab7-4e32-82b2-5f058d0f7ae1.json` — the payload `session_id` equals the env var byte-for-byte. Epic 1 may hardcode the shared key on this basis. Its test suite should carry an explicit note documenting the assumed equality (the tests inject a synthetic `session_id` on both sides, so they cannot themselves catch an upstream divergence), and any future Claude Code version that breaks the equality is tracked via the re-probe Issue b.cj2.

## Background and rationale

This SDD follows a multi-day investigation (2026-08-14→16) that started from "does the workflow clear context between Epics in work-through-all-Epics mode?" and found the existing "Epic-boundary context-clear discipline" instructs the model to do something it cannot — corrected separately as defect b.ja9. This feature is the constructive follow-on: since the model cannot clear or observe its own context natively, an out-of-band status-line writes a measured usage value to a well-known file that the workflow reads at clean boundaries. Every load-bearing fact was verified rather than assumed: the status-line payload schema and its null cases against official Claude Code docs (code.claude.com/docs/en/statusline) and confirmed live on both a corporate-managed macOS host and inside claude-secure-container; `CLAUDE_CODE_SESSION_ID` observed exported to Bash live this session; wrap-don't-replace proven on the host's pre-existing status line; and the container producer already shipped and observed writing this session's gauge (30%→ growing) live. The producer/consumer split exists specifically because a higher-precedence `--settings` source can pin the `statusLine` slot in some environments (the container), so no single installer can win everywhere — the published file contract is what makes the one consumer work across all of them.

## Decisions and rejected alternatives

- **Decision: producer/consumer split with the gauge file as the single contract.** The consumer is environment-agnostic and branch-free; only the producer's install path varies. This is what lets one boundary check cover ordinary machines and pinned/wrapper environments.
- **Decision: the consumer `read` path is a bundled Python helper subcommand, not inline `jq`.** Bash etiquette forbids the multi-step/JSON-parse shape inline; the helper keeps the boundary check to two single literal Bash calls (`printenv`, then `context_gauge.py read`).
- **Decision: helper lives in `quo-setup/scripts/` with `produce`/`read` subcommands.** quo-setup owns installation (the `detect_fast_path.py` "installer owns its script" precedent), and the three execution skills sibling-resolve it for the `read` path (the `scoped_marker_resolver.py` cross-skill precedent). *Alternative considered:* placing it in `quo-execute/scripts/` (primary consumer) like `hive_commit.py`; rejected because quo-setup is the install site and keeping producer+reader in one file under the installer's dir is the cleaner ownership story. Final placement can be confirmed at breakdown.
- **Decision: default threshold 50% (single authoritative value — see SR-2.1).** Derived from ~83% compaction minus a ~25-30% per-Epic budget: 50% + a ~30% unit ≈ 80% < ~83%. Lowered from an initial 55% during plan review because 55% + a ~30% unit ≈ 85% > 83% did not survive its own arithmetic. The guard is a boundary tool that cannot prevent a mid-oversized-unit compaction — that case degrades to b.ja9's lossless backstop, stated explicitly rather than overclaimed. The PRD `## Open Questions` records the same 50% resolution so the docs agree. Post-first-use recalibration is flagged RESEARCH NEEDED. (This is the SINGLE threshold-decision bullet — Epic 1's helper constant must read 50%.)
- **Decision: distinguish `missing` (hard-stop) from `no-reading`/null (continue).** A file-absent reading means the producer isn't wired → FR4 hard-stop; a present-but-null reading is a transient early/post-compact state → continue. Treating them the same would either nag on transient nulls or silently skip a genuinely misconfigured environment.
- **Decision: reject stale readings via file mtime, routing them to a STOP (plan-review #4, corrected in re-review).** Because context grows monotonically, a stale gauge biases low and low routes to "continue" — the banned fail-safe direction. The read path returns a distinct `stale` classification (file present, mtime older than the freshness window) that routes to a **stop** (SR-2.3 / SR-2.5), NOT to the `no-reading` continue branch. The first attempt folded stale into `no-reading`, which left "stale → continue" open and, worse, discarded a valid over-threshold-then-stalled stop signal; the corrected design keeps `stale` distinct and stopping. Chosen mtime over an embedded timestamp field to avoid a producer change (overwrite already updates mtime).
- **Decision: persistent opt-out marker (plan-review #6).** Resolves the optional-setup-vs-mandatory-hard-stop tension: an operator who wants to run unguarded writes the marker once (offered by quo-setup, or via the hard-stop's "Never guard me" choice) instead of being hard-stopped every session. The opt-out suppresses only the missing-reading hard-stop, never a real over-threshold stop.
- **Decision: "Configure now" recommends a fresh session (plan-review #3).** A freshly-installed producer only activates next session, so configuring cannot guard the current run; the honest remedy is to resume in a fresh session, not to silently continue this one unguarded.- **Decision: hard-stop (not silent-skip) on `missing`, with an inline `/quo-setup` offer.** The hard-stop is the discovery mechanism for pinned environments. *Rejected: silent-skip when unconfigured* — false comfort, the wishful-prose failure class b.ja9 fixes.
- **Decision: exactly one silent carve-out** — `CLAUDE_CODE_SESSION_ID` unset — because those operators cannot satisfy the guard at all.
- **Rejected: parsing the session transcript for usage** — the format is documented internal/version-unstable and the workflow can't locate its own transcript.
- **Rejected: relying on the model's innate context awareness** — real but unverifiable; nothing to threshold against.
- **Rejected: a hook-based producer** — deferred to b.cj2 (upstream #27969). Hooks merge across settings sources (unlike the winner-takes-all `statusLine` slot), so a hook producer would work even in pinned environments — but hook-visible context usage is not shipped upstream yet.
- **Rejected: quo-setup forcing the producer into every environment** — impossible where a higher-precedence source pins `statusLine`; hence the published contract + per-environment producer.
