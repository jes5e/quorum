## Context

Core of Epic 2 (SDD SR-3): `/quo-setup` gains a new OPTIONAL, `AskUserQuestion`-gated step that wires the Epic 1 producer into the operator's environment by writing/updating the `statusLine` command in the user settings to invoke the gauge helper's `produce` subcommand. quo-setup writes no settings file today; the optional PRD/SDD-bootstrap section is the in-skill precedent for a detect-then-offer, gated, optional setup step. The Claude Code statusLine settings shape, session-start loading behavior, and settings-precedence pinning were verified against official Claude Code documentation and live probes during spec authoring (SDD `## Background and rationale`) — treat those SDD-recorded facts as the external contract; no discovery probes are needed.

Depends on Task 1: the step installs `--wrap-command` wrappers, so the wrap-blanking fix must land first and this step's prose must describe the post-fix semantics.

## What Needs to Change

- Add the new optional step to the quo-setup skill prose, slotted in the slow path near the Build Commands / Next Steps sections, modeled on the optional Bootstrap-PRD/SDD section (SR-3.1).
- The step detects whether a `statusLine` command already exists in the user settings and branches:
  - none → offer to write a `statusLine` pointing at the helper's `produce` subcommand, resolved via own-skill base-directory resolution (SR-3.5);
  - existing → wrap-don't-replace: configure `produce --wrap-command "<existing command>"` so the operator's current display is preserved (SR-3.2).
- Offer a "run unguarded" choice that writes the persistent opt-out marker (SR-3.6); the marker's location is the documented stable path in the SDD (SR-2.8) and is a cross-Epic string contract — Epic 3's consumer reads it, so the exact path must match the SDD verbatim.
- Declining the step leaves all setup behavior unchanged.
- State both caveats in the step prose: (i) pinned-environment — where a higher-precedence settings source pins `statusLine`, a user-settings write cannot win; say so and point at the published file contract instead of writing an ineffective setting (SR-3.3); (ii) activation — status-line config loads at session start, so the producer activates from the NEXT session, mirroring the existing restart/hot-reload subagents caveat (SR-3.4).
- Idempotency: re-running the step detects an already-configured producer (direct or wrapped) and does not double-wrap or duplicate configuration.
- Decide and document whether the fast path offers this step or only the slow path (an explicit requirement on the Epic body — the decision and its rationale must appear in the step prose or the fast-path section, not just in review notes).
- The settings read-modify-write must comply with the repo's Bash etiquette and SR-4.1: multi-step/JSON logic belongs in a bundled Python helper invoked as a single literal command, not in inline shell. Whether that means a new helper, a new subcommand on the existing gauge helper, or first-class Read/Write tool usage is the implementer's design call — but the constraint is binding.

## Why

Ordinary machines should get the guard's producer without manual configuration, while operators with an existing status display keep it, and operators who want to run unguarded say so exactly once. This step is also the configure-now action Epic 3's missing-reading hard-stop dispatches inline.

## Cross-Task / cross-Epic contract

- **Inline invokability (Epic 3, t1.55r.h9):** Epic 3's missing-reading hard-stop offers this step inline via the Skill tool. The step must therefore be invokable that way and be idempotent — the gate may fire on a machine where the step already ran.
- **Opt-out marker path (Epic 3):** the marker path written here is read by Epic 3's consumer check; it is a protected string contract per the SDD — do not vary it.
- **Helper path resolution symmetry (Epic 3):** this step resolves the helper via own-skill resolution; Epic 3 sibling-resolves the same helper for `read`. Keep the two consistent so they name the same file.
- **Wrap semantics (Task 1):** the step's description of wrap behavior must match Task 1's post-fix implementation.
- **Producer failure semantics (Task 1, PM-pinned cross-check):** with Task 1's fix landed, `produce` always exits 0 and reports a malformed payload only as a single stderr line — the step prose must not describe the producer as failing loudly (non-zero exit) on a malformed payload, and any troubleshooting guidance must route through `read`'s `stale`/`missing` classifications rather than the producer's exit code.

## Success Criteria

- Running `/quo-setup` presents the new optional step; declining leaves setup behavior unchanged (no settings write).
- Accepting with no existing status line writes a `statusLine` invoking `produce`; accepting with an existing status line wraps it, preserving the existing display while adding the gauge.
- The step prose states the pinned-environment caveat and the next-session activation caveat.
- The "run unguarded" choice writes the opt-out marker at the SDD-specified path.
- Re-running `/quo-setup` is idempotent for this step: an already-configured producer is detected and not double-wrapped.
- The fast-path treatment of this step is decided and documented.
- Existing quo-setup flow (hive registration, CLAUDE.md contract-key writes, fast-path re-registration) is unregressed.
- All new snippets are paired POSIX + PowerShell; prose is project-neutral; any scratch writes follow the workflow scratch-dir convention with no cleanup; no shipped-artifact reference to repo-only docs (CLAUDE.md review criteria).
