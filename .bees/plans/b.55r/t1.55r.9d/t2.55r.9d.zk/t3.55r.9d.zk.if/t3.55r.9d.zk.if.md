## Context

This is the user-visible half of the Task: a new OPTIONAL, `AskUserQuestion`-gated step in the quo-setup slow path that offers to wire the gauge producer into the operator's status line (SR-3.1), wraps an existing status line rather than replacing it (SR-3.2), offers a run-unguarded opt-out (SR-3.6), and states both caveats (SR-3.3 pinned environments, SR-3.4 next-session activation).

The structural model is the existing `### Bootstrap PRD/SDD from existing codebase (optional)` section (SKILL.md lines 487-644): detect repo state first, reframe the question so the operator understands what it buys them, then offer a small set of genuine choices, then act. Follow that shape rather than inventing a new one.

quo-setup writes no settings file today — this is the skill's first such write, and the entire mechanism lives in the bundled helper's `inspect-statusline` / `install-statusline` / `write-opt-out` subcommands (sibling subtasks), so this section's job is detection-driven branching, gating, and honest reporting.

Preconditions: both helper subtasks have landed.

## What Needs to Change

**`skills/quo-setup/SKILL.md`** — add one new section, `### Configure the context-usage gauge producer (optional)`, between `### Build Commands` (line 646, ending at line 708) and `### Next Steps` (line 710).

1. **Opening framing.** Two or three sentences, in the same register as the bootstrap section's "Why this matters" block: Claude Code reports how much of the model's context window is in use to the status-line command and nowhere else, so a small producer republishes that reading to a per-session file the workflow can read back at clean stopping points. State that it is optional and that declining changes nothing else about setup.

2. **Detect first.** A paired POSIX/PowerShell snippet running the inspector as one literal command, using own-skill base-directory resolution exactly as the fast-path detector does at lines 106-116 — `<bees-setup-base-dir>/scripts/context_gauge.py` on POSIX and `<bees-setup-base-dir>\scripts\context_gauge.py` on PowerShell, with the same "Replace `<bees-setup-base-dir>` with the literal path from the skill invocation header" instruction. Show the JSON payload shape inline, as the fast-path section does at lines 118-132.

3. **Skip rules, evaluated before any prompt — in this order (the order is load-bearing).**
   1. **Opt-out first:** when `opt_out_marker_present` is true — say nothing at all and move on. This rule short-circuits the WHOLE step, including the refresh branch below: an operator who chose "run unguarded — don't ask again" gets no writes and no announcements, even when a stale producer configuration is detected. (The direct-invocation entry point in the sibling fast-path subtask deliberately OVERRIDES this rule and is the sole exception: on the direct path an existing marker is reported and the gate still fires — an explicit request to configure is itself the change of mind the marker was never meant to veto.)
   2. **Already-configured-and-current second:** when `producer_state` is `direct` or `wrapped` AND `producer_current` is true — print one line ("The context-usage gauge producer is already configured.") and move on with no question. When the state is `direct` or `wrapped` but `producer_current` is **false** (the installed command's interpreter or path no longer matches what would be composed now — e.g. a moved or upgraded interpreter, which leaves a silently broken status line), do not fire the gate either: take a short **refresh** branch — announce that an existing producer configuration is stale, name any detected higher-precedence sources per item 7(a)'s conditional caveat (the refresh has no gate, so this announcement is where SR-3.3's honesty requirement lands), run `install-statusline` (single literal command), and report per item 5's reporting duties: echo `previous_command`, report the self-check outcome, and do not present a failed self-check as complete.

   State explicitly that this ordering is what makes the step idempotent and what makes it safe for a boundary-time gate to dispatch on a machine where it already ran.

4. **The gate.** Otherwise fire `AskUserQuestion` with exactly three options (the runtime auto-appends a free-text slot; per the multi-choice-only convention do **not** add a fake "Other").

   **Pre-gate pinned-environment evaluation (SR-3.3, ordering is load-bearing):** BEFORE composing the gate, evaluate the conditional half of the pinned-environment caveat. When `higher_precedence_sources` is non-empty, the gate's question text must name each entry's scope and path and state plainly that a user-settings write may not take effect there, and option 1 must drop "(recommended)" — its label states the write may be outranked. When a managed entry's reason is `disableAllHooks` / `allowManagedHooksOnly`, the question must lead with the published-file-contract pointer (the environment owner must satisfy the contract; a user-settings write is documented to be silently skipped) rather than presenting the write as the recommended action. SR-3.3's "say so rather than silently writing an ineffective setting" is only honest if the operator learns this before choosing, not after the write.

   1. **Configure it (recommended — only when no higher-precedence source was detected)** — when `producer_state` is `foreign`, the label must say the existing status line will be preserved and the gauge added alongside it, and the question text must quote the operator's current command back to them. When `producer_state` is `other-install`, the question must state that an existing gauge producer at a different path was found, that it will be repointed at this install, and that any wrapped display inside it is preserved rather than nested.
   2. **Not now** — no write of any kind; re-offered on a future setup run.
   3. **Run unguarded — don't ask again** — writes the persistent opt-out marker.
   Note in prose that the wrap-vs-direct decision is made from the detection result, not by the operator — there is no "wrap it" option, because wrapping is what "Configure it" already does when a status line exists.

5. **Act.** Paired snippets for `install-statusline` (option 1) and `write-opt-out` (option 3), each a single literal command. The prose must also disclose the self-check side effect: after the write, the step exercises the new command once with a synthetic payload to verify it produces a reading — which runs the operator's wrapped command once. Show the summary JSON shape and instruct: report `action`, echo `previous_command` back to the operator verbatim when non-null with the note that it is the only record of their prior configuration, and report the self-check outcome. If `self_check.verified` is false, tell the operator the setting was written but the command did not produce a reading when exercised, quote `self_check.detail`, and say the status line may come up blank — do not present the install as complete.

6. **Caveat: activation (SR-3.4).** State that status-line configuration is picked up when a session starts, so the producer should be treated as active from the **next** session, and the run in progress must not be assumed guarded. Mirror the register of the existing restart/`/agents` subagents caveat.

7. **Caveat: pinned environments (SR-3.3).** Two parts, both required. (a) Conditional — **evaluated pre-gate and folded into the gate's question text per item 4**; do not defer it to after the write. (b) Unconditional, stated even when the detected list is empty: some higher-precedence sources cannot be detected from disk — a session launched against an explicit settings file, organization settings delivered at sign-in, and MDM policy — so a written setting can still be silently outranked. In both cases point the operator at the published gauge-file contract in the project's customer-facing documentation so their environment owner can satisfy it with a producer of their own, rather than at a setting that cannot take effect.

8. **Opt-out semantics.** One short paragraph: what the marker suppresses (only the stop that fires when no reading is being published), what it does not suppress (a genuine over-threshold stop when a reading *is* present), where it lives (`<tempdir>/.quorum/context-guard-opt-out`, spelled per-OS in the paired convention this repo uses elsewhere), and that removing that file re-enables the offer. **Do not prescribe a deletion command** — name the file and let the operator remove it.

9. **Troubleshooting wording constraint (PM-pinned).** Any diagnostic guidance must route through the reader's classifications — no reading published, or a reading that has stopped refreshing — and must **not** describe the producer as failing loudly or exiting non-zero on a malformed payload. Post-Task-1, `produce` exits 0 on every input shape and reports a malformed payload only as a single stderr line. Do not write prose that contradicts that.

10. **Fast-path pointer.** One sentence recording that the fast path also offers this step, with the rationale stated in the fast-path section (sibling subtask owns that text).

**Constraints (mandatory).** Every snippet ships as paired POSIX bash + Windows PowerShell blocks — no bash-only fallback. Prose must be project-neutral: no ticket ids, no Epic/Task references, no paths into this repo, and no cross-reference to a repo-only document (`docs/*`, `CONTRIBUTING.md`, or a `CLAUDE.md ## <section>` other than the two contract keys) — such a reference dangles on a fresh install. Point at "the project's customer-facing documentation" generically rather than at a filename. No scratch file is needed by this step; if one is introduced it must live under `<tempdir>/.quorum/` and must not be cleaned up.
