**Fix-path resolution (orchestrator note, 2026-08-18):** the implementation subtask for this Task implements refined path (b) — `produce` exits `0` on every input shape, always emits the display, and downgrades the unparseable-stdin `fail()` to a stderr-only `warn()`. Path (a) (emit-then-exit-2) was rejected because the harness blanks the status line on any non-zero exit regardless of stdout (verified against https://code.claude.com/docs/en/statusline: "Scripts that exit with non-zero codes or produce no output cause the status line to go blank"). Wherever the body below states per-path wording, the path-(b) wording applies; still verify against the landed diff rather than assuming.

## Context

Task 1 changes what `context_gauge.py produce --wrap-command <cmd>` does on two stdin shapes that currently blank the operator's wrapped status line: (i) non-empty unparseable stdin (`cmd_produce` at `skills/quo-setup/scripts/context_gauge.py:366-369` returns `fail(...)` -> exit 2 before `run_wrapped` is ever reached), and (ii) empty/whitespace-only stdin (`skills/quo-setup/scripts/context_gauge.py:371-373` returns 0 with no `emit_display` call).

`docs/doc-writing-guide.md` `## The context-gauge file contract` (the contributor-facing depth section, currently lines 207-249) is the ONLY doc in the repo that states the pre-fix blanking behavior in prose. The offending text is in the ``**The `produce` subcommand.**`` paragraph at line 229, specifically these two sentences (verbatim):

1. "A stdin payload that is non-empty but unparseable (not JSON, or JSON that is not an object) is the one case that is *not* a no-op: `produce` exits `2` with a single human-readable line on stderr and emits no display at all, so the harness sees a non-zero exit and a blank status line."
2. "Environment owners publishing the gauge themselves, and anyone wiring `produce` as a `statusLine` command, should read that blank line as the visible symptom of a malformed payload rather than of a missing gauge."

A second, subtler gap in the same paragraph: the empty/whitespace-only stdin shape is **not documented at all** today. The paragraph documents the no-usable-`session_id` no-op ("A payload carrying no usable `session_id` is a 0-exit no-op that writes nothing — there is nothing to key a gauge file on, and the display is still emitted." — that sentence stays true post-fix and must survive) but never says what an empty-stdin refresh does to the display. The Task body requires BOTH blanking shapes to be explicitly dispositioned in prose, so this subtask closes the documentation gap for shape (ii) as well as correcting shape (i).

This subtask assumes the implementation Subtask has already landed and has settled the fix path — (a) trivial-tweak (emit the wrapped display, then return the exit-2 failure) or (b) refactor-locally (treat unparseable stdin as a 0-exit no-op). The wording differs per path; both are specified below. Do not guess the path — read the landed diff in `skills/quo-setup/scripts/context_gauge.py` and `tests/test_context_gauge.py` and document what actually shipped.

This section is the contributor-facing home for the decision record the Task body requires ("The decision record (choice + why) belongs in the diff's documentation updates, not only in the conversation"). The customer-facing README carries only the operator-level guarantee (sibling doc Subtask), so the reasoning belongs here.

## What Needs to Change

**1. Replace the two pre-fix sentences in the ``**The `produce` subcommand.**`` paragraph (`docs/doc-writing-guide.md:229`).** Keep the rest of that paragraph intact — the once-drained-stdin sentence, the wrap-don't-replace sentence, the omit-the-flag default-display sentence, and the no-usable-`session_id` no-op sentence are all still accurate post-fix and must not be reworded gratuitously.

SUPERSEDED — path (b) shipped (see the orchestrator note above); the following path-(a) wording is retained for history only and must NOT be implemented:

- Non-empty unparseable stdin (not JSON, or JSON that is not an object) is still a reported failure: one human-readable line on stderr, exit `2`.
- The display is emitted **before** that failure returns: under `--wrap-command` the once-captured stdin bytes are still fed to `<cmd>` and its stdout re-emitted verbatim, so a malformed payload no longer blanks a wrapped operator's status line. Without `--wrap-command` there is no parsed payload to build a default display from, so the display is empty — that is the unwrapped case only.
- Empty or whitespace-only stdin is a 0-exit no-op that writes nothing, and (state explicitly what the landed code does) the wrapped display is emitted for that shape too.
- The observable symptom of a malformed payload for a wrapped operator is now the **non-zero exit and the stderr line**, not a blank status line. The replaced sentence-2 above told readers to diagnose from the blank line; that diagnostic advice is now wrong and must be replaced with the exit-code/stderr diagnostic.

The implementation shipped **path (b) — unparseable-is-a-no-op** (verify against the landed diff). The replacement text must convey:

- Both empty/whitespace-only stdin and non-empty unparseable stdin exit 0 and write nothing to the gauge (the unparseable shape is not a full no-op — its malformation diagnostic is retained as a single human-readable stderr line), and under `--wrap-command` the captured stdin bytes are still fed to `<cmd>` and its stdout re-emitted, so no producer-side parse failure can blank the operator's display.
- `produce` no longer has an input-parse exit-2 path at all; exit `2` from `produce` is now reserved for argparse usage errors.
- The diagnostic consequence, stated plainly because it is a real loss: a malformed payload is now silent **on the exit code** — the single human-readable stderr line is retained, but it is invisible on the status line itself. The operator-visible symptom moves downstream — the gauge stops being refreshed, so `read` reports `stale` (and `missing` if it never got a first write). Environment owners should diagnose a suspected payload-schema change by reading the gauge back rather than by watching the status line or the exit code.
