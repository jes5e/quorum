- Update the customer-facing docs to document the new optional quo-setup step: its four behaviors (configure the producer; wrap-an-existing-status-line, which is what configure does when a status line exists rather than a separate gate option; run-unguarded opt-out; decline), presented as the three options the shipped gate actually offers, how to enable it, and its two caveats (next-session activation; pinned environments where a user-settings write cannot win, with a pointer to the published file contract).
- Reflect the step in the skill catalog / setup-flow description where the customer-facing docs enumerate what `/quo-setup` does (the docs' catalog table is the single source of truth for the user-visible surface).
- Document the opt-out: what the "run unguarded" choice does, what it suppresses (the missing-reading stop) and what it does not (a genuine over-threshold stop), and where the marker lives — consistent with the published gauge-contract section's level of detail.
- Keep consistency with the existing gauge-contract section (which Task 1 may have amended): terminology, paths, and semantics must agree across the two sections.
- Amend the pre-existing scratch-files/deletion-semantics paragraph in the customer-facing docs (the one enumerating the residents of the workflow scratch directory and their regeneration semantics — "safe to delete between runs", body files regenerate, the run-state manifest does not, the gauge file heals itself): after Task 2, the persistent opt-out marker is a SECOND non-regenerable resident whose deletion is silent and behavior-changing (it clears the operator's standing opt-out and, once Epic 3's consumer lands, re-arms the missing-reading stop). Name it there. Keep the wording consistent with the CLAUDE.md-internal statement of the same fact landed by Task 2's doc subtask (which runs first).
- Conditional verification (not a forced edit): if Task 2 shipped a NEW bundled helper script, check whether the customer-facing "where bundled helper scripts live" list warrants naming it; a legitimate no-op if no new helper shipped.
- Document the direct-invocation path: the customer-facing skill catalog / usage surface must name `/quo-setup`'s producer-configuration argument and the configure-only direct path it triggers (skips full setup; usable on a machine with no configured repo), matching the trigger of the shipped direct-invocation section (the frontmatter `argument-hint` is hint text and may carry optionality brackets) and the extended skill `description`.
