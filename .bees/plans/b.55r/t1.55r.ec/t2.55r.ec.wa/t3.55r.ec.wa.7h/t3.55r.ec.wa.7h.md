## Context

Task 1 adds `skills/quo-setup/scripts/context_gauge.py` and, with it, a protected cross-skill string contract: the gauge-file path `<tempdir>/.quorum/context-usage-<session_id>.json`, the two subcommands (`produce`, `read`) and their flags (`--wrap-command`, `--session-id`), the JSON field names (`session_id`, `context_window.used_percentage`), and the four-value `read` output vocabulary. Three downstream lanes consume it: Epic 2 (t1.55r.9d) points the Claude Code status line at `produce`, Epic 3 (t1.55r.h9) sibling-resolves `read` from the execution skills, and sibling Task 3 (t2.55r.ec.jj) publishes the user-visible half in the README.

The repo's established carrier for a contributor-facing cross-skill string contract of exactly this shape is `docs/doc-writing-guide.md`: `## The Scoped-marker contract` (currently docs/doc-writing-guide.md:165-205; line numbers in this body are advisory — the heading anchors are the operative locators, re-resolve at execute time) documents the Scoped-marker's grammar, hard-fail rules, and bundled parser, and the SDD's Key-components bullet for that script points at the section. No sibling lane owns this carrier for the gauge contract — Task 3 is scoped to the customer-facing README (different audience: where the file lives, its required fields, overwrite-per-session semantics, the restricted/pinned-statusline note), Epic 2 to the `/quo-setup` install step, Epic 3 to the cumulative PRD/SDD `### Feature:` subsections. Without this section, the "do not rename without updating all consumers in lockstep" rule has no durable home and a future contributor renaming a subcommand or field has nothing to read.

Assumes Task 1's helper has landed, so the section documents the contract **as built**, not as planned.

## What Needs to Change

Add one new section, `## The context-gauge file contract`, to `docs/doc-writing-guide.md`, placed immediately after `## The Scoped-marker contract` and before `## Hard-fail preconditions` (heading anchors operative; the current line positions ~205/~207 are advisory). Mirror the Scoped-marker section's structure and depth. Cover:

- **The gauge-file path**: `<tempdir>/.quorum/context-usage-<session_id>.json`, with `<tempdir>` resolved via `tempfile.gettempdir()`; the `session_id` keying is what keeps concurrent sessions from colliding.
- **The file shape**: `{"session_id": ..., "context_window": {...}}`, with `context_window.used_percentage` named as the field consumers read.
- **Write semantics**: overwrite-per-refresh (truncate-and-write, a live gauge, never append); the overwrite is what keeps mtime current, and mtime — not an embedded timestamp field — is what freshness is judged against.
- **The `produce` subcommand**: reads the status-line JSON from stdin exactly once; `--wrap-command` is wrap-don't-replace (the once-captured stdin bytes are re-fed to the wrapped command and its stdout re-emitted verbatim); a payload with no `session_id` is a 0-exit no-op that writes nothing.
- **The `read` subcommand's four-value output vocabulary**: the integer `used_percentage`, `no-reading`, `stale`, `missing` — all exit 0 (they are normal states); exit 2 only on a genuinely malformed file. State the fail-safe constraint as a contract rule: a consumer must never treat an absent, null, or stale reading as `0` or as headroom, and `stale` and `no-reading` are distinct values that must not be collapsed.
- **The two named constants** (stop threshold, freshness window) as single-definition-site tunables inside the helper that consumers read rather than re-derive.
- **The lockstep rule**: the path, subcommand names, flag names, and field names are a string contract; renaming any of them requires updating every consumer in the same change — the same warning `## The lookup-key pattern` carries for the CLAUDE.md contract keys.
- **The interpreter-floor note**: this helper deliberately targets a lower Python floor than the rest of the repo's toolchain (no PEP 604 union annotations), because the status line invokes it with whatever `python3` resolves on the operator's PATH — which can be an older system interpreter than the one the toolchain floor governs. Contributors editing the helper must preserve that constraint.

Scope boundaries — do not write these here:

- Do NOT describe the status-line install step or its caveats (Epic 2 owns that).
- Do NOT describe boundary-guard routing — which value routes to stop vs. continue at an Epic/Issue boundary (Epic 3 owns that). Documenting the *values* is contract; documenting what an orchestrator *does* with them is not yet true of any shipped skill, and the guide's own `## What not to document` forbids pre-documenting features that do not exist.
- Do NOT restate the customer-facing README material Task 3 authors.

Style: follow the guide's own `## Inline style` — sentence-case heading, backticked paths/flags/subcommand names, no emojis.
