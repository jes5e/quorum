## Context

Fourth required element of Task 3's README section, and the reason the file contract is published at all. PRD FR6 and the b.8sh acceptance criterion ("The customer-facing docs contain the reading's location, required fields, freshness/overwrite semantics, and a restricted-environment note") require the docs to tell an operator whose environment pins the status-line slot how to satisfy the contract themselves. The SDD's rejected-alternative record is the rationale: quo-setup forcing the producer into every environment is impossible where a higher-precedence settings source wins the `statusLine` slot, so the published contract plus a per-environment producer is the design.

Precondition: the sibling Subtask that authors the gauge-contract subsection has landed, so this note appends to an existing section rather than creating one. This Subtask edits the same README region and is deliberately sequenced after it.

## What Needs to Change

Append a short note (a titled paragraph, or a `**Restricted / pinned status-line environments.**` lead-in paragraph — match whichever shape the surrounding README prose uses) to the end of the `### The context-usage gauge file` subsection in `README.md` (the exact heading pinned by the preceding Subtask). It must convey:

- **Who this is for.** An environment where a higher-precedence configuration source pins the status-line slot — e.g. a launcher that passes `--settings`, or a managed/organization-level settings file that outranks user settings — so a user-level status-line write cannot take effect. Describe the situation generically; do not name any specific product, container image, or internal tool (design rule 3, project-neutral prose).
- **The self-service path.** Any process that writes a conforming file at the published path — keyed to the current session id, with the fields above, refreshed at least as often as the freshness window — satisfies the contract. The producer does not have to be quorum's helper: the environment's own status-line command, a wrapper around it, or any other process that can see the session's context-usage payload works equally well. No quorum-side change is needed, and nothing in the workflow needs to know which producer wrote the file.
- **How to confirm it works.** Optional but recommended: a one-line conformance check using the reader that Task 1 shipped — `context_gauge.py read --session-id <id>` — written with `<id>` as a placeholder. If included, it ships as paired POSIX bash + Windows PowerShell labeled blocks that are actually runnable by the operator: include the interpreter invocation (`python3` on POSIX, `python` on Windows), point the reader at the `### Where bundled helper scripts live` subsection (or restate the `skills/<skill-name>/scripts/` convention in one clause) so the helper's path is resolvable per-install rather than hardcoded, and note in one clause that the current session's id is available in the `CLAUDE_CODE_SESSION_ID` environment variable (that is how the reader obtains `<id>`; the variable's existence is environment fact, not guard behavior). The snippet must describe only what the reader prints, not what any consumer does with the value.

Scope guards, all enforced by review:

- Do NOT describe `/quo-setup`'s producer-install step, its wrap-don't-replace behavior, or its next-session activation caveat as the alternative for non-pinned environments — Epic 2 (t1.55r.9d) owns that prose. This note may say the contract can be satisfied by any producer without cross-referencing a setup step that does not exist yet at this Epic.
- Do NOT describe the boundary guard's stop behavior, its threshold, or the missing-reading prompt — Epic 3 (t1.55r.h9) owns those.
- Do NOT restate the location/fields/semantics already published by the sibling Subtask; reference them ("the path and fields above") rather than duplicating.
- Keep it short. This is operator-facing orientation, not the contributor-facing contract section in `docs/doc-writing-guide.md`.
