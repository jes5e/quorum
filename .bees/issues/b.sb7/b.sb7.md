## Description

The Doc Writer is instructed to describe "what was actually built" from the Engineer's diff and to append or rewrite a `### Feature: <title>` subsection in the project PRD and SDD on every run, in both execute and fix mode. The Doc Reviewer is instructed to grade the result as a current-state cheat sheet with no design decisions and no history, and to hunt for completeness gaps and duplication. The two contracts contradict each other, and neither assigns any kind of fact a single owning document. The result across every repo using quorum is an SDD that restates mechanism already in the code, carries ticket-keyed history, and duplicates facts across three to six carriers, so every fix pays a doc tax and every doc-review round finds something.

## Expected behavior

### Ownership

Every kind of fact has exactly one owning carrier, and the Doc Writer routes facts to owners instead of updating every doc the diff touches:

| Kind of fact | Owner | Never in |
|---|---|---|
| Mechanism: what the code does, internal constants, enum arms, field and metric names, step-by-step algorithms | the code and its doc comments | the SDD |
| Rules: current-state invariants, the contracts the code honors, decisions with rejected alternatives, verified external facts with their source | the SDD register, stated as the rule with its why, a code pointer, and a test pointer when one pins it | changelogs, per-feature narrative, CLAUDE.md beyond a one-line pointer |
| Structure: component boundaries, interactions, data flow, where schemas and API surfaces live, and the path of any archived design doc | the SDD map | duplicated elsewhere |
| History: what changed, when, why, ticket ids, superseded claims, deferred work | the commit message and the bees ticket (already written, never re-reviewed) | SDD, README, CLAUDE.md |
| Behavior: what operators and users see — install, commands, configuration surface, user-visible defaults, release notes | README or the configured customer docs | duplicated tables elsewhere |
| Requirements (pre-implementation): product scope, non-goals, acceptance criteria | Spec Bee `t1=Doc` children and Issue bodies; whatever the `Project requirements doc (PRD)` key names is background, never authority, never a write target | per-Issue entries |

Engineering, test, and doc conventions belong to the four guides named in `## Documentation Locations` and never enter the register. A CLAUDE.md may state a rule in one line as a pointer to its register entry; the rationale lives only in the register; those pointer lines are hand-maintained by the operator and are never a Doc Writer target. A Spec Bee SDD child and an Analyst proposal section are ratified **sources**, not owners, so "no fact in two owners" is never read against them. The table governs over any Subtask body: an instruction that would place a fact outside its owner (a body asking for a `### Feature:` entry, say) is not followed, and the register and map work it implies is done instead. The table lives in exactly one shipped place, `agents/doc-writer.md` `## Fact ownership`; the review skill, the setup skill's generated guide, README, and CONTRIBUTING carry the principle in one sentence and a pointer, phrased install-independently as "the doc-writer subagent definition's `## Fact ownership` section", never a second copy of the rows.

### The SDD

The maintained SDD is two parts under a size cap. The **map** is the bootstrap skeleton's sections plus one line per archived design document — its path and "historical record, not maintained, verify against code"; pre-migration, the map is whatever architecture sections the SDD carries. The **register** is a single `## Register` section with one `### <subsystem>` subsection per owning subsystem, where subsystem names are the map's `## Key components` bullet names (pre-migration, the SDD's top-level architecture section titles) and a rule spanning components goes under `### Cross-cutting`; the Doc Writer creates `## Register` at the end of the document when absent and creates a subsystem subsection when absent. Entry shape: `- **<rule>** Why: <one to three sentences>. Code: <path>. Test: <test>` (Test omitted when nothing pins it). The cap is 500 lines unless the project's doc-writing guide carries a line of the form `SDD size cap: <N> lines`. The admission test for a line: would an agent that skipped it make a worse design decision or reintroduce a fixed bug?

### Relays

Register entries are transcribed from ratified sources the orchestrator relays verbatim, not inferred from the diff. Every relay is an existing or new row in the §5 dispatch table; nothing a writer returns is relayed to anyone.

- **`## Ratified decisions`** — recipients Doc Writer, Doc Reviewer, PM (the PM because it invokes the per-Task doc review through the Skill tool in execute mode). Fix mode: the approved directive's `### Policy decisions this change implies` plus the light-revision clarification the Engineer's directive block already carries, verbatim. The clarification is free text and may touch `### Recommended approach`; that leak is accepted explicitly, because carving out its policy-answer part would be an orchestrator judgment over prose. The Analyst's section is unconditional with its own none-line, so the row's fixed line is unreachable in fix mode; the fix body's cell reads "unreachable — the Analyst's section is unconditional" and no fix-mode branch is built. Execute mode: the `## Decisions and rejected alternatives` section — from that heading to the next `## ` heading or end of file — of the spec source's SDD, resolved by the walk `agents/pm.md` already documents: Grandparent Bee `reference_materials` → `bees` resolver → Spec Bee child titled `SDD`; `file-path` resolver → the entry `/quo-plan-from-specs` recorded from its `<sdd-path>` argument, which item 6 pins as the second entry of a two-entry `[<prd-path>, <sdd-path>]` array (the PRD also carries that heading, so position, not content, selects); null → the Plan Bee body's section under that literal heading. Whatever sits under the heading travels verbatim, its own explicit-none placeholder included. Fixed line, used when there is no resolvable SDD source (no child titled `SDD`, no second `file-path` entry, no such heading in the body) or the source has no such heading: `None — the source carries no decisions section.` The fixed line never substitutes for a lost proposal: after a compaction the proposal is re-derived before the dispatch that needs it, the same clause the `## Blast radius` row carries. Relaying to every Doc Writer dispatch is uniform by design: `/quo-breakdown-epic` creates one doc Subtask per code-changing Task without an internal-versus-customer distinction, so routing by Subtask kind would be an orchestrator judgment over ticket bodies.
- **`## Blast radius`** (fix mode only) gains the Doc Writer and the Doc Reviewer as recipients of the existing verbatim relay, alongside Engineer, PM, Code Reviewer. Its contract stays "invariants the change adds, removes, or weakens". Execute mode has no such row, so the removed-invariant hole this closes in fix mode stays open in execute mode by construction; b.eid (plan-path up-front enumeration) is where that closes.
- **`## Source paths to fingerprint`** gains the Doc Writer as a recipient, so duty 1's Engineer-diff half has a changed-file set without Bash. When that heading is omitted (no Engineer source change), that half has no input and only the customer-doc Subtask and, in fix mode, the Blast radius doc sites apply.
- The Analyst promotes a load-bearing rule or verified external fact it finds in the code or in an archived doc **only** through `### Policy decisions this change implies`, framed as "should this rule enter the register?" with a recommended answer — never through `### Blast radius`. The archive directory the map names is excluded from the blast-radius sweep's internal-docs group as a path rule. The Analyst opens an archived doc when the register lacks a rule the Issue implicates; it does not read the archive on every dispatch.

### Doc Writer duties

Three duties per dispatch:

1. **Customer-facing docs, and every SDD sentence the Engineer's diff makes false.** Correct the false sentence in its owner, or delete it when it is mechanism or history. In fix mode, each customer-docs and internal-docs site on the `## Blast radius` list is handled the same way. The Issue body's `## Doc divergence noted` items are inputs to this duty only: a named false sentence is corrected or deleted against the diff, which needs no ratification; an item that points at a PRD is left alone.
2. **Register transcription.** An entry for each relayed decision the diff implements, and for each `## Blast radius` added invariant that passes the admission test; delete the entry of a removed invariant; amend the entry of a weakened one. **Implements** means the rule the decision states is true of the code at this diff; a relayed decision the diff does not implement gets no entry. A divergence item enters the register only if the Analyst carried it through `### Policy decisions this change implies`. The Doc Writer MAY add an entry the diff plainly establishes on its own when it passes the admission test — the entry is the rule with a pointer to the pinning test or the code comment that records the external fact, never a copy of either; no return marker, the reviewer derives such entries.
3. **Map update** when the diff moved a component boundary, interaction, data flow, external dependency, or schema or API surface.

The Doc Writer's return carries nothing the orchestrator or a reviewer would have to route or read: no disposition list, no not-yet-landed list, no over-cap report, no no-owner report. Reviewers derive everything from the diffs and the relayed lists.

### Doc Reviewer checks

Scope: every claim in the README or SDD about code the Engineer's diff changed, plus every region the Doc Writer's diff edited, plus the relayed lists. Pre-existing misplaced facts, pre-existing duplicates, and a pre-existing over-cap SDD outside that scope are not findings (each repo's migration is tracked separately, item 10). The Doc Reviewer reads source and tests to verify register claims and to detect a contradicting diff; it does not review source quality, which is the Code Reviewer's lane. Five checks:

1. Claims in scope are true against the diff; in fix mode, each customer-docs and internal-docs site on the relayed `## Blast radius` list is correctly handled in the docs diff — fixed, deleted as mechanism, or not a hit — derived from the diff exactly as unrelayed register entries are.
2. Each relayed decision the diff implements, and each added invariant, has a normative register entry with a code pointer, a test pointer when one pins it, and no ticket id — or the reviewer states why the item fails the admission test when it lacks one; a removed invariant has no surviving entry and a weakened one is amended; a relayed decision the diff **contradicts** is a `blocker` with two fix paths: change source (routed through part (g) in fix mode and the PM's in-flight review in execute mode), or, in execute mode only, revise the Spec SDD child — orchestrator-executed through the existing Encode mechanics (`bees update-ticket --body-file`) or `/quo-write-sdd <spec-bee-id>` inline via the Skill tool, and routed to gate (c) row 3 because it moves the spec beyond the unit's ticket. **Contradicts** means the diff makes the rule false where the pre-diff code honored it, or the Subtask body or directive calls for the rule and the diff violates it; otherwise the decision is pending and not a finding. Any register entry the diff touched that is not on the relayed lists is checked against the code and its test. When the caller supplied no `## Ratified decisions` heading (standalone or pre-relay invocation), the transcription half is skipped and the return says so.
3. The map reflects every component, boundary, data-flow, external-dependency, and schema or API-surface change the diff made — today's architecture check restated against the map.
4. The diff did not take the SDD over its cap. Severity `suggestion`; fix paths (a) compact the subsystem subsections the diff touched by the admission test, (b) if still over, file a follow-up Issue naming the repo's migration.
5. No fact the diff wrote appears in two owners.

Severity follows ownership: a false claim is a `blocker`; a fact in the wrong owner or in two owners is a `suggestion` with a move-and-pointer fix path; wording inside the right owner is a `nit` unless false.

## Impact

Wall-clock and token cost on every `/quo-fix-issue` and `/quo-execute` run in every downstream repo: five to eight doc-review rounds per Issue were reported, most spent on descriptive prose and multi-carrier drift. ## Background and rationale

Three truths, and code owns only one. Code is the truth for what the system does; tests are the truth for what it must keep doing; specs are the truth for what it should do for users. A doc sentence describing what the code does is a second copy and drifts. A doc sentence stating what the code must do is normative: when it disagrees with the code, the code is wrong. That is the line between the register and everything that leaves.

The churn decomposes into four kinds: drift corrections on descriptive claims (eliminated when mechanism leaves the docs), multi-carrier edits (eliminated by single ownership), wording rounds (shrunk by a convergent reviewer criterion), and genuine README defects (kept; they are product defects). Round caps, delta-only rounds, and skipped lanes were rejected as speed levers on 2026-09-04 and are not proposed here; this change shrinks what there is to review, and narrows the reviewer's read to the two diffs (a recorded deviation, below), without changing how hard anything in scope is reviewed.

The live_edit CLAUDE.md invariant section (one-line rules with SDD section pointers) is already register-shaped and was grown by hand because agents needed it; the SDD behind it is the encyclopedia nobody can read whole. Both downstream repos already carry an IMPLEMENTATION_CHANGELOG (155k and 18k words); moving history there would relocate the churn, since the Doc Reviewer reviews it too, so history's owner is the commit and the ticket.

## Decisions and rejected alternatives

- **Retire the per-feature fold-in entirely** rather than narrow the Doc Writer's question. Rejected because live_edit proves the fold-in is not the only growth surface; the topical sections grew the same way. The ownership table addresses both shapes.
- **Archive the PRD, do not freeze it in place, and key nothing on a header.** A frozen doc still on the agents' read list is read as authority. The signal that a document is background is that the PRD key names it.
- **Keep bootstrapping a starting-point PRD; make the empty key a steady state.** The bootstrap's four user questions (purpose, why, non-goals, an acceptance criterion) capture background nothing else in the workflow asks for; the Analyst reads what the key names as background and the human reader gets a one-page statement of purpose. `/quo-plan` does not read it. Stopping the bootstrap was rejected on the first ground; present-but-empty means skipped so the walkthrough stops re-asking.
- **History's owner is the commit and the ticket, with no changelog clause.** "A changelog when CLAUDE.md names one" was a lookup against no contract key and contradicted the Background; a user-facing CHANGELOG is release notes, which is Behavior, not History.
- **Transcribe register entries from ratified sources; allow one bounded, reviewer-checked exception.** Transcription removes the judgment call that inflated the old SDDs. The unrelayed entry for a rule the diff plainly establishes is kept deliberately and derived by the reviewer rather than marked by the writer.
- **Duty 1 covers every SDD sentence the Engineer's diff makes false, and the Doc Reviewer's scope is the Engineer's diff plus the Doc Writer's.** Scoping to the doc diff alone would let a changed CLI flag with no README edit pass with zero findings and would leave a false sentence in an unmigrated SDD nobody's duty until migration.
