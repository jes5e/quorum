# quorum — Software Design

## Tech stack

- **Skill prose**: Markdown (`SKILL.md`) with YAML frontmatter (`name`, `description`). The body is the instructions Claude follows when the skill is invoked.
- **Helper scripts**: Python 3 (cross-platform) — `quo-setup/scripts/detect_fast_path.py` (new-machine fast-path detection), `quo-breakdown-epic/scripts/scoped_marker_resolver.py` (Scoped-marker parser/scoper, sibling-resolved by `quo-execute` and `quo-fix-issue`), `quo-execute/scripts/hive_commit.py` (hive-path resolution and deferral-encode staging/commit), and `quo-setup/scripts/context_gauge.py` (context-usage gauge producer/reader, plus status-line settings inspection/installation and the opt-out-marker writer).
- **External CLI**: [bees](https://github.com/gabemahoney/bees) (`bees-md` on pipx, Python 3.10+) for ticket management.
- **Runtime host**: [Claude Code](https://claude.com/claude-code) — skills are invoked via `/<skill>` slash commands. The execution skills (`quo-execute`, `quo-fix-issue`, `quo-breakdown-epic`) orchestrate parallel work by dispatching ephemeral background subagents via the stable `Agent` tool (`run_in_background=true`). Role contracts ship as eight custom-subagent definition files at `agents/<role>.md` in the repo root (`engineer.md`, `test-writer.md`, `doc-writer.md`, `pm.md`, `code-reviewer.md`, `doc-reviewer.md`, `test-reviewer.md`, `analyst.md`), installed alongside skills at `~/.claude/agents/` (global) or `<repo>/.claude/agents/` (per-project). The first seven are dispatched by both `/quo-execute` and `/quo-fix-issue`; `analyst` is dispatched only by `/quo-fix-issue`, at two sites: the design-analysis gate between Validate Issue and per-issue Agent dispatch, and a mid-implementation re-dispatch when an Engineer stops and returns a `## Design question` the approved proposal did not enumerate, which **on the forward fix path, before the Issue is closed out**, re-enters that same gate's Revise branch — a post-completion design question is filed as a follow-up Issue instead, with no Analyst re-dispatch (execute mode handles design analysis upstream via `/quo-plan` and does not pick up the Analyst). No experimental feature flags or display-backend configuration are required.

## Architecture overview

The repo ships 14 portable-core skills under `skills/<name>/`, each self-contained as a `SKILL.md` plus optional `scripts/`. Skills are loaded by Claude Code from either `~/.claude/skills/` (global install) or `<repo>/.claude/skills/` (per-project install). When a skill needs a bundled helper script (its own or a sibling's), it resolves the absolute path at runtime from the skill's own base directory — which Claude Code provides in the skill invocation header. No per-machine paths are persisted to CLAUDE.md or any other tracked file.

The workflow chain is linear with two entry points:

- `/quo-setup` — one-time per repo (idempotent re-runs)
- `/quo-plan` *or* `/quo-plan-from-specs` — produces a Plan Bee with Epic children
- `/quo-breakdown-epic` — decomposes one Epic into Tasks/Subtasks, commits the new ticket files at end-of-skill
- `/quo-execute` — walks every Epic, dispatches subagents per Task, commits
- `/quo-file-issue` *and* `/quo-fix-issue` — anytime, for bugs/follow-ups

Four review skills exist. Three of them (`quo-engineer-review`, `quo-doc-writer-review`, `quo-test-writer-review`) are orchestrator-only — invoked by `/quo-execute` and `/quo-fix-issue` during their review cycles, with no standalone-invocation path. The fourth, `quo-spec-review`, is dual-mode — primarily invoked by orchestrating skills (`/quo-write-prd`, `/quo-write-sdd`, and `/quo-plan`) during their review cycles, with standalone invocation also supported for ad-hoc reviews outside the workflow.

The workflow uses three hives in the target repo: **Plans** (top-level, with t1/t2/t3 = Epic/Task/Subtask, statuses `drafted`/`ready`/`in_progress`/`done`), **Issues** (no children, statuses `open`/`done`), and **Specs** (top-level Spec Bees with `t1=Doc/Docs` children, statuses `drafted`/`ready`). The Specs hive is colonized by `/quo-setup`; the `t1=Doc` children (PRD and SDD) are authored by `/quo-write-prd` and `/quo-write-sdd`, typically invoked inline from `/quo-plan` during planning. `/quo-setup` does not author Spec content itself. Plan Bees and Issues may carry one or more spec sources in their `reference_materials` field, resolved per-item by one of several resolvers the bees CLI supports: the **`file-path` resolver** (the default) treats each entry as a path to an on-disk source document (PRD, SDD, etc.) — used by `/quo-plan-from-specs`; the **`bees` resolver** treats each entry as a ticket ID — used by `/quo-plan` to point at a Spec Bee whose body and `t1=Doc` children (PRD + SDD, differentiated by exact title-match) hold the authoritative spec content; the **external-URL resolvers** (`github-issue`, `linear-issue`, `url`, etc.) treat each entry's `value` as a URL pointing at an external bug report (GitHub Issue, Linear ticket, internal bug tracker page, Slack archive link, etc.) — used by `/quo-file-issue --reference` (and its `--from-github` alias) on Issues, and consumed by `/quo-fix-issue`'s Engineer and PM via `WebFetch` since the bees CLI does not yet ship concrete resolver implementations for these names. When a Plan Bee or Issue has null/empty `reference_materials`, the **ticket body itself becomes the authoritative spec** — downstream skills explicitly substitute the body for the PRD/SDD in that mode. The full resolver-contract phrasing lives in `docs/doc-writing-guide.md` `## Project terminology`.

## Key components

- **`skills/quo-setup/`** — one-time configuration: colonizes three hives (**Plans** — top-level, t1/t2/t3 = Epic/Task/Subtask, statuses `drafted`/`ready`/`in_progress`/`done`; **Issues** — no children, statuses `open`/`done`; **Specs** — top-level Spec Bees with `t1=Doc/Docs` children, statuses `drafted`/`ready`, colonized by `/quo-setup` for use by future skills, no content is authored here at setup time), writes the two required CLAUDE.md sections (`Documentation Locations`, `Build Commands`), optional PRD/SDD bootstrap from existing codebase. Detects the new-machine case (on-disk hive markers present, the repo's scope not registered in `~/.bees/config.json`, CLAUDE.md already populated) via the bundled `detect_fast_path.py` helper and offers a fast path that re-registers hives from canonical defaults without touching CLAUDE.md. Also offers an **optional, `AskUserQuestion`-gated** step to wire the context-usage gauge producer into the operator's status line: it writes/updates the user-level settings `statusLine` to invoke the bundled `context_gauge.py` `produce` subcommand (wrapping — never replacing — any existing status-line command), or, if the operator declines, writes a persistent opt-out marker instead. This is the first user-settings-file write `/quo-setup` performs, and it touches no CLAUDE.md file. The step is offered on **both** the fast path and the slow path (a freshly-cloned machine is exactly where the per-machine status-line setting is unconfigured), and detection suppresses the gate entirely when a producer is already configured and current or when the opt-out marker is present. A direct-invocation entry point (the `--configure-gauge-producer` argument, or a caller request scoped solely to producer configuration) runs this step alone and stops, needing neither the bees CLI nor a configured repo.
- **`skills/quo-plan/`** — interactive scope discovery for an idea or feature without finalized specs. Produces a Plan Bee with Epic children.
- **`skills/quo-plan-from-specs/`** — express path for a finalized PRD+SDD on disk. Same Plan Bee output as `/quo-plan`. Default (single-feature) mode hard-fails on PRDs/SDDs that contain more than one `### Feature: <title>` subsection (the cumulative-PRD pattern produced by repeated `/quo-plan` invocations) and routes the user back to `/quo-plan` to avoid re-planning previously-planned features. The optional `--feature "<title>"` flag bypasses the multi-feature guard and scopes the planning run to a single `### Feature: <title>` subsection extracted from each of the PRD and SDD (heading must exist in both docs); `reference_materials` still points at the canonical full PRD/SDD paths, and the Plan Bee body carries a `Scoped to ...` marker so downstream skills can tell the Bee covers a sub-region of a cumulative spec. **Marker producer.**
- **`skills/quo-write-prd/`** — authors or revises a `t1=Doc` child titled `PRD` under a Spec Bee in the Specs hive. Composable as a solo skill for revisions (`/quo-write-prd <spec-bee-id>`) or via inline Skill-tool delegation from `/quo-plan` when initial specs are being authored.
- **`skills/quo-write-sdd/`** — authors or revises a `t1=Doc` child titled `SDD` under a Spec Bee in the Specs hive. Composable as a solo skill for revisions (`/quo-write-sdd <spec-bee-id>`) or via inline Skill-tool delegation from `/quo-plan` when initial specs are being authored.
- **`skills/quo-breakdown-epic/`** — decompose one Epic into Tasks and Subtasks. The only skill where dispatched subagents run in `mode: "plan"` (read-only researchers). At end-of-skill, stages and commits the new ticket files (Tasks, Subtasks, Epic status update) when the Plans hive lives inside the current git repo — resolved via `bees list-hives` in the same pattern `quo-file-issue` uses; when the hive lives outside the repo, the commit step is skipped and the next-steps menu carries a one-line note. The end-of-skill next-steps menu carries per-option "best when …" rationales and moves the Recommended badge across three cases keyed on (a) whether any drafted sibling Epics remain under the parent Bee and (b) whether breaking down the next Epic right now risks rework: when no drafted siblings remain, the Recommended option is "execute the whole Bee"; when drafted siblings remain and the orchestrator judges that the just-broken-down Epic's implementation will reshape contracts consumed by them (foundation-then-rewrites pattern), the Recommended option is "execute this Epic first; defer downstream breakdown"; when drafted siblings remain with pure-ordering dependencies only (no reshape risk), the Recommended option is "break down the next Epic". The case-specific rationale is surfaced only as the Recommended option's `Best when …` subtitle — a freestanding rationale paragraph above the menu is forbidden because the Claude Code UI has been observed truncating long header prose mid-sentence. **Marker consumer** — Step 1 (read parent Bee) detects the `Scoped to ...` marker and restricts the resolved doc content to the matching `### Feature: <title>` subsection before Task decomposition and Spec Traceability Review. Bundles the shared parser/scoper helper at `scripts/scoped_marker_resolver.py` (sibling-resolved by `quo-execute` and `quo-fix-issue`).
- **`skills/quo-execute/`** — execute a Plan Bee end-to-end. Walks Epics in dependency order, dispatches ephemeral background subagents per Task, commits per Task, reviews at Bee close. **Marker consumer** — Step 4 PM section detects the `Scoped to ...` marker on the Grandparent Bee and compares per-Task work against the scoped subsection only (sibling-resolves `quo-breakdown-epic`'s `scoped_marker_resolver.py`).
- **`skills/quo-fix-issue/`** — fix one or more issue tickets. Single, list, or `all` modes. Same orchestration shape as `quo-execute` but at issue scope. **Marker consumer (via up_dependencies-link)** — Issues live in the `issues` hive and have no canonical parent-Plan-Bee field in the bees ticket schema, so the PM discovers a scope-context Plan Bee opportunistically by iterating the Issue's `up_dependencies` array (a deliberate dual-use of that field — blocker AND optional scope-context source) and applying the marker from any entry that resolves to a Plan Bee. Best-effort: a missing marker, a non-`plans`-hive `up_dependencies` entry, or a parser hard-fail falls back to full-doc spec content; if multiple Plan Bees in `up_dependencies` carry markers, the first in `up_dependencies` iteration order wins. **External-reference consumer** — when an Issue carries `reference_materials` produced by `/quo-file-issue --reference` (resolver name `github-issue`, `linear-issue`, or `url`), the orchestrator embeds the `reference_materials` JSON value alongside the (thin) Issue body in each Agent dispatch prompt; the Engineer and PM fetch the upstream content via `WebFetch` and treat it as the spec source, since concrete resolver implementations for these names do not exist in the bees CLI yet.
- **`skills/quo-file-issue/`** — file a new issue ticket (bug, follow-up, small feature, tech debt). Two invocation modes: (a) **in-conversation capture** — body-as-spec, populated from a free-text description or distilled from a prior conversation, with optional `## Background and rationale`, `## Decisions and rejected alternatives`, and `## Doc divergence noted` sections; (b) **external-reference mode** — invoked as `/quo-file-issue --reference <url>` or `/quo-file-issue --from-github <url>`, produces a thin 2-3 sentence body and writes `reference_materials` as `[{"value":"<url>","resolver":"<name>"}]` where `<name>` is selected by URL pattern (`github-issue` for GitHub Issue URLs, `linear-issue` for Linear ticket URLs, `url` otherwise). The bees CLI does not yet have concrete resolver implementations for these names — `/quo-fix-issue`'s Engineer and PM fall back to fetching the upstream content via `WebFetch` until a real resolver lands. Symmetric with `/quo-plan-from-specs` on the planning side.
- **`skills/quo-status/`** — show workflow stages and current progress across all hives.
- **`skills/quo-engineer-review/`**, **`skills/quo-doc-writer-review/`**, **`skills/quo-test-writer-review/`** — orchestrator-only reviewers invoked by `/quo-execute` and `/quo-fix-issue` during their review cycles, with bees-specific loop-bounding prose for that path.
- **`skills/quo-spec-review/`** — dual-mode reviewer for Spec Bee content (PRD and SDD `t1=Doc` children). Primary use: gates a Spec Bee's (or PRD/SDD child's) `drafted → ready` transition; invoked automatically by `/quo-plan` (after both writer skills complete, before the Spec Bee parent's promotion, no `--doc` flag), `/quo-write-prd` (after solo Step 6's user-approval gate, before the PRD child's promotion, with `--doc PRD`), and `/quo-write-sdd` (after solo Step 7's user-approval gate, before the SDD child's promotion, with `--doc SDD`); the per-writer review is skipped when the writer is invoked inline from `/quo-plan` since Site 1 covers both children end-to-end. Secondary use: standalone ad-hoc spec review (`/quo-spec-review <spec-bee-id> [--doc PRD|SDD]`). Returns a list of improvement work items in the same severity-tagged shape as the other three reviewers; does not mutate any ticket. Conceptual analog of upstream apiary's `/req-review`.
- **`agents/`** — top-level directory of eight custom-subagent definition files, one per role, installed alongside skills at `~/.claude/agents/` (global) or `<repo>/.claude/agents/` (per-project). Each file carries YAML frontmatter (`name`, `description`, `model`, `effort`, `tools` allowlist) plus a markdown body capturing role-specific Instructions (what to read, what to do, what to return). The execution skills reference these by `subagent_type: "<role>"` rather than carrying inline role prose, which substantially reduces SKILL.md size and makes role customization a first-class operation.

  The per-role model and effort pins are deliberately *not* repeated here — CLAUDE.md `## Model assignment in execution skills` owns them (see `## Model assignment in execution skills` below).

  | File | Purpose |
  |---|---|
  | `agents/engineer.md` | Implements code changes for a Subtask or set of Subtasks |
  | `agents/test-writer.md` | Writes/updates tests for completed Engineer work |
  | `agents/doc-writer.md` | Authors or updates documentation |
  | `agents/pm.md` | Per-Task PM review (spec drift, scope creep, in-flight code/doc review invocations) |
  | `agents/code-reviewer.md` | Wraps `/quo-engineer-review` skill invocation |
  | `agents/doc-reviewer.md` | Wraps `/quo-doc-writer-review` skill invocation |
  | `agents/test-reviewer.md` | Wraps `/quo-test-writer-review` skill invocation |
  | `agents/analyst.md` | Pre-implementation, codebase-grounded design analysis on an Issue dispatched by `/quo-fix-issue`. Tools allowlist is `Read`, `Grep`, `Glob`, `Bash`, `WebFetch` (no `Edit` / `Write` / `Skill` — the Analyst returns a structured Design Proposal to the orchestrator and exits). Dispatched only by `/quo-fix-issue` (not `/quo-execute`), at two sites: the design-analysis gate between Validate Issue and per-issue Agent dispatch, and a mid-implementation re-dispatch when an Engineer returns a `## Design question`, which **on the forward fix path, before the Issue is closed out**, re-enters that gate's Revise branch — a post-completion design question is filed as a follow-up Issue instead, with no Analyst re-dispatch. |

- **`skills/quo-setup/scripts/detect_fast_path.py`** — detect the new-machine fast-path scenario. Emits a JSON status payload (hive markers found, scope-already-registered check, CLAUDE.md sections populated, `fast_path_eligible` boolean) consumed by `/quo-setup`.
- **`skills/quo-breakdown-epic/scripts/scoped_marker_resolver.py`** — shared parser/scoper for the `Scoped to ...` marker emitted by `/quo-plan-from-specs --feature`. Takes one positional argument (path to a file containing the parent Bee body); prints `{"scoped": false}` when no marker is present, prints `{"scoped": true, "title": "...", "docs": [{"path": "...", "content": "..."}, ...]}` when the marker is present and well-formed, and exits 2 with a single human-readable line on stderr otherwise. Resolved as a sibling script by `quo-execute` and `quo-fix-issue`. Grammar and hard-fail rules documented in `docs/doc-writing-guide.md` `## The Scoped-marker contract`.
- **`skills/quo-execute/scripts/hive_commit.py`** — stage/commit helper for the deferral-hygiene Encode branch, plus non-mutating hive-path resolution. Two argparse subcommands: `resolve-hive-paths --hive <name> [...]` prints each named, in-repo hive's absolute path one per line (emits nothing for out-of-repo hives; no mutation), and `encode-commit --skill <slug> --count <N> [--doc-path <abs-path> ...]` resolves the Plans/Specs/Issues hive paths via `bees list-hives`, stages only the in-repo hive paths and explicit `--doc-path` arguments (never `-A`), and commits only when something is staged — printing `skipped: nothing staged` otherwise. Commit-subject contract: `Encode deferral: /<skill> — <N> ticket(s) updated`. Owned by `quo-execute`; consumed as a sibling script by `quo-fix-issue`, `quo-breakdown-epic`, and `quo-file-issue` (the last uses only `resolve-hive-paths`). Failure convention: `fail()` → one stderr line, exit 2.
- **`skills/quo-setup/scripts/context_gauge.py`** — publish and read a per-session context-window usage gauge, bridging the status-line process (the only place Claude Code delivers its context-window payload) to any skill that needs to know how much headroom is left, plus inspect and install the operator's status-line settings and write the guard opt-out marker. Five argparse subcommands: `produce [--wrap-command <cmd>]` drains the status-line JSON payload from stdin once, publishes `{"session_id": ..., "context_window": {...}}` to the gauge file, and prints a display string (the wrapped operator command's stdout when `--wrap-command` is given, otherwise a minimal default); `read --session-id <id>` prints exactly one of four values — an integer percentage (a genuine measured reading), `no-reading` (fresh file, percentage null or absent), `stale` (file older than the freshness window, so the producer appears stopped), or `missing` (no gauge file and an absent or traversable gauge directory, so no producer is configured); `inspect-statusline [--repo-root <path>]` reports the current user-level status-line configuration (settings path, effective command, `producer_state`, whether the producer is current, opt-out-marker presence, higher-precedence settings sources) as one compact JSON object, read-only; `install-statusline [--repo-root <path>] [--python <path>] [--no-self-check]` writes or updates the user-level settings `statusLine` to run this helper's `produce` on every refresh, wrapping (never discarding) any existing command and never double-wrapping, reporting the action (`installed`, `wrapped`, `repointed`, `already-configured`) as one JSON summary with an advisory post-write self-check; `write-opt-out` writes the persistent opt-out marker (idempotent, no removal subcommand by design) and prints its path. Gauge-file path: `<tempdir>/.quorum/context-usage-<session_id>.json`; opt-out marker path: `<tempdir>/.quorum/context-guard-opt-out`, both with `<tempdir>` resolved via `tempfile.gettempdir()` so they work on POSIX and Windows without per-OS branching. Exit-code split: `produce` exits `0` on every input shape and on a failed gauge write (an unwritable, read-only, or full gauge directory — one stderr line, display still emitted, so the status line is never blanked); `read` exits `0` for all four reading values — `missing`, `stale`, and `no-reading` are ordinary states a consumer must be able to distinguish from a crash — and `2` only on genuine malformation (unreadable or non-conforming gauge file, a gauge directory that cannot be traversed or is not a directory, or an argparse usage error); `inspect-statusline` and `install-statusline` exit `0` on every reportable configuration and `2` (single stderr line, never-clobber) only when the settings file exists but does not parse as a JSON object; `write-opt-out` exits `0`. Contract documented in `docs/doc-writing-guide.md` `## The context-gauge file contract`.

## Contract keys

The target repo's CLAUDE.md carries two sections that act as a string contract between skills. `quo-setup` writes them; every other skill reads them.

- `## Documentation Locations` — `Project requirements doc (PRD)`, `Internal architecture docs (SDD)`, `Customer-facing docs`, `Engineering best practices`, `Test writing guide`, `Test review guide`, `Doc writing guide`
- `## Build Commands` — `Compile/type-check`, `Format`, `Lint`, `Narrow test`, `Full test`

`quo-execute`, `quo-fix-issue`, and `quo-breakdown-epic` hard-fail with `Run /quo-setup first.` (with a trailing `— <reason>` clause naming the specific gap, e.g., `Run /quo-setup first. — Specs hive is not colonized for this repo.`) if either of the two required CLAUDE.md sections, any required key inside them, or any of the three required hives (Plans, Issues, Specs) is missing.

Bundled helper script paths (e.g., `scoped_marker_resolver.py`) are *not* part of the CLAUDE.md contract — each skill resolves its own bundled scripts at runtime from its own base directory, which Claude Code provides in the skill invocation header. This keeps per-machine paths out of tracked files.

## Orchestration in execution skills

`quo-execute`, `quo-fix-issue`, and `quo-breakdown-epic` orchestrate work by dispatching ephemeral background subagents via the stable `Agent` tool (`run_in_background=true`). The main Claude Code session running the skill is the orchestrator — mechanically a reconciliation-loop driver, not a chat hub.

- **Reconciliation loop (read state / reconcile / yield).** Each tick is purely event-driven — the harness wakes the orchestrator on Agent completion notifications, user input, and tool results. There is no clock primitive: no `/loop`, no `ScheduleWakeup`, no `CronCreate`, no polling loop. A tick reads ticket state (`bees execute-freeform-query`, `bees show-ticket`), reads the in-flight lane state (the run-state manifest's `## Lanes` in `/quo-execute` and `/quo-fix-issue`; the TaskList in `/quo-breakdown-epic`), reconciles the gap (dispatch a fresh Agent for any Subtask whose preconditions are met but no Agent is on it; persist results for any Subtask whose Agent has just returned; trigger PM review for completed Tasks; run inter-Epic checkpoints; dispatch the post-Bee fresh-eyes reviewers when all Epics are done), then yields. This is a Kubernetes-controller shape applied to skill orchestration: declarative state goal (bees ticket statuses), continuous reconciliation against actual state, no hand-managed message queues.
- **Hub-and-spoke as a structural property of the substrate.** Workers do not communicate with each other. All routing is orchestrator → Agent. The artifact-based handoff (Engineer's commits become Test Writer's input; Test Writer's tests become PM's review material) replaces the message-based handoff. This is structurally identical to the prior hub-and-spoke prescription, but achieved through a substrate that doesn't permit peer comms rather than through a "do not message peers" rule the model can drop.
- **Flat orchestration.** Per the [Claude Code sub-agents docs](https://docs.claude.com/en/docs/claude-code/sub-agents), subagents cannot dispatch other subagents — only the top-level orchestrator may dispatch Agents, so its working context grows **monotonically within a session** and **nothing in these skills reclaims those tokens**; reclamation is owned by the harness (which compacts once the window fills) and by the user's choice to start a fresh session (see `CONTRIBUTING.md` `## Known limitations`). What the skills guarantee instead is that the growth is **survivable**: a state-externalization checkpoint at every unit boundary verifies that each load-bearing fact already lives in a durable carrier — bees ticket statuses, git commits, the session-scoped compromise tracker (execution skills only — `/quo-breakdown-epic` has none), the `defer-*` ledger (the run-state manifest's `## Obligations` in the two execution skills; the TaskList in `/quo-breakdown-epic`), and the run-state manifest — and refreshes those carriers, so a compaction is lossless whenever it fires, including mid-unit. See `### Feature: Epic-boundary context-clear discipline instructs an unexecutable action; rewrite as state-externalization + run-state manifest` below for the checkpoints, their per-skill locations, and the manifest design.
- **Cold dispatch for all roles.** Engineer, Test Writer, and Doc Writer are dispatched fresh per Subtask; PM, Code Reviewer, Doc Reviewer, and Test Reviewer are always fresh by design (fresh-eyes review). Coherence across dependent Subtasks is preserved through the diff: each later Engineer reads the prior Engineer's commit, matching the hub-and-spoke "diff is the handoff" pattern. **Concurrency is preserved across units and ordered within one.** Fan-out across units stays parallel in `/quo-execute` — Engineer-Subtask-N+1 runs in parallel with Test-Writer-Subtask-N once the orchestrator's reconciliation loop ticks past Engineer-Subtask-N's completion — because the ticket graph already orders the forward work. Lanes *within* one unit are ordered in `/quo-fix-issue`, which walks each Issue through a Phase A / B / C ladder, and the review re-dispatch path is ordered in **both** skills: a finding whose fix changes source goes Engineer → code review → affected writer rather than concurrently. See `### Feature: Sequence lanes strictly: Engineer + code review to clean before Test Writer / Doc Writer run once; ask reviewers for second-order effects` below for the ladder, the dispatch precondition, and why the execute-mode mirror is narrow.
- **State-aware dispatch.** Before dispatching any Agent, the orchestrator re-reads the target ticket's current state via `bees execute-freeform-query` and skips the dispatch when the ticket is already `done`. This prevents redundant work caused by acting on stale memory.
- **Verbatim ticket-body quoting.** Agent dispatch prompts embed the ticket body exactly as `bees show-ticket` returns it — no paraphrasing. Identifier names (function/flag/type names) are preserved literally so workers do not invent or mis-spell them downstream. Framing prose stays outside the quoted block.
- **TaskList as progress UI and routing input — `/quo-breakdown-epic` only, since the orchestrator rewrite.** `/quo-breakdown-epic` creates one TaskList task per concurrent Agent invocation (e.g., `engineer-qf-subtask-1`, `test-writer-qf-subtask-1`, `pm-qf-subtask-1-review`). Status transitions (`pending → in_progress → completed`) are updated as Agents start and finish; `metadata.activity` carries finer-grained progress (e.g., `"running /quo-engineer-review (~5 min)"`). Claude Code's native TaskList UI renders these live, providing visual parallelism without an Agent Teams display backend. TaskList is also a **routing input**, not only a display: obligation markers that stand for no Agent at all (`defer-*`, `gate-*`, and the `aborted-*` redelivery markers described in the per-feature entry below) live in the same list, and the ordering rules that gate dispatch are evaluated by matching task-name **prefixes** plus statuses — which is what lets those rules be re-derived after a compaction rather than remembered. `/quo-execute` and `/quo-fix-issue` carry the same state in the run-state manifest instead — lanes in `## Lanes`, `defer-*` and `aborted-*` obligations in `## Obligations`, batched-nit counts in `## Rounds`, the pending gate in `## Open gate` — read no TaskList state, and evaluate their dispatch-ordering rules against lane rows by role, scope, and status.
- **Time-bounded review iteration.** In `quo-execute`, the PM short-circuits `/quo-engineer-review` and `/quo-doc-writer-review` when a single invocation returns more than ~10 items or runs more than ~5 turns: triage to blocker-severity items only and defer the rest to the Task summary.

## Model assignment in execution skills

## Per-feature design

### Feature: Side-effect-free /quo-plan and /quo-file-issue with preserved context

**Architecture.** The redesign is structured around four architectural moves: a new **Specs hive**, a polymorphic `reference_materials` field with a `bees` resolver, two new composable spec-authoring skills, and an expansion of the `doc-writer` agent's responsibility to own post-implementation cumulative-doc updates. Together these decouple per-feature spec authoring from cumulative project-doc mutation: per-feature PRD/SDD content lives in queryable bees tickets and is folded into the cumulative on-disk docs only after implementation lands.

**Specs hive.** A third top-level hive joins Plans and Issues. Spec Bees are top-level Bees in the Specs hive with `t1=Doc/Docs` children — PRD and SDD as separate `t1=Doc` tickets, differentiated by exact title-match (`PRD` vs `SDD`), not by tier. The hive's allowed resolver is `bees`, so a Plan Bee's `reference_materials` can point at a Spec Bee. Status vocabulary is two-state — `drafted` (being written) and `ready` (referenceable) — distinct from the four-state Plans ladder and the two-state Issues ladder; `worker`/`finished` semantics are conformance-driven for spec docs and do not add meaning, so the shorter ladder is intentional. `/quo-setup` colonizes the Specs hive at first-run and detect-and-adds it on existing repos that pre-date the hive; `/quo-execute`, `/quo-fix-issue`, and `/quo-breakdown-epic` hard-fail with `Run /quo-setup first. — Specs hive is not colonized for this repo.` when the hive is missing.

**Reference materials with `bees` resolver.** The bees CLI's `reference_materials` field accepts arbitrary resolvers per entry. Two are now in use across the workflow: the **`file-path` resolver** (the default) treats each entry as a path to an on-disk source document — used by `/quo-plan-from-specs`; the **`bees` resolver** treats each entry as a ticket ID of the shape `[{"value":"<bee-id>","resolver":"bees"}]` — used by `/quo-plan` to point at a Spec Bee whose body and `t1=Doc` children hold the authoritative spec content. When `reference_materials` is null/empty (e.g., the bootstrap-mode case), the **Plan Bee body itself becomes the authoritative spec** and downstream skills explicitly substitute the Bee body for the PRD/SDD. This three-source-mode design (path on disk / referenced Bee + children / own Bee body) preserves polymorphism for future GitHub-issue, Linear, or external-doc resolvers without skill changes.

**Two-hop lookup.** `agents/pm.md` and `skills/quo-breakdown-epic/SKILL.md` resolve `bees`-resolver entries via a two-hop pattern: hop 1 reads the entry's `value` from the parent Bee's `reference_materials`; hop 2 runs `bees show-ticket --ids <bee-id>` and treats the resolved Bee's body (or, for Spec Bees, its `t1=Doc` children enumerated by exact title-match) as the spec source. The `file-path` resolver path and the body-as-spec fallback remain functional and untouched. Canonical recipes for the two-hop pattern live in `docs/doc-writing-guide.md` `## Project terminology` under the `Reference materials` entry.

**`/quo-write-prd` and `/quo-write-sdd` skills.** Spec-authoring logic factors out of `/quo-plan` into two new composable sub-skills, each owning the quality-bar prose for its respective doc type. Default user experience is unchanged — typing `/quo-plan` still produces a Plan Bee with PRD and SDD content authored — because `/quo-plan` invokes them inline via the Skill tool. They are also solo-invokable for revisions (`/quo-write-prd <spec-bee-id>`, `/quo-write-sdd <spec-bee-id>`), which is a real use case (revising a PRD after learning something during execution). The factoring shrinks `/quo-plan` substantially and gives mental-model parity with apiary's `/write-prd` + `/write-srd`. PRD and SDD child-ticket bodies include explicit sections for decisions, rejected alternatives, and rationale — not just requirements.

**`doc-writer` agent expanded responsibility.** The `agents/doc-writer.md` contract now owns appending or updating `### Feature: <title>` subsections in the cumulative project PRD (`## Per-feature scope` header) and SDD (`## Per-feature design` header) post-implementation, reflecting what was actually built. The redundancy that previously had `/quo-plan` writing speculative SDD content AND `doc-writer` updating SDD from the actual diff is resolved: the speculative write is gone; the post-implementation write (anchored to what shipped) remains. The doc-writer's categorization heuristic (user-facing feature vs architecture-only vs deployment vs pure-refactor) governs which cumulative doc(s) get an entry on a given run; the diff is the primary signal, with the dispatched Task/Subtask body as a secondary signal. Idempotency is enforced by exact-match on the verbatim Plan Bee title — `### Feature: <title>` heading text is matched case-sensitively, and an existing subsection is replaced in place rather than duplicated.

**`/quo-file-issue` redesign.** The former filing-time doc-mutation step (now folded into the body-authoring step's optional `## Doc divergence noted` capture) no longer mutates project docs when an Issue surfaces doc divergence. Instead, divergence observations are captured in a `## Doc divergence noted` section in the Issue body for `/quo-fix-issue`'s doc-writer to act on at fix time. The Issue body template gains optional `## Background and rationale` and `## Decisions and rejected alternatives` sections so that the analytical depth of the originating discussion survives into the Issue (the Issue body is the spec source for `/quo-fix-issue` — there is no `reference_materials`, no children, no PRD/SDD pointer). The skill is mid-conversation aware: when invoked from a substantive preceding discussion, it does not re-ask discovery questions that the conversation already answered.

**Scoped-marker machinery retained.** The `Scoped to ...` marker, the `skills/quo-breakdown-epic/scripts/scoped_marker_resolver.py` parser, and the asymmetric Path A vs Path B handling in `agents/pm.md` are all retained. `/quo-plan-from-specs --feature "<title>"` remains the marker producer; `/quo-breakdown-epic`, `/quo-execute`, and `/quo-fix-issue` remain marker consumers (the `quo-fix-issue` consumer iterates the Issue's `up_dependencies` array opportunistically, since Issues have no canonical parent-Plan-Bee field). What changed is only that `/quo-plan` no longer emits markers — because it no longer co-mingles per-feature content into shared cumulative docs, there is nothing to scope inside.

**Decomposition.** The feature shipped as eight Epics under Plan Bee `b.31f`: Epic 1 (Specs hive setup in `/quo-setup`); Epic 2 (`/quo-write-prd` skill); Epic 3 (`/quo-write-sdd` skill); Epic 4 (`/quo-plan` redesign with Spec Bee + `reference_materials` + `bees` resolver, including mid-conversation context awareness in Steps 0-2); Epic 5 (PM/breakdown two-hop lookup updates); Epic 6 (`doc-writer` cumulative-doc responsibility expansion); Epic 7 (`/quo-plan-from-specs` regression check + Overview prose positioning vs `/quo-plan`); Epic 8 (`/quo-file-issue` redesign — no doc mutation, `## Doc divergence noted` capture, optional discussion-derived body sections, mid-conversation awareness). ### Feature: Add /quo-spec-review skill (apiary /req-review analog)

**Architecture.** A new dual-mode review skill that mirrors the work-item-list shape of `/quo-engineer-review`, `/quo-doc-writer-review`, and `/quo-test-writer-review` (which are themselves orchestrator-only post the b.mak rename). Lives at `skills/quo-spec-review/SKILL.md` (no bundled scripts — the skill is prose-only, dispatching through `bees execute-freeform-query` and `bees show-ticket` for ticket I/O). No new contract keys; no new agents; no changes to the seven role files in `agents/`.

**Inputs and resolution.** One positional argument `<spec-bee-id>` (the Spec Bee whose PRD and/or SDD `t1=Doc` children are under review) and one optional `--doc PRD|SDD` flag scoping to a single child. Doc resolution uses a freeform query stage `[hive=specs, parent=<spec-bee-id>, title~^(PRD|SDD)$]` (or the narrowed single-title regex when `--doc` is passed); the title regex is anchored on both ends so the match is exact and case-sensitive against the canonical `PRD` / `SDD` titles produced by `/quo-write-prd` and `/quo-write-sdd`. Each resolved child's body is fetched via `bees show-ticket --ids <doc-ticket-id>` and treated as the source of truth — no on-disk file is read as a substitute, since downstream skills (`/quo-breakdown-epic`, `/quo-execute`'s Engineer / PM, `/quo-fix-issue`) consume the bees ticket body, not any artifact on disk.

**Checklists.** The skill carries three checklist passes inline in its prose:

1. **PRD checklist** — eight categories tied to the twelve required sections imposed by `/quo-write-prd` Step 4: section completeness, problem-statement clarity, acceptance-criteria measurability, scope clarity (`## Non-Goals / Out of Scope`), implementation-detail leakage (PRD covers what/why, not how), vague-language detection, rationale-and-decisions substance, and open-questions discipline.
2. **SDD checklist** — ten categories tied to the seven required sections imposed by `/quo-write-sdd` Step 5: section completeness, codebase-grounding (real module/file/function names, `RESEARCH NEEDED:` tag surfacing), requirements structure (`SR-` prefix, domain grouping, observable-behavior framing), architecture coverage (top-level framing plus component-by-component coverage), existing-behavior preservation (greenfield placeholder vs explicit contracts), test-fixture conventions, documentation coverage (canonical CLAUDE.md `## Documentation Locations` paths), decomposition signal for downstream Epic breakdown, data-model and contract-key impact callouts, and rationale-and-decisions substance.
3. **Cross-document consistency pass** — five categories run only when both PRD and SDD are in scope: goal-to-requirement coverage (every PRD `## Goals` entry maps to at least one SDD `SR-` requirement), acceptance-criterion-to-design coverage (every PRD `## Acceptance Criteria` entry has SDD coverage), out-of-scope alignment (no SDD design element implements anything PRD `## Non-Goals / Out of Scope` excludes), open-question alignment (no SDD section confidently decides a question PRD `## Open Questions` lists as still open), and rationale alignment (PRD and SDD `## Decisions and rejected alternatives` sections agree on rejected alternatives when both have substantive content).

**Output contract.** The skill returns a numbered markdown list under a `## Spec Review Work Items` heading. Each item carries a severity tag (`blocker`, `suggestion`, `nit`) matching the ladder used by the other three reviewers, cites the document (`PRD` or `SDD`) and section heading, and gives a one-line description of the finding. When there are no important findings, the skill says so explicitly rather than padding the list with trivia. The skill does not mutate any ticket — output is text-only, returned to the caller (human or orchestrating skill).

**Dual-mode invocation.** Standalone use is `/quo-spec-review <spec-bee-id> [--doc PRD|SDD]` from the prompt — the caller is a human or another standalone tool, output the work-item list and stop. Orchestrator-invoked use (when `/quo-write-prd`, `/quo-write-sdd`, or `/quo-plan` later wires this skill in as a post-write gate on the Spec Bee's `drafted → ready` transition) applies the same loop-bounding discipline the other three reviewers carry: be selective, do not report trivial-but-not-important items each pass, say "no important findings" when applicable to avoid infinite review-fix-review loops.

**Preconditions.** Hard-fail with `Run /quo-setup first.` (plus a one-line note naming the missing piece) if the Specs hive is not colonized for the host repo (`bees list-hives` must include a hive whose `normalized_name` is `specs`). The skill does not require CLAUDE.md `## Build Commands` since it produces text findings, not build/test/lint output.

**Catalog and prose updates.** README.md skill table gets a new row parallel to the existing review-skill rows; the surrounding "three reviewers" sentence becomes "four reviewers" and lists `/quo-spec-review` alongside the existing three. The portable-core skill count (referenced in README.md's "Coming soon" preamble, this SDD's `## Architecture overview`, CLAUDE.md's tmux-dependency rule, and `docs/doc-writing-guide.md`'s contributing principles) bumps from 13 to 14. The SDD `## Architecture overview` "Three review skills" sentence becomes "Four review skills" and adds `quo-spec-review` to the parenthetical list; the SDD `## Key components` review-skill entry stays as-is and a new `quo-spec-review/` entry follows it.

**Decomposition.** Shipped as a single Issue (`b.uxa`) rather than a multi-Epic Plan Bee, on the reasoning that the skill is small (one new `SKILL.md`, no new helpers, no contract changes, no agent changes) and the analogs already exist for the Engineer to model from. The `up_dependencies: [b.31f]` on the Issue is a blocker dep, not a scope-context Plan Bee — the new skill stands on its own and is not scoped to any subsection of `b.31f`'s spec content.

### Feature: /quo-file-issue: add --reference URL mode for external sources (GitHub, Linear, etc.)

**Architecture.** The redesign threads three architectural moves through the existing `/quo-file-issue` and `/quo-fix-issue` skills plus the Engineer and PM subagents: a **mode-fork branch** in `/quo-file-issue` that routes external-reference invocations away from the body-template authoring path, a **URL-pattern resolver-name heuristic** that picks a canonical resolver name (`github-issue` / `linear-issue` / `url`) without requiring a concrete resolver implementation in the bees CLI, and a **`WebFetch`-fallback fetch path** in `/quo-fix-issue`'s Engineer and PM subagents that consumes external-URL `reference_materials` entries when picking up the Issue. No new skills, no new agents, no new bundled helpers, no new contract keys.

**Mode fork in `/quo-file-issue`.** `skills/quo-file-issue/SKILL.md` gains a "Mode fork" sub-section before Step 0 that parses `--reference <url>` / `--from-github <url>` from the argument string and routes accordingly. When an external-reference flag is present, the skill skips Step 0 (mid-conversation context detection) and Step 1 (distill-vs-restart fork) and Step 3's full body-template path entirely; instead it routes to a new "External-reference branch" at the end of the Steps section with three sub-steps: (A) author a thin Issue body (2-3 sentences, optionally distilled from conversation context, fetched via `WebFetch`, or asked from the user in prose); (B) pick a resolver name from the URL-pattern heuristic; (C) run `bees create-ticket` with the inline `--body` plus `--reference-materials '[{"value":"<url>","resolver":"<name>"}]'`. Steps 4 (commit) and 5 (report back) are shared with the in-conversation capture flow. The `argument-hint` is updated to `[<description> | --reference <url> | --from-github <url>]`.

**URL-pattern resolver-name heuristic.** The resolver name is selected by URL pattern matching on host first, then path-shape: GitHub Issue URLs (`https://github.com/<owner>/<repo>/issues/<n>` and similar) yield `github-issue`; Linear ticket URLs (`https://linear.app/<workspace>/issue/<id>` and similar) yield `linear-issue`; anything else (Slack archive link, internal bug tracker, generic web page) falls back to `url`. The match is best-effort and informational — it primarily helps human readers and future resolver implementations identify the source class. Writing the canonical resolver name now (rather than always writing `url`) future-proofs existing Issue tickets so they do not need to be migrated when concrete resolvers ship.

**Concrete-resolver gap and `WebFetch` fallback.** No concrete `github-issue`, `linear-issue`, or `url` resolver exists in the bees CLI today — that is intentional and out of scope for this skill set; concrete resolvers are tracked separately as their owners materialize. Until those land, the workflow falls back to fetching the upstream content via `WebFetch` whenever it is needed. `agents/engineer.md` and `agents/pm.md` both gain `WebFetch` in their tool allowlists and a new instruction bullet describing the fetch convention: when the Issue's `reference_materials` is non-empty and points at an external URL, the worker fetches the upstream content via `WebFetch` and treats it as the spec source for the implementation (Engineer) or the spec review (PM); the Issue body itself is intentionally thin on this path. `WebFetch` failures (network policy, auth-gated source, etc.) are surfaced to the orchestrator rather than silently fallen back to the thin body alone — the dispatch prompt's embedded body is not enough on this path.

**`/quo-fix-issue` orchestrator wiring.** `skills/quo-fix-issue/SKILL.md` gains a single sub-bullet in the "Dispatch prompt: quote the issue body verbatim" sub-section: when the Issue's `reference_materials` is non-empty, embed the `reference_materials` JSON value alongside the (thin) body in each dispatch prompt so the worker can read the resolver name and URL. The orchestrator does not pre-fetch the URL — fetch is the worker's responsibility per the role contracts. The PM dispatch description's resolver-branching list is updated to enumerate `github-issue` / `linear-issue` / `url` alongside the existing `file-path` and `bees` resolver paths; `agents/pm.md` is the authoritative spec for all three resolver-driven paths (`file-path`, `bees`, and the external-URL resolvers like `github-issue` / `linear-issue` / `url`); the body-as-spec path is the null/empty fallback. Scoped-marker resolution is skipped on the external-URL path (Scoped markers apply to file-on-disk PRD/SDD content, not to external URLs).

**Body-shape divergence on the external-reference path.** The thin body shape on this path is intentionally **flat** — no `## Description` / `## Current behavior` / `## Expected behavior` / `## Impact` / `## Suggested fix` headings. Those sections exist to extract structure from in-conversation capture; on the external-reference path the structure lives at the URL, and forcing the headings into a thin body would either duplicate URL content or render mostly-empty stubs. The optional `## Doc divergence noted` section may still be appended on this path when the user (or surrounding conversation) explicitly flags a doc-divergence observation that the external source does not already capture; in routine external-reference filings the section is omitted. A single convention line near the top of the body — `External reference: <source-class> <url>` — names the referenced source so a human reader of the Issue body alone can tell where to look; the line is a convention, not a contract — `reference_materials` is the load-bearing signal that downstream `/quo-fix-issue` reads.

**Inline-body vs temp-file fallback in step C.** Unlike the in-conversation capture path (which always writes the body to a temp file under `<tempdir>/.quorum/` to avoid Claude Code's command-injection guard on multi-line bodies and shell-special characters), the external-reference branch passes the thin body inline via `--body` because most thin bodies fit cleanly on a single line. The temp-file convention from Step 3c is the safety valve: if the thin body authored in (A) contains anything that would trip the injection guard — a newline followed by a `#` heading, backticks, or shell-special characters — fall back to the temp-file path (write under `<tempdir>/.quorum/bees-body-<short-suffix>.md` with the `mkdir -p` / `New-Item -ItemType Directory -Force` create-if-absent step) and replace `--body "<...>"` with `--body-file <path>`, keeping `--reference-materials` unchanged.

**Customer-facing and architecture doc updates.** README.md skill table row for `/quo-file-issue` is rewritten to document both invocation modes (in-conversation capture vs external-reference) and explicitly names the external-URL resolvers and the `WebFetch` fallback. SDD `## Architecture overview` resolver list is extended from two resolver classes (`file-path`, `bees`) to three (adding the external-URL resolver class). SDD `## Key components` entries for `quo-file-issue` and `quo-fix-issue` are updated — the `quo-file-issue` entry now describes both modes; the `quo-fix-issue` entry gains an "**External-reference consumer**" rider naming the dispatch-prompt embedding and the `WebFetch` fallback. `docs/doc-writing-guide.md` `## Project terminology` `Reference materials` entry adds an "External-URL resolvers" sub-bullet alongside the existing `file-path` and `bees` resolver sub-bullets.

**Decomposition.** Shipped as a single Issue (`b.qs8`) rather than a multi-Epic Plan Bee. The work is small and surgical (one mode-fork branch in one `SKILL.md`, two tool-list and instruction additions in agents, one orchestrator-side dispatch-prompt sub-bullet, and parallel doc updates), and the analogs already exist for the Engineer to model from (`/quo-plan-from-specs` is the symmetric planning-side skill). ### Feature: Recommend gh issue close at end of /quo-fix-issue for github-issue resolver

**Architecture.** Add a GitHub-close recommendation block (since the orchestrator rewrite: the final-output step of `skills/quo-fix-issue/SKILL.md` plus `references/github-close.md`), executed after the post-completion review either reports clean or its per-finding follow-ups close out, and **before** the orchestrator yields the turn. The section is pure prose-driven — no helper script, no agent dispatch, no contract-key change. It iterates the run's fixed-issue list, reads each Issue's `reference_materials` (re-using the value the orchestrator captured during the dispatch reads when still in context, otherwise re-reading via `bees show-ticket --ids <issue-id>`), filters for entries whose `resolver == "github-issue"`, parses the canonical GitHub Issue URL pattern (`https://github.com/<owner>/<repo>/issues/<n>`) for `<owner>`, `<repo>`, and `<n>`, captures the per-issue commit SHA from the per-Issue close-out commit (preferred path: track at commit time, keyed by issue ID; fallback: re-derive post-hoc by walking back from `HEAD` over the session's commits using `git log --format=%H <pre-session-sha>..HEAD`), abbreviates via `git rev-parse --short`, and emits one bullet of the shape `gh issue close <n> --repo <owner>/<repo> -c "Fixed in <sha>."` per matching entry. The entire block is suppressed when zero bullets are collected. The skill never invokes `gh issue close` itself.

**Why this shape.** Three design decisions shape the GitHub-close block:

- **Scope to `github-issue` resolver only.** `linear-issue` close requires Linear's own CLI/API which isn't bundled with the workflow; the generic `url` resolver has no close concept. The recommendation block intentionally does not generalize to those resolvers — adding either is a separate Issue once the corresponding integration is decided. This keeps the prose simple (one URL pattern to parse, one command shape to emit) and the surface minimal.
- **Pure recommendation, never executes.** The workflow does not assume the user is authenticated against `gh` on the same machine where `/quo-fix-issue` runs (a real concern: many users develop on one machine and authenticate `gh` only on a build / CI machine, or against multiple accounts). Surfacing the command for copy-paste keeps the auth surface owned by the user. This mirrors the broader "skills must work on Rust, Node, Python, Go" portability principle: no assumption baked into the workflow about the user's external tooling state.
- **Position after the post-completion review, before yield.** Emitting earlier (e.g., at the per-Issue close-out) would interleave the recommendation lines with per-issue summary blocks and dilute the signal. Emitting after the post-completion review consolidates the recommendation into a single end-of-run block the user can copy in one gesture. The "before yield" constraint is load-bearing — once the orchestrator yields the turn, the user's next action may begin and the recommendation becomes harder to spot.

**SHA capture.** Two equivalent paths are documented to obtain the per-issue commit SHA: (a) **track at commit time** — record the SHA the moment the per-Issue close-out's `git commit` returns, keyed by issue ID (the manifest's `**Progress:**` line), and re-use it in the final output (abbreviating via `git rev-parse --short` if the captured form is the full 40-char SHA); (b) **re-derive post-hoc** — resolve the commit per Issue by `--grep`-filtering the session's commits against the per-Issue close-out's commit-message convention (every per-issue commit's subject begins with `Fix issue: <title> (<issue-id>)`), running once per fixed Issue: `git log --reverse --format=%h --grep='Fix issue:.*(<issue-id>)' <pre-session-sha>..HEAD` (substituting the literal Issue ID for `<issue-id>` and the session-start SHA recorded in the manifest's `**Pre-session SHA:**` for `<pre-session-sha>`). Each invocation returns at most one match — the per-issue commit for that Issue — and `%h` emits the abbreviated SHA directly so no follow-up `git rev-parse --short` step is needed on the fallback path. Path (a) is preferred for clarity but path (b) is sound when the orchestrator did not track at commit time. Two design choices on the fallback command are load-bearing: (i) **scoping each lookup by `(<issue-id>)`** filters out any extra commits the post-completion review's "Fix in this session" branch may have landed in the same `<pre-session-sha>..HEAD` window — a positional bulk-log pairing without `--grep` would mis-pair those follow-up commits against the fixed-issue list; (ii) **`--reverse`** flips `git log`'s default newest-first ordering to oldest-first, which only matters in the (rare but legal) case where multiple commits in the window match the per-issue grep — oldest-first then puts the original per-issue fix-commit at position 1 of the output, ahead of any later amendments that share the same Issue ID in their subject. Both ordering decisions defend against silent SHA / Issue mis-pairing.

**Suppression and ordering.** The block is suppressed entirely when zero bullets are collected (every fixed Issue's `reference_materials` is null/empty or carries only non-`github-issue` resolvers). This keeps the trace clean for users who never used the URL path. Bullet ordering matches the run's fixed-issue iteration order (single-issue mode: one bullet; list / `all` mode: bullets in fixed-list order). When a single fixed Issue carries multiple `github-issue` entries in `reference_materials` (uncommon but legal — the resolver list is an array), one bullet is emitted per matching entry, in array order. Issues that were skipped (per the run-start blocked-issue handling in batch mode) or never reached (e.g., upfront validation soft-failed at run start) do not contribute bullets — only Issues that this run actually marked `done` via the per-Issue close-out are iterated.

**Informational, not a gate.** The recommendation block is plain console output — NOT an `AskUserQuestion` gate. The user is not asked to confirm; the orchestrator emits the block and yields. Adding a confirmation gate would defeat the purpose: users who want to act on the recommendation copy the line and run it; users who don't want to act on it ignore the block.

**No agent / contract changes.** The GitHub-close block lives entirely in `skills/quo-fix-issue/SKILL.md` orchestrator prose (since the rewrite, its final-output step plus `references/github-close.md`). No agent role files (`agents/engineer.md`, `agents/pm.md`, `agents/doc-writer.md`, etc.) need updates — the recommendation is built by the orchestrator from data already captured during the run. No `## Build Commands` / `## Documentation Locations` contract keys are added or renamed. Existing Issue tickets do not require migration; the recommendation is computed at run time from `reference_materials` data already on each ticket.

**Decomposition.** Shipped as a single Issue (`b.h3s`) — a small, prose-only orchestrator extension at the tail of `skills/quo-fix-issue/SKILL.md`, plus the cumulative-doc subsections in PRD and SDD and a one-line README skill-table addendum. ### Feature: Spec-review loop-back UX gates dropped under orchestrator load

**Architecture.** Move the load-bearing routing prescription for review-skill findings out of nested orchestrator prose and into each review skill's own output as a `**Next action for the orchestrator:**` trailer line. The trailer names the precise gate or follow-up the orchestrator must run after consuming the findings — `AskUserQuestion` with the recommended option set on a findings-present return, immediate promote-and-continue on a clean return — so the routing rule travels with the artifact a fresh orchestrator agent actually reads, rather than living three levels deep in a long orchestrator-skill body that the agent is reproducibly missing under load. Affects four review skills (`/quo-spec-review`, `/quo-engineer-review`, `/quo-test-writer-review`, `/quo-doc-writer-review`) and five orchestrator sites (`/quo-plan` Step 4c, `/quo-write-prd` Step 6a, `/quo-write-sdd` Step 7a, and the review loops of `/quo-execute` and `/quo-fix-issue`). No new skills, no new agents, no new bundled helpers, no new contract keys, no changes to the seven role files in `agents/`. Existing review-skill output consumers that already followed the orchestrator-prose rules continue to work without modification — the trailer is additive, not a contract evolution.

**Trailer shape — three variants for `/quo-spec-review`.** The spec reviewer's output is severity-tagged (`blocker` / `suggestion` / `nit`), so the trailer collapses to three shapes keyed on what the work-item list above it contains: (1) **Blockers present** — trailer prescribes `AskUserQuestion` with finite choices `Revise` (recommended) / `Proceed anyway (override blockers)` before the Spec Bee's `drafted → ready` promotion; (2) **Suggestions / nits only** (no blockers) — trailer prescribes `AskUserQuestion` with finite choices `Proceed (acknowledge findings)` / `Revise` before promotion; (3) **No findings** — trailer prescribes immediate promotion with no user prompt at this step. The phrasings are emitted verbatim by `/quo-spec-review` Step 4 alongside the work-item list itself.

**Trailer shape — two variants for the three code/test/doc reviewers.** `/quo-engineer-review`, `/quo-test-writer-review`, and `/quo-doc-writer-review` do not emit severity tags, so each collapses to two shapes: (1) **Findings present** — trailer prescribes the orchestrator-side review-loop discipline (judge whether the items must be addressed; if yes, dispatch a fresh implementer Agent to address them and re-invoke the review skill on the updated diff; if no, carry the ignored items into the final/Bee-level summary so they remain visible); (2) **No findings** — trailer prescribes proceeding to the next review lane (or to Task / Issue close-out if this was the last lane), with no re-dispatch needed for the reviewed role on this iteration. The phrasings are subject-specific per skill (the Engineer reviewer's trailer names "Engineer Agent"; the Test Writer reviewer's names "Test Writer Agent"; the Doc Writer reviewer's names "Doc Writer Agent") but share the same skeletal structure.

**Orchestrator-side prose downgrade.** At each of the five orchestrator sites, the prose that previously carried the load-bearing routing prescription is downgraded to reference context with explicit language naming the trailer as authoritative — phrasings of the form "follow the **Next action for the orchestrator:** line in the review output" plus a "follow the trailer literally; the prose below is reference context, not a load-bearing rule the orchestrator must recall from memory" callout. The reference prose is kept (it documents the routing rules for human readers and for maintainers who diff the orchestrator skills), but the orchestrator agent is explicitly told that the trailer wins when the two ever diverge (and that divergence is a bug in the review skill to file). `/quo-plan` Step 4c additionally carries a quick-reference summary table of the three trailer shapes (a belt-and-suspenders measure at the orchestrator site that surfaces the routing prescription closer to where the orchestrator's attention lands — the table is reference context only; the trailer in the review output remains canonical).

**Standalone-invocation handling.** When a review skill is invoked standalone by a user (not by an orchestrating skill), the "orchestrator" the trailer addresses is the assistant turn presenting the findings to the user, and the user is the human in the gate prompt. The trailer still emits in all output shapes on the standalone path — it is not suppressed — both so the standalone caller benefits from the same routing prescription and so its presence acts as a self-check that the skill considered the routing question. This is consistent with the dual-mode design of `/quo-spec-review` and the orchestrator-only design of the three code/test/doc reviewers (which on the rare standalone invocation path are read by a human directly).

**Why this shape.** Three design decisions shape the fix:

- **Routing rule lives with the artifact.** Orchestrator agents reproducibly miss routing rules buried in nested orchestrator prose under load — the agent reads the rule once at skill-invocation time and then re-reads only the review-skill output when consuming findings. Moving the routing rule into the review-skill output itself means the agent re-reads the rule every time it consumes the findings, which is exactly when the rule is needed. This is structurally similar to the cross-anchored prose pattern shipped in `b.v4g` for the `/quo-file-issue` ↔ `/quo-fix-issue` hand-off contract: both fixes move a load-bearing prose anchor to the place the consuming agent actually re-reads, rather than relying on prose-elsewhere-in-this-skill-body recall.
- **Verbatim emit, not paraphrase.** The trailer phrasings are emitted verbatim by the review skills (literal `**Next action for the orchestrator:**` prefix; literal `AskUserQuestion`-with-finite-choices language; literal "Do not yield without doing this" enforcement clause where applicable — superseded by the `b.fpm` refinement below for the literal trailer phrasings). Paraphrased trailers would invite per-invocation drift in the load-bearing routing prescription, defeating the move-to-artifact purpose. The orchestrator prose downgrade explicitly calls out that the trailer is the authoritative routing prescription and that divergence between trailer and prose is a bug in the review skill.
- **No control-flow change.** The reconciliation loop's tick semantics, the time-budget short-circuit, the AskUserQuestion option-ordering rules, the end-of-skill report bucketing for acknowledged/overridden findings, and the inline-skip contract (`/quo-write-prd` Step 6a and `/quo-write-sdd` Step 7a skip when invoked inline from `/quo-plan` Step 4b) are all unchanged. The fix is purely a relocation of where the routing prescription is authored so the orchestrator agent reproducibly reads it at the right moment.

**No agent / contract changes.** No agent role files (`agents/engineer.md`, `agents/test-writer.md`, `agents/doc-writer.md`, `agents/pm.md`, `agents/code-reviewer.md`, `agents/test-reviewer.md`, `agents/doc-reviewer.md`) are touched — the trailer convention is a skill-to-skill prose contract between the four review skills and the five orchestrator sites that consume their output, not an agent-side instruction. No `## Build Commands` / `## Documentation Locations` contract keys are added or renamed. No bundled helper scripts are added or modified. The bees CLI and the ticket shapes are all unchanged. Existing tickets and existing review-loop iteration outputs do not require migration; the trailer is invisible from the bees-state perspective.

**No README change.** The user-typed slash-command invocation surfaces for all four review skills and all five orchestrator skills are byte-for-byte unchanged, and the README skill-table rows describe what each skill does at a user-visible level that this fix does not shift. The trailer convention is an internal contract between review skills and their orchestrators — not user-visible — and is not surfaced in the README skill catalog.

**Decomposition.** Shipped as a single Issue (`b.sfy`) — a prose-only hardening across nine `SKILL.md` files (the four review skills and the five orchestrator skills) plus this cumulative-doc subsection. No multi-Task decomposition was warranted; the trailer-emit prose in the four review skills and the prose-downgrade-plus-quick-reference at each of the five orchestrator sites are tightly coupled and ship together as a single atomic change. No PRD subsection is added because the user-facing behavior is unchanged — the categorization heuristic in `agents/doc-writer.md` places this fix in the architecture-only row (orchestrator-orchestrated contract refinement with no user-visible surface change), which warrants an SDD entry but not a PRD entry.

**Follow-up hardening (`b.fpm`) — second-person imperative form and counter-anchor clause.** After the `b.sfy` trailer convention shipped, orchestrators were observed routinely emitting the trailer text and yielding the turn without firing the prescribed `AskUserQuestion` or `bees update-ticket --status ready` tool call — the user had to nudge the workflow back into motion before the gate fired. Diagnosis: three reinforcing factors were at play — third-person framing (`**Next action for the orchestrator:**` describes the gate rather than commanding the agent that is about to act), end-of-response attentional drift (the trailer is the last thing the agent emits, so its imperative weight evaporates as the response closes), and no pre-commitment at the call site (the orchestrator skills' Step 4c / 6a / 7a sites did not explicitly say "your next tool use after the Skill call must be the gate"). `b.fpm` hardens the trailer convention on top of `b.sfy` with two complementary refinements that address all three factors: (1) the trailer text in all four review skills is rewritten from third-person framing to **second-person imperative** — `**Your next tool call MUST be AskUserQuestion** with finite choices …`, `**Your next tool call MUST be bees update-ticket --status ready** …`, `**Your next tool use MUST address these findings now.**`, `**Your next tool use MUST advance the workflow.**` — addressing the orchestrator turn directly as the agent that is about to act; (2) every trailer carries a verbatim **counter-anchor clause** at the end (`Do not produce a text response describing this gate — call the tool directly.` for `/quo-spec-review`'s `AskUserQuestion` shapes, `… describing this transition …` for the no-findings `bees update-ticket` shape, and `Do not yield with this text as your assistant response — perform the judgment and act on it, or pass it to the user via prose explaining your decision.` for the three code/test/doc reviewers' orchestrator-judgment shapes), which is the specific affordance that addresses the narrate-instead-of-do failure mode; (3) a **pre-commitment line** is added immediately before each `/quo-spec-review` Skill invocation at the three consumer sites (`/quo-plan` Step 4c, `/quo-write-prd` Step 6a, `/quo-write-sdd` Step 7a) — `When the Skill call returns, your next tool use MUST be either AskUserQuestion (findings present) or bees update-ticket --status ready (no findings). A text-only response between the Skill return and that tool use is a defect.` — relocating attentional weight from end-of-response (where it is easy to drop) to immediately-before-Skill-call (where it is easy to recall when the Skill return lands). The convention contract for future skill authors is anchored in `docs/doc-writing-guide.md` `## Review skills emit a routing trailer`, which now names second-person imperative as the load-bearing form and the counter-anchor clause as a required component of every trailer. No agent / role-file / contract / README change — `b.fpm` is the same shape as `b.sfy` (skill-prose-only, eleven files: four review skills (`/quo-spec-review`, `/quo-engineer-review`, `/quo-test-writer-review`, `/quo-doc-writer-review`) carrying the rewritten trailers, three consumer-orchestrator skills (`/quo-plan`, `/quo-write-prd`, `/quo-write-sdd`) carrying the new pre-commitment lines, two reference-context-only orchestrator skills (`/quo-execute`, `/quo-fix-issue`) whose review-loop sections cite the trailer-prefix phrasing and were updated to match the new shape, the `docs/doc-writing-guide.md` convention anchor, and this SDD continuation). Existing review-skill output consumers continue to work without modification — the trailer's substance is unchanged; only the grammatical form and the counter-anchor clause are added.

### Feature: PM dispatch in /quo-fix-issue: drop Complex gate, Section 4 timing, short-circuit

**Architecture.** (Section numbers in this entry are the pre-rewrite body's; since the orchestrator rewrite the PM is dispatched in Phase C of `## 4. The loop`.) Three coupled changes to the per-Issue PM dispatch flow that disentangle three concerns the previous design conflated — *whether* to dispatch PM, *when* to dispatch PM, and *what* PM does on an Issue with no spec surface to verify. The PM goes from "dispatched only when the orchestrator pre-classifies the Issue as Complex, in parallel with the implementers in Section 3" to "always dispatched per Issue, alongside the three reviewers in Section 4 after the diff exists, with a content-based self-short-circuit inside `agents/pm.md` for the no-spec-surface case." The orchestrator's role on this question collapses to "always dispatch"; the substance judgement moves into the PM Agent where the spec content is actually readable.

- **Drop the orchestrator-direct Simple/Complex gate.** The "Assess complexity" sub-section in `skills/quo-fix-issue/SKILL.md` Section 3 is deleted in its entirety. The two bullet lists it carried (Simple = categories of work; Complex = risk surfaces) were structurally non-symmetric — a 2-file source+test fix matched neither side cleanly, and the catch-all "could have non-obvious side effects" bullet pulled almost any code-touching change toward Complex. The gate also fired *before* the Engineer ran, but several of its bullets ("changes span 3+ source files") are properties of the post-implementation diff, which the orchestrator was guessing about from the Issue body. More fundamentally, the spec-drift-risk judgement requires reading the spec content; that content lives where the PM has access (the Issue body, the linked Plan Bee body, the cited PRD/SDD docs, the upstream URL content via `WebFetch`) and where the orchestrator does not (the orchestrator only sees the Issue body verbatim). Moving the judgement to the actor that has the context, rather than tuning the gate's thresholds, addresses the root cause of the false-positive Complex classifications the user observed as noise on routine fixes.
- **Relocate PM dispatch from Section 3 (implementer phase) to Section 4 (reviewer phase).** PM joins the three reviewer Agents (Code Reviewer / Test Reviewer / Doc Reviewer) in the Section 4 dispatch block, after the Engineer / Test Writer / Doc Writer have produced their diff. The implementer-phase Section 3 "Per-issue cold dispatch" sub-section drops PM from its role list and the "Per-issue PM dispatch" sub-section relocates to Section 4. Two consequences: (i) the internal contradiction at the former Section 3 reconciliation-loop step 2 (which simultaneously said "PM dispatched **alongside** the implementer Agents" and "the PM's report **joins the implementer outputs as input** to Section 4" — parallel-and-sequential at once) is eliminated; (ii) the PM's role contract in `agents/pm.md` — already correctly framed as the after-implementers gate — is no longer in tension with the SKILL.md prose. The previous design had drift: maintainers updating the SKILL.md were one step away from "fixing" `agents/pm.md` to match the wrong side. The Section 4 move makes the SKILL.md the side that aligns with the role contract.
- **PM is dispatched outside the conditional-spawn rules for reviewers.** The Section 4 dispatch block has historically carried a rule that a reviewer is dispatched only when its corresponding implementer was used (Test Reviewer only when Test Writer ran; Doc Reviewer only when Doc Writer ran). That rule does not apply to PM: spec-alignment review is meaningful on any diff regardless of which implementers contributed, so PM is dispatched per Issue unconditionally. The Section 4 prose names PM as the exception to the conditional-spawn rule and as a fourth Agent alongside the three reviewers, not instead of any of them. The Section 4 review-iteration logic also drops its former "if the original fix was simple (no PM dispatched), do NOT dispatch the PM on iteration" branch — PM is always available for re-dispatch on review-loop iterations.
- **Section 5 collapses to a single unified path.** The previous Section 5 branched on the Complex/Simple classification — Complex deferred spec-alignment to the PM dispatched in Section 3, Simple did an orchestrator-direct spec-vs-code check. In the new design the PM was always dispatched in Section 4 and has either produced a spec-alignment verdict or short-circuited with "no spec drift surface to review for this Issue" — either way the verdict lands in the per-issue summary, so Section 5 is always informational confirmation of what the PM already produced, never load-bearing orchestrator-direct work. The unified path keeps the `## Doc divergence noted` confirmation logic unchanged.
- **Content-based self-short-circuit in `agents/pm.md`.** The PM's flow gains a no-spec-surface short-circuit at the top: read every available spec source first (the Issue body itself, the Plan Bee body if `up_dependencies` links one via the existing Scoped-marker Path B, the PRD/SDD-equivalent docs from CLAUDE.md `## Documentation Locations` if the body cites them, the upstream content fetched via `WebFetch` if `reference_materials` is set), then assess whether those sources *collectively* carry substantive spec content — behavior described, architecture constrained, requirements specified — beyond a title plus a one-sentence problem statement that merely identifies what to fix without specifying how. When substantive content is present in any source, the PM proceeds with the existing deep spec-vs-diff review against that substantive source. When substance is absent across all available sources, the PM exits with a one-line verdict ("no spec drift surface to review for this Issue") and skips the deep review. The orchestrator reads either outcome as a clean signal and includes it in the per-issue summary.
- **The short-circuit is content-based, not shape-based — by construction.** The PM's short-circuit logic explicitly forbids keying off shape signals like "PRD/SDD path mentioned in body," "Plan Bee linked in `up_dependencies`," or "`reference_materials` is non-null." Those signals do not reliably correlate with spec richness: a body can cite a PRD path and still be a one-line rename; a Plan Bee can be linked for a trivial typo fix; a one-sentence GitHub Issue can sit behind a non-null `reference_materials`. Conversely, a self-describing body with no external pointers can carry rich behavioral spec the PM must verify against. A shape-based pre-read check inside the PM would reproduce the exact failure mode of the orchestrator-side gate this Issue eliminates, just relocated; the content-based rule prevents that regression by mandating the PM read content before deciding.

**Why this shape.** Four design decisions shape the fix:

- **Doc Writer precedent for "always dispatched."** The same skill already names Doc Writer as "always dispatched. The Doc Writer decides whether docs actually need updating after reading the diff; the orchestrator does not pre-judge." PM now follows the same pattern, with the spec-surface check standing in for the docs-needed check. This unifies the two roles that both make a "does this diff need review?" judgement that the orchestrator was structurally bad at predicting, and matches the existing precedent rather than introducing a new dispatch pattern.
- **Move the judgement to the actor that has the context.** The orchestrator can only see the Issue body verbatim; the PM Agent can read the Issue body, follow `up_dependencies` to the Plan Bee, walk the Scoped-marker resolver to the PRD/SDD content, and `WebFetch` upstream URLs. Spec-drift risk is a function of how much content is actually in those sources, not a property predictable from the Issue body alone. Putting the judgement where the content is readable addresses the root cause of false-positive Complex classifications rather than tuning thresholds on a structurally under-informed gate.
- **No latency penalty for the always-dispatched move.** PM runs in parallel with Code Reviewer / Test Reviewer / Doc Reviewer in Section 4, and the three reviewers already gate Section 5 entry, so adding PM to that parallel block does not lengthen Section 4. The token-cost delta is one additional PM Agent invocation per Issue that today classifies as Simple (those used to skip PM entirely) — but those invocations typically hit the short-circuit and end quickly, so the per-Issue cost on the formerly-Simple path is small rather than zero.
- **No new control-flow primitives.** The reconciliation loop's tick semantics, the per-Issue cold-dispatch shape, the TaskList naming convention (`pm-<issue-id>` survives unchanged; the bullet relocates from the implementer-Agents group to the reviewer-Agents group), and the verbatim ticket-body quoting in dispatch prompts are all unchanged. The fix is a re-routing of when PM is dispatched and a self-short-circuit inside the PM, not a new orchestration primitive. Six alternative designs (two-phase PM, internal-wait PM, gate-only timing fix, drop-gate-keep-Section-3, shape-based short-circuit, and the chosen drop-gate-plus-Section-4-plus-content-short-circuit) were considered; the chosen design is the only one that addresses all three concerns (whether, when, what) without adding orchestration complexity, and is recorded in the Issue's `## Decisions and rejected alternatives` section.

**No README change.** The user-typed `/quo-fix-issue` invocation surface is byte-for-byte unchanged — no new flags, no new arguments, no new prompts. The README skill-table row for `/quo-fix-issue` does not name the Complex/Simple distinction (the gate was internal orchestrator prose, never user-visible CLI), and the `## Why this exists` PM bullet at line 31 already describes the PM as "After Engineer, Test Writer, and Doc Writer complete a Task, a PM agent reads ..." — which is the post-fix timing, not the pre-fix Section 3 timing the SKILL.md had drifted toward. The README is the side that stayed correct; the SKILL.md is the side that drifted, and only the SKILL.md needs correction.

**No agent / contract changes beyond `agents/pm.md`.** No other agent role files are touched. No `## Build Commands` / `## Documentation Locations` contract keys are added or renamed. No bundled helper scripts are added or modified. The bees CLI, the Issue ticket shape, and `reference_materials` resolver vocabulary are all unchanged. Existing Issue tickets do not require migration; the dispatch-timing and short-circuit changes are invisible from the bees-state perspective. `/quo-execute` is unaffected — that skill always dispatches PM per Task and has never carried a complexity gate to remove.

**Decomposition.** Shipped as a single Issue (`b.tmk`) — a prose-only fix across one `SKILL.md` file (`skills/quo-fix-issue/SKILL.md`) and one agent role file (`agents/pm.md`) plus this cumulative-doc subsection. The user-perceived noise reduction on trivial fixes is an internal quality improvement (a mis-classification was happening invisibly inside the orchestrator and producing extra review-burden lines in the per-issue summary), not a new surface the user interacts with.

### Feature: Workflow trusts Issue ticket bodies as authoritative design specs

**Architecture.** Insert a pre-implementation **design-analysis gate** into `/quo-fix-issue`, owned by a new **Analyst** subagent that does its own codebase research and returns a Design Proposal grounded in *this* codebase rather than in the Issue body's framing. The gate sits between the existing Validate-Issue step and the per-issue implementer dispatch; the user (the quorum operator) approves, revises, or cancels the Analyst's proposal before any Engineer dispatch fires. Issue bodies remain quoted verbatim in downstream dispatch prompts — the change is that the Engineer's authoritative design directive is now codebase-grounded Analyst output rather than the Issue body's proposed solutions taken at face value. As shipped here that directive was the **Recommended approach** alone; the follow-up `b.q3f` (see `### Feature: Analyst must produce a blast-radius sweep and name implied policy decisions at the design gate` below) widened it to three sections, so the single-section description in this subsection reflects the `b.1bv`-era design, not the current one. The fix is `/quo-fix-issue`-only by design: `/quo-execute` already handles design analysis upstream via `/quo-plan` (PRD/SDD authoring + Epic decomposition + spec review), so the same gate would be redundant in execute mode and is not wired there. Two artifact changes carry the architecture — a new role-contract file (`agents/analyst.md`) and a new orchestrator gate in `skills/quo-fix-issue/SKILL.md` — plus the precondition-list and subagent-count bumps that follow from the eighth required subagent type.

**New `agents/analyst.md` role file.** The eighth custom-subagent definition file. Model is Opus (always) — not user-configurable — matching the Engineer / Test Writer / Code Reviewer / Test Reviewer standard because the Analyst does substantive codebase research and design reasoning where output quality is load-bearing. Tools allowlist is `Read`, `Grep`, `Glob`, `Bash`, `WebFetch` — deliberately no `Edit`, `Write`, or `Skill`: the Analyst returns a structured Design Proposal to the orchestrator and exits; downstream file modification is owned by the Engineer / Test Writer / Doc Writer subagents, and user interaction is owned by the orchestrator. The role contract enumerates: (i) reading the Issue body verbatim and (when `reference_materials` carries a `github-issue` / `linear-issue` / `url` resolver) fetching the upstream content via `WebFetch`, treating both as **problem-report context, not authoritative design**; (ii) reading the local codebase — source files implicated by the Issue, the SDD / PRD section(s) named in CLAUDE.md `## Documentation Locations`, related skills' contracts (`skills/<name>/SKILL.md`) and subagent role files (`agents/<name>.md`) when the Issue touches workflow behavior, and adjacent Issue ticket notes via `bees show-ticket --ids <related-id>` when the body references them; (iii) producing a Design Proposal in the structured shape below; (iv) surfacing the proposal as structured output to the **orchestrator** (NOT the user — the orchestrator owns the user-interaction gate). The role file's cold-start invariant matches the other subagents: every dispatch is single-shot; a `Revise`-branch re-dispatch is a fresh cold invocation that re-reads everything from scratch with the user's revision feedback added to the new dispatch prompt — the `b.1bv`-era shape; `b.q3f` below added a second trigger (an Engineer's `## Design question`, which travels in place of the user's feedback) and the instruction to read the working tree as mid-change.

**Structured-output contract (Analyst → orchestrator).** The Analyst returns a single markdown response under a `## Design Proposal for <issue-id>` heading. As originally shipped here it carried six sections — `### Problem`, `### Root cause`, `### Recommended approach`, `### Why`, `### Alternatives considered`, `### Options the body did not consider`. **The current contract is eight unconditional sections**, in order: `### Problem`, `### Root cause`, `### Recommended approach`, `### Blast radius`, `### Policy decisions this change implies`, `### Why`, `### Alternatives considered`, `### Options the body did not consider` — the two middle additions landed with `b.q3f` below. Then an optional `### Upstream-fetch status` section when `reference_materials` is non-empty, a trailer line `Analyst verdict: <one of: recommend-as-stated | recommend-with-refinements | recommend-different-approach | escalate-to-user>`, and a `### Deferred refinements` block after the trailer (added by `b.dgq` below). The verdict is a **load-bearing framing signal**: the orchestrator reads it and uses it to shape the prose preamble that introduces the proposal to the user — divergent verdicts (`recommend-different-approach`, `escalate-to-user`) get a prominent "⚠️ The Analyst diverged" framing so the user encounters the proposal already aware of the divergence rather than discovering it by reading carefully. Routing through the `AskUserQuestion` gate is still driven by the user's choice, not the verdict — the verdict shapes how the user *encounters* the proposal, not which gate option is offered. On the Approve branch the orchestrator carries the directive sections into the Engineer dispatch prompt — the Recommended approach as shipped here, and, since `b.q3f` below, the Recommended approach together with `### Blast radius` and `### Policy decisions this change implies`. The `### Alternatives considered` section must enumerate every distinct solution the Issue body proposed (kept, refined, or set aside, with a one-or-two-sentence reason) so the user can see the Analyst engaged with each option from the body's menu rather than ignoring them. **Why this shape.** Four design decisions shape the fix:

- **Codebase research, not body classification.** An earlier-rejected alternative was a body-quality classifier — a heuristic that tagged Issue bodies as "well-researched" or "casual" upfront and routed only the casual ones through extra design scrutiny. That design is structurally fragile: any classifier is a heuristic, classifiers misfire on edge cases, and the misfires bias against the exact bodies that most need the scrutiny (a casual body that happens to cite a file name looks well-researched; a thorough analysis that omits citations looks casual). The chosen design avoids classification entirely — the Analyst always runs, always reads the codebase, and the Design Proposal naturally converges to the body's framing when the body IS well-researched (with prompt-caching keeping the overhead bounded) and naturally diverges when the body is shallow. Either way, the user reacts to an informed recommendation rather than a raw body menu.
- **Pre-implementation, not post-implementation.** A second-rejected alternative was to keep the existing post-implementation PM spec-alignment review as the only design-scrutiny gate — letting the PM challenge whether the body's framing was correct, in addition to its existing role of checking that the implementer faithfully executed the body. That design is too late: by the time the PM runs, the Engineer has already implemented per the body's proposed solutions, and the PM either rubber-stamps the wrong-by-design fix or asks the orchestrator to re-do the work. The Analyst gate runs **before** any implementer dispatch, so design divergence is caught when re-work is cheap (re-dispatch the Analyst with revision feedback, or change the Engineer dispatch prompt) rather than when re-work means re-implementing the fix.
- **Prose for the proposal, `AskUserQuestion` for the decision.** The Design Proposal is free-form analysis — Problem, Root cause, Recommended approach, Why, Alternatives considered, and the rest of the section set the structured-output contract above enumerates (that enumeration is the current one; the sections named here are illustrative of the shape, not a complete list). ### Feature: Phase skills silently drop "defer to next session" items at session handoff

**Architecture.** Three layers of complementary change carry the fix across the four phase skills and two agent role files. No new skills, no new bundled helpers, no new contract keys, no changes to the bees CLI or the Issue / Plan Bee / Epic ticket shapes. The wrapper reviewer Agents (`agents/code-reviewer.md`, `agents/test-reviewer.md`, `agents/doc-reviewer.md`) and their wrapped review skills (`/quo-engineer-review`, `/quo-test-writer-review`, `/quo-doc-writer-review`) are intentionally **not** touched — the Engineer's in-flight diff-review pass treats unaddressed `blocker`-severity findings from the wrapped review skills as the existing deferral-equivalent surface, and adding a parallel destination-annotation contract to the wrappers is a separable follow-up if the heuristic proves insufficient.

- **Layer 1 — `defer-<short-suffix>` TaskList convention.** Each phase skill's TaskList naming convention is extended with a new **deferral-ledger task** category: name shape `defer-<short-suffix>` (e.g., `defer-1`, `defer-2`, or any collision-resistant suffix), `metadata.activity` carries the deferral's one-line description, status transitions are `pending` → (`in_progress` while the orchestrator routes the resolution) → `completed` (the moment the deferral lands in a durable carrier: an updated ticket body, a new Issue, or an explicit in-session resolution with the resolution path logged into `metadata.activity`). The convention is **run-scope** only — persisting the ledger across Claude Code sessions would re-introduce the silent-drop failure mode the gate exists to eliminate. The orchestrator creates a `defer-*` task at the moment an inline-invoked writer/reviewer skill or a dispatched Agent surfaces an item carrying a destination annotation (per Layer 3 below), OR when the orchestrator itself sets an item aside during its own reconciliation (e.g., end-of-skill report buckets in `/quo-plan` Step 5f that previously had no ledger surface).

- **Layer 2 — "Before handoff — deferral hygiene" gate in each phase skill.** A new sub-section is inserted into each of the four phase skills' SKILL.md prose, positioned immediately before the existing yield-control step:
  - `/quo-plan` **Step 5g** — between Step 5f (Report) and Section 6 (Offer Next Steps).
  - `/quo-breakdown-epic` **Section 6.5** — between Section 6 (Commit) and Section 7 (Offer Next Steps).
  - `/quo-execute` **`## 9. Deferral hygiene`** — between the post-completion review and the final output (since the orchestrator rewrite; previously Section 6.5).
  - `/quo-fix-issue` **`## 9. Deferral hygiene`** — between the per-Issue close-out and the post-completion review (previously Section 7.5), with **per-Issue firing** (between each Issue's close-out and the advance to the next Issue / the post-completion review) AND **end-of-batch firing** (between the last Issue's per-Issue gate and the post-completion review itself) in `all` / list mode. Single-issue mode fires the per-Issue gate once and the end-of-batch firing is a no-op.

  The gate enumerates the active `defer-*` TaskList set; when empty it emits a one-line console message (`Deferral hygiene: no deferred items.` for per-Issue / single firings; `Deferral hygiene (batch close): no deferred items.` for `/quo-fix-issue`'s end-of-batch firing) and advances. When non-empty it surfaces the set as a numbered markdown list and presents an `AskUserQuestion` with finite choices `Fix in this session` / `File as issue tickets` / `Encode in an existing ticket body`. The three options are mutually-non-exclusive at the active-set level — the user may route different items to different destinations in one reply. The **Encode in an existing ticket body** option authors a revised body to a temp file under `<tempdir>/.quorum/` per the project's scratch-file convention (`mkdir -p` / `New-Item -ItemType Directory -Force` create-if-absent; no `rm` / `Remove-Item` cleanup), appending a `## Deferred from /<skill> run (<YYYY-MM-DD HH:MM>)` section to the named ticket's body and landing the update via `bees update-ticket --ids <ticket-id> --body-file <path>`. The `## Deferred from /<skill> run` stem is the contract string; the appended `(<YYYY-MM-DD HH:MM>)` date-and-time-of-day suffix (authored from the run's own clock as a literal string in the body-file, not a shell-computed substitution) disambiguates multiple Encodes to the same ticket body across separate runs so they sit side-by-side rather than stacking identical headings. The gate hard-stops the skill until every `defer-*` task is `completed` — the run cannot advance past it while any deferral remains pending or in-progress; failed sub-options (e.g., the inline `/quo-file-issue` dispatch cancelled at one of its gates, a `bees update-ticket` invocation erroring) re-surface the still-active set and re-run the gate.

  `/quo-plan` Step 5g additionally carries a **retroactive ledger reconciliation** clause — Step 5f's six end-of-skill buckets (three Step-4c spec-review buckets, three Step-5e plan-review buckets) enumerate findings the user accepted at the gate without authoring an explicit destination. Before running the gate, Step 5g walks Step 5f's buckets and creates a corresponding `defer-*` task for any item that does not already have one, so the gate's enumeration is canonical against the prior buckets even though they pre-date the `defer-*` convention's introduction.

- **Layer 3 — Agent-contract tightening for destination annotations.** Two agent role files gain a **destination annotation contract** so the orchestrator can deterministically map every deferred item the Agent surfaces onto a `defer-*` task:
  - `agents/pm.md` — the existing **Final report contract** gains a new **Deferred-item destination contract** bullet enumerating three permitted destinations per item: `addressed-now`, `defer-to-existing-ticket-body: <ticket-id>` (with `<ticket-id>` naming a Plan Bee / Epic / Task / Subtask / Spec Bee `t1=Doc` child / or the project PRD/SDD via a doc-writer pass, named by the CLAUDE.md `## Documentation Locations` contract key when the destination is a project-level doc), `defer-to-new-Issue`. Vague "defer to next phase" / "address later" / "handle during execution" framings without a named destination are explicitly forbidden — the orchestrator turns each annotation into a `defer-*` TaskList task at the dispatch site; items without a destination are flagged back to the PM as a contract violation. **The per-item choice among the three was qualified by `b.nn8`.** On a `blocker`-severity item `addressed-now` is the **only** permitted destination — deferring a blocker belongs to the orchestrator's routing gates, which pair the deferral with a dispatched narrowing and a tracker entry recording it, and the PM's `defer-*` channel carries no such pairing, so a blocker annotated for deferral here would be shelved with nothing narrowed. See the `b.nn8` feature below.
  - `agents/analyst.md` — the existing structured-output contract gains a new `### Deferred refinements` section after the `Analyst verdict:` trailer. The section's shape is **verdict-keyed**: on `recommend-as-stated` and `escalate-to-user` the section is structurally empty (the heading is emitted followed by `None` so the orchestrator can parse the section deterministically); on `recommend-with-refinements` and `recommend-different-approach` the section is a bulleted list with the same three destination annotations as the PM contract (with `Task` ↔ `Issue` wording shifts to match the fix-mode context the Analyst dispatches into). The Analyst's third option originally differed from the PM's in wording only (`Issue` for `Task`, matching the dispatch context — the Analyst is fix-mode-only, the PM dispatches in both execute and fix mode); the orchestrator rewrite unified both to the single literal `addressed-now`.

**Why this shape.** Five design decisions shape the fix:

- **Structural enforcement, not discretionary discipline.** The pre-fix design relied on the orchestrator manually translating each "address later" remark into a ticket-body update or a new Issue before yielding — a discipline that was easy to drop under load (long runs, late hour, complex multi-Issue batches). Moving the close-out behind a hard-stop gate makes it impossible to yield with active deferrals on the books, eliminating the silent-drop failure mode at the substrate rather than at the agent-instruction level. This mirrors the routing-trailer convention shipped under `b.sfy` / `b.fpm` for review skills: load-bearing routing prescriptions live in artifacts the consuming agent reproducibly reads, not in prose buried elsewhere in the skill body.
- **TaskList as the ledger substrate.** TaskList tasks are already the orchestrator's native progress-tracking primitive (per-Agent invocations, per-Issue cold dispatches, per-Subtask reviews), they render live in Claude Code's UI so the user sees the active deferral set without typing a status command, and they support the `metadata.activity` field for carrying the deferral's description. Adding a new ledger primitive (a separate JSON file, a bees ticket sub-shape, etc.) would have introduced a parallel state surface to keep coherent across the orchestrator's reconciliation loop; reusing TaskList collapses the ledger into the existing tick semantics without new primitives.
- **`defer-<short-suffix>` naming, deliberately short.** The convention is `defer-1` / `defer-2` rather than `deferred-from-pm-task-2.abc.de` or `deferral-2026-05-28-1` because the orchestrator emits these into the Claude Code UI live during a run; a long name compresses the visible activity prefix the user reads at a glance. The short-suffix form is also collision-resistant within a run-scope ledger (the deferral-set rarely exceeds a handful per Issue / Task / Epic) without forcing a uniqueness-checking step on every emit. Filesystem-path naming conventions (e.g., the existing `bees-body-<short-suffix>.md` scratch-file pattern) use longer suffixes because they may collide across concurrent runs writing to a shared filesystem; TaskList names are per-orchestrator-session and do not face that constraint.
- **Three options, not two.** A two-option design (`Fix in this session` / `File as issue tickets`) would have forced the user to either own every deferral immediately or fragment them across many new Issue tickets — both routes lose the natural locality some deferrals have (e.g., a "polish this section's prose later" item belongs in the Spec Bee's PRD child body, not as a standalone Issue). The third option (**Encode in an existing ticket body**) gives the user a way to thread the deferral into a ticket whose body is already the natural place to keep it without inflating the Issue queue with low-priority polish items. The three options are mutually-non-exclusive at the active-set level so a long active set can route different items to different destinations in one reply.
- **Wrapper-reviewer omission, deliberate.** `agents/code-reviewer.md`, `agents/test-reviewer.md`, and `agents/doc-reviewer.md` are wrapper Agents over `/quo-engineer-review`, `/quo-test-writer-review`, and `/quo-doc-writer-review` — they return the wrapped skill's findings list verbatim and the orchestrator's review-loop discipline decides which findings warrant a fresh implementer dispatch versus carrying into the per-Task / per-Issue summary as ignored. Adding a destination-annotation contract to those wrappers would have duplicated the PM's contract on three Agents whose role is intentionally thin (orchestration glue, not judgement). The Engineer (option b) heuristic — unaddressed `blocker`-severity findings from the wrapped review skills count as the deferral-equivalent surface — keeps the wrapper Agents' contracts simple and routes the inter-session-deferral concern through the PM, which already carries the substantive deferral-shape contract. If the heuristic proves insufficient in practice, a follow-up Issue can extend the destination-annotation contract to the wrappers without re-shaping the gate.

**Idempotency and re-run semantics.** The gate is **per-run** — the `defer-*` ledger is a session-scope TaskList state that does not survive Claude Code session handoff. Re-running a phase skill against the same Bee / Issue creates a fresh ledger; deferrals encoded during a prior run live in the durable carriers (ticket bodies, new Issues) the prior run's gate closed them out into. This is the desired behavior — persisting the ledger across sessions would defeat the close-out-into-durable-carrier purpose by re-surfacing the same items in the new session's gate.

**No agent / contract changes beyond `agents/pm.md` and `agents/analyst.md`.** No other agent role files are touched. No `## Build Commands` / `## Documentation Locations` contract keys are added or renamed. As originally shipped, `b.dgq` added no bundled helper scripts — the Encode close-out's git workflow lived as inline paired POSIX+PowerShell shell snippets in each phase skill's gate prose. That detail was superseded by the follow-up `b.5js` (see the **Deferral-hygiene Encode-commit helper** feature below), which extracted those triplicated snippets into a single bundled helper; the inline-snippet description above reflects the `b.dgq`-era design, not the current one. The bees CLI, the ticket shapes, the `reference_materials` resolver vocabulary, the Scoped-marker machinery, and the routing-trailer convention from `b.sfy` / `b.fpm` are all unchanged. Existing tickets do not require migration; the gate is invisible from the bees-state perspective.

**Decomposition.** Shipped as a single Issue (`b.dgq`) — a focused prose-and-contract fix across four `SKILL.md` files (the four phase skills), two `agents/<role>.md` files (`pm.md`, `analyst.md`), and this cumulative-doc subsection plus the corresponding cumulative-PRD subsection. No multi-Task decomposition was warranted; the TaskList convention, the four per-skill gates, and the two agent-contract additions are tightly coupled — the gates have nothing to enumerate without the convention, and the convention has no semantics without the gates closing it out; the agent contracts produce the destination annotations the convention consumes. The user-facing surface shift (a new `AskUserQuestion` gate visible at the tail of every phase-skill run when the active deferral set is non-empty) puts the change in the user-facing-feature row of `agents/doc-writer.md`'s categorization heuristic, which warrants both PRD and SDD entries — the PRD entry captures what the user sees and why, the SDD entry captures the TaskList-as-ledger substrate choice, the per-skill gate positioning, the wrapper-reviewer omission rationale, and the two agent-contract destination-annotation additions.

### Feature: Narrate-instead-of-do failure mode persists after b.fpm's prose-strengthening fix

**Architecture.** Three coupled changes carry a **structural** mitigation against the narrate-instead-of-do failure mode on top of the prose-only `b.sfy` / `b.fpm` mitigations that preceded it: (1) a new central-contract section `## The two-step TaskCreate → prescribed-tool contract` in `docs/doc-writing-guide.md` that names the two-step obligation and the `gate-<kind>-<short-suffix>` TaskList naming convention; (2) trailer-and-pre-commitment updates across seven skills (`/quo-spec-review`, `/quo-engineer-review`, `/quo-test-writer-review`, `/quo-doc-writer-review`, `/quo-write-prd`, `/quo-write-sdd`, `/quo-plan`) that wire the two-step shape into every gate-firing site; (3) a yield-control discipline added to the four consuming orchestrator skills (`/quo-plan`, `/quo-breakdown-epic`, `/quo-execute`, `/quo-fix-issue`) that reuses the `b.dgq` agent-side ledger pattern. A new `## Known limitations` section in `CONTRIBUTING.md` documents the residual failure surface the two-step contract does not close and names the harness / API mechanisms that would close it. No new skills, no new bundled helpers, no new contract keys, no new agents, no changes to the eight `agents/<role>.md` role files.

**Layer 1 — `## The two-step TaskCreate → prescribed-tool contract` central anchor.** A new section in `docs/doc-writing-guide.md` immediately after `## Review skills emit a routing trailer` (with which it composes) specifies the two-step shape that every gate-firing site must honor:

1. **First** — create a `gate-<kind>-<short-suffix>` TaskList task via `TaskCreate`. The `<kind>` segment names the prescribed tool (today `gate-askuserquestion-<short-suffix>` is the dominant form; `gate-<other-tool>-<short-suffix>` generalizes to future prescribed tools). The `<short-suffix>` is any collision-resistant suffix that disambiguates the task from any other active `gate-*` task. The task's `subject` carries the gate's identity (e.g., `Spec-review gate for Spec Bee b.abc — findings present`); `metadata.activity` carries the prescribed tool's finite choices verbatim where applicable.
2. **Then** — in the same turn, call the prescribed tool with the trailer's finite choices. The gate-task is marked `completed` immediately after the prescribed tool call returns and its result has been consumed.

The section also documents (a) the yield-control discipline (no skill yields control to the harness with active `gate-*` TaskList tasks remaining in `pending` or `in_progress` status), (b) the trailer-less-gates carve-out (orchestrator-driven gates that fire `AskUserQuestion` without a dispatched-skill trailer — Analyst-approval in `/quo-fix-issue`, plan-reviewer verdict in `/quo-plan` Step 5e, multi-Epic run-mode choice in `/quo-breakdown-epic` Section 1.5 and `/quo-execute`'s run start, deferral-hygiene close-out from `b.dgq`, etc. — also honor the contract: the orchestrator prose is the source of the prescription rather than a returned trailer, but the structural improvement applies identically), and (c) the non-duplication of `defer-*` (the `defer-*` ledger tracks inter-session deferrals on a long lifecycle; the `gate-*` ledger tracks intra-turn gate obligations; they share the TaskList substrate but are different lifecycles).

**Layer 2 — Trailer-and-pre-commitment updates across seven skills.** The four review skills' routing trailers — added by `b.sfy` and strengthened by `b.fpm` — gain a third refinement layer here: each trailer-emit site (findings-present and no-findings shapes alike) now names the two-step obligation inline, prescribing `TaskCreate` of a `gate-askuserquestion-<short-suffix>` task as the first action and the existing `AskUserQuestion` (with finite choices) or `bees update-ticket --status ready` as the second. The two spec-authoring skills (`/quo-write-prd`, `/quo-write-sdd`) carry the obligation at the post-user-approval spec-review gate (the gate that fires the dispatched `/quo-spec-review` call). `/quo-plan`'s pre-commitment lines (added by `b.fpm`) are extended with the two-step instruction so the orchestrator agent reads the obligation immediately before each `/quo-spec-review` Skill invocation, where attentional weight is easiest to recall when the Skill return lands. The trailer's substance — second-person imperative voice, counter-anchor clause, verbatim finite-choice language — is preserved verbatim from `b.fpm`; only the two-step instruction is added on top.

**Layer 3 — Yield-control discipline in the four consuming orchestrators.** The four orchestrator skills (`/quo-plan`, `/quo-breakdown-epic`, `/quo-execute`, `/quo-fix-issue`) gain a yield-control discipline that mirrors the existing `defer-*` rule from `b.dgq`: no skill yields control to the harness with active `gate-*` TaskList tasks remaining in `pending` or `in_progress` status (since the orchestrator rewrite, `/quo-execute` and `/quo-fix-issue` create no `gate-*` tasks; their equivalent is the manifest's `## Open gate` reading `none` at yield). The discipline lives at the same place each skill's `defer-*` discipline lives (the trailer-consumption sites — `/quo-plan` Step 4c and Step 5e, `/quo-breakdown-epic` Section 5, and in the two rewritten orchestrators the gate definition in their `## 6. Gates`) and references the central-contract section rather than re-deriving the rationale. The `gate-*` lifecycle is shorter than `defer-*` (created and completed within a single turn under normal operation) but the active-set rule is the same shape, so reusing the established discipline keeps the prose surface tight.

**Why this shape.** Five design decisions shape the fix:

- **Structural mitigation, not a fourth prose variant.** `b.sfy` (third-person trailer) and `b.fpm` (second-person imperative + counter-anchor + pre-commitment) shipped progressively stronger prose-only variants and continued to observe the failure mode in production traffic. The pattern of evidence establishes that the failure is a model-adherence phenomenon, not a prose-clarity phenomenon: no further prose strengthening can change the structural fact that an `AskUserQuestion` invocation can be silently yielded. The two-step contract changes the substrate: `TaskCreate` is itself a tool call, which the orchestrator cannot silently yield. A missed `gate-*` task is recoverable by next-turn TaskList processing; a silent prose yield is only recoverable by the user noticing the stall.
- **TaskList substrate reuse, not a new primitive.** TaskList tasks are already the orchestrator's native progress-tracking primitive (per-Agent invocations, per-Issue cold dispatches, per-Subtask reviews, `defer-*` ledger entries from `b.dgq`), they render live in Claude Code's UI so the user sees the active `gate-*` set briefly without typing a status command, and they support the `metadata.activity` field for carrying the prescribed tool's finite-choice text. Adding a new ledger primitive (a separate JSON file, a bees ticket sub-shape) would have introduced a parallel state surface to keep coherent across the reconciliation loop; reusing TaskList collapses the gate ledger into the existing tick semantics without new primitives, mirroring the design decision `b.dgq` made for its `defer-*` ledger.
- **`gate-<kind>-<short-suffix>` naming, parallel to `defer-<short-suffix>`.** The convention is `gate-askuserquestion-abc` rather than `gate-spec-review-blockers-present-on-spec-bee-b.xyz` because the orchestrator emits these into the Claude Code UI live during a run; a long name compresses the visible activity prefix. The `<kind>` segment names the prescribed tool (generalizing to future tools beyond `AskUserQuestion`); the `<short-suffix>` is any collision-resistant suffix. The two-segment shape parallels `b.dgq`'s `defer-<short-suffix>` convention, deliberately — the two ledgers share substrate and the parallel naming makes them visibly part of the same family in the TaskList UI.
- **Trailer-less gates also honor the contract.** Several orchestrator-driven gates fire `AskUserQuestion` without a dispatched-skill trailer prescribing it — the Analyst gate in `/quo-fix-issue` (added by `b.lwa`), the plan-reviewer verdict gate in `/quo-plan` Step 5e (added by `b.bjp`), the multi-Epic run-mode choice in `/quo-breakdown-epic` Section 1.5 and `/quo-execute`'s run start (added by `b.m7f`), the deferral-hygiene close-out in all four phase skills (added by `b.dgq`). These gates also go through the two-step contract: the orchestrator prose itself is the source of the prescription rather than a returned trailer, but the structural improvement applies identically because the susceptible step is the same (firing a single prescribed tool call). Covering both shapes uniformly avoids creating a class of gates that escape the structural mitigation.
- **Known-limitations note, not a fourth attempt at closure.** The two-step contract narrows the failure surface but does not eliminate it — the orchestrator can still fail to fire the *first* tool call (`TaskCreate`) before yielding. The narrowing is real (the second step's prescribed tool call is now structurally hard to drop because the orchestrator has already begun the two-step sequence, and a half-fired sequence is more visible than a fully-narrated yield), but residual leakage is expected. Definitive closure requires harness-level enforcement that this repo cannot author: Anthropic API `tool_choice` would force a specific tool to be called on a specific turn at the API layer; a Claude Code harness-level rule that detects "skill prose says fire X, model yielded without firing X" and re-prompts would close the failure mode at the integration layer. Both mechanisms are tracked outside this repo. The `CONTRIBUTING.md` known-limitations entry documents the b.sfy → b.fpm → b.wii evidence chain and explicitly enumerates the prose-only patterns that have been considered and rejected (more imperative trailer prefixes, layered counter-anchor clauses, additional pre-commitment lines, third-person re-framing) so future maintainers do not ship a fourth prose variant against the same problem.

**User-visible surface.** Brief, intentionally small: at the moment any orchestrator skill is about to fire a gate (an `AskUserQuestion` prompt, a `bees update-ticket --status ready` promotion), a transient `gate-*` TaskList entry appears in the Claude Code UI naming the gate, then transitions to `completed` once the prescribed tool call returns and its result has been consumed. Users who pay attention to the TaskList UI during a run will see the new entries briefly; users who don't will see no behavioral difference from the existing `b.sfy` / `b.fpm` baseline. The user-typed slash-command surfaces of every affected skill (`/quo-plan`, `/quo-breakdown-epic`, `/quo-execute`, `/quo-fix-issue`, `/quo-write-prd`, `/quo-write-sdd`, the four review skills) are byte-for-byte unchanged; no new flags, no new prompts beyond what existing gates already showed.

**No agent / role-file changes.** No agent role files (`agents/engineer.md`, `agents/test-writer.md`, `agents/doc-writer.md`, `agents/pm.md`, `agents/code-reviewer.md`, `agents/test-reviewer.md`, `agents/doc-reviewer.md`, `agents/analyst.md`) are touched. The two-step contract is a skill-to-skill prose contract between the four review skills (plus the orchestrator-driven trailer-less gates) and the orchestrator sites that consume their trailers — not an agent-side instruction. Agents continue to dispatch under the existing per-Subtask / per-Issue cold-dispatch shapes; the gates the orchestrator fires after consuming Agent output are where the contract applies. No `## Build Commands` / `## Documentation Locations` contract keys are added or renamed. No bundled helper scripts are added or modified. The bees CLI, the ticket shapes, the `reference_materials` resolver vocabulary, the Scoped-marker machinery, the routing-trailer convention from `b.sfy` / `b.fpm`, and the `defer-*` ledger convention from `b.dgq` are all unchanged.

**No README change.** The user-typed slash-command surfaces of every affected skill are byte-for-byte unchanged, and the README skill-table rows describe what each skill does at a user-visible level that this fix does not shift. The two-step contract is an internal substrate-level mitigation against a model-adherence failure mode — not user-visible CLI behavior — and is not surfaced in the README skill catalog. The brief `gate-*` TaskList entries the user may see during a run are a natural extension of the existing TaskList progress UI rather than a new surface to document at the catalog level.

**Decomposition.** Shipped as a single Issue (`b.wii`) — a prose-only fix across the central-contract anchor in `docs/doc-writing-guide.md`, the CLAUDE.md cross-link, seven `SKILL.md` files (the four review skills, the two spec-authoring skills, and `/quo-plan`), four orchestrator skill files for the yield-control discipline (`/quo-plan`, `/quo-breakdown-epic`, `/quo-execute`, `/quo-fix-issue`), the new `## Known limitations` section in `CONTRIBUTING.md`, and this cumulative-doc subsection plus the corresponding cumulative-PRD subsection. No multi-Task decomposition was warranted; the central-contract section, the trailer-and-pre-commitment updates, the yield-control discipline, and the known-limitations note are tightly coupled — the trailers reference the contract section, the orchestrator skills reference the contract section, and the known-limitations note explains why the structural fix is the right shape and why no fourth prose variant should be shipped on top. The user-facing surface shift (a brief `gate-*` TaskList entry visible during a run) puts the change in the user-facing-feature row of `agents/doc-writer.md`'s categorization heuristic, which warrants both PRD and SDD entries — the PRD entry captures what the user sees and why, the SDD entry captures the substrate choice, the trailer-less-gates carve-out, the agent-side ledger reuse from `b.dgq`, and the b.sfy → b.fpm → b.wii evidence-chain framing that justifies the structural-not-prose direction.

### Feature: Deferral-hygiene Encode-commit helper

**Architecture.** A single new stdlib-only Python 3 helper, `skills/quo-execute/scripts/hive_commit.py`, owned by `/quo-execute` and **sibling-resolved** by `/quo-fix-issue`, `/quo-breakdown-epic`, and `/quo-file-issue` via `..` traversal from each consuming skill's own base directory — the same owner/consumer shape `scoped_marker_resolver.py` already uses (owned by `/quo-breakdown-epic`, sibling-resolved by `/quo-execute` and `/quo-fix-issue`). It encapsulates the git workflow that closes out the **Encode in an existing ticket body** option of the `b.dgq` deferral-hygiene gate: the three phase skills' gate prose (`## 9. Deferral hygiene` in `/quo-execute` and `/quo-fix-issue`, `/quo-breakdown-epic` Section 6.5) previously each carried a ~30-line paired POSIX+PowerShell "Follow-up commit" snippet (hive-path resolution via `bees list-hives`, in-repo scoping, conditional commit on `git diff --cached --quiet`), triplicated and kept in sync by hand. The first Issue collapsed all three inline snippets into a single literal Bash invocation of the bundled helper per skill, and removed the `cb30bc5` "decompose at runtime" clarifying notes the inline-snippet form had required.

**Two roles, one shared resolver.** A follow-up consolidation refactor added a second, **non-mutating query mode** to the same helper, selected by an argparse subcommand. Both modes reuse the same `bees list-hives` parsing, repo-root resolution (`git rev-parse --show-toplevel`), and in-repo membership test (`Path.resolve()` + `Path.is_relative_to`) — that single implementation of the hive-scoping mechanics is the whole reason the consolidation was worth doing. The driving observation: the three per-ticket commit steps (`/quo-execute`'s After-Task close-out, `/quo-fix-issue`'s After-Issue close-out, `/quo-breakdown-epic` Section 6 Commit-New-Ticket-Files) each independently needed to learn the in-repo hive path to `git add` and each carried a forbidden inline `bees list-hives | python3 -c '...'` + `git rev-parse` + `case` compound-shell fragment to derive it (a CLAUDE.md "Bash etiquette" violation). Rather than re-implement the resolver a fourth time, those three steps now call the existing helper's new query mode.

**CLI contract.** The helper now exposes two subcommands.

*Encode-commit mode* (explicit subcommand `encode-commit`, also accepted bare for backward compatibility) — behavior-identical to the original helper:

`hive_commit.py [encode-commit] --skill <slug> --count <N> [--doc-path <abs-path> ...]`:

- `--skill <slug>` (required) — one of `quo-execute`, `quo-fix-issue`, `quo-breakdown-epic`; used only to build the commit subject. An unknown slug is a hard failure (exit 2).
- `--count <N>` (required, integer) — appears verbatim in the commit subject; the count of `defer-*` items the user routed to Encode in this gate firing. The helper does not derive it from git state.
- `--doc-path <abs-path>` (optional, repeatable) — a project PRD/SDD path the orchestrator already resolved from CLAUDE.md `## Documentation Locations` and routed an Encode to. Each given path must exist (exit 2 otherwise). The helper does not parse CLAUDE.md itself — the orchestrator passes resolved paths explicitly, so contract-key knowledge stays in the orchestrator and the helper stays purely git/hive-mechanical.

*Resolve-hive-paths mode* (non-mutating query):

`hive_commit.py resolve-hive-paths [--hive plans|specs|issues ...]`:

- `--hive <name>` (optional, repeatable) — one of `plans`, `specs`, `issues`. When omitted, defaults to all three, matching the encode-commit mode's resolve-all behavior. Filters the resolved hives to the named set.
- Resolves the named hive(s) via the shared `bees list-hives` + repo-root machinery, tests each for in-repo membership, and **prints each in-repo hive's absolute path to stdout, one per line**. Emit-only: it performs **no `git add`, no `git commit`, no mutation whatsoever**. Prints nothing and exits 0 when no named hive is in-repo (the out-of-repo case — the caller stages nothing). Exits 2 with a one-line stderr message on `bees list-hives` or `git rev-parse` failure, matching the encode-commit mode's failure contract.

The judgement layer — deciding which working-tree files are plausibly related to this unit of work and the explicit "**Do NOT `git add -A`**" discipline — is deliberately **not** mechanized into the helper; only the deterministic hive-path lookup moved into the query mode. This keeps the helper purely git/hive-mechanical and leaves staging judgement and per-site subject strings where they belong, in the orchestrator.

**Helper serves two roles; renamed to match.** With the query mode added, the helper serves both (a) the deferral-hygiene Encode follow-up commit and (b) per-ticket in-repo hive resolution. The helper follows the established bundled-helper precedent set by `detect_fast_path.py` and `scoped_marker_resolver.py` — stdlib-only Python 3, cross-platform via `pathlib`, single executable file, exit-2-on-hard-failure with a single human-readable stderr line.

### Feature: Depth-aware finding routing and compromise tracking in /quo-fix-issue and /quo-execute

**Architecture.** This feature lands in two phases against the review-finding pipeline. **Phase 1 (emission enrichment)** extends the reviewer output contract so each finding carries, in addition to its existing severity tag (`blocker` / `suggestion` / `nit`), a **depth tag per enumerated fix path** (`trivial-tweak` / `refactor-locally` / `re-architect`) and the full set of fix paths the reviewer sees rather than a single collapsed path. The four review skills (`/quo-engineer-review`, `/quo-doc-writer-review`, `/quo-test-writer-review`, `/quo-spec-review`) and `/quo-plan` Step 5e's plan-review dispatch emit this enriched shape; the three reviewer-wrapper subagents (`agents/code-reviewer.md`, `agents/doc-reviewer.md`, `agents/test-reviewer.md`) name the depth dimension in their structured-output bullets and defer the concrete shape to the wrapped skill. **Phase 2 (routing + tracker + post-completion reframe)** lands in the two execution orchestrators (`/quo-fix-issue`, `/quo-execute`), which are the consumers of in-flow reviewer findings against a landing diff.

**Routing-table contract.** Each orchestrator gains an "Orchestrator discipline: routing review findings" section whose centerpiece is a deterministic table mapping the `(number-of-fix-paths, maximum-depth-across-paths)` tuple to exactly one routing decision — no tuple maps to two:

```
| Number of fix paths | Maximum depth across paths | Orchestrator routing                         |
|---------------------|----------------------------|----------------------------------------------|
| 1                   | trivial-tweak              | Auto-dispatch the implementer with the fix   |
| 1                   | refactor-locally           | Auto-dispatch the implementer with the fix   |
| 1                   | re-architect               | User gate before dispatching                 |
| > 1                 | (any)                      | User gate before dispatching                 |
```

The orchestrator reads the reviewer-emitted tags and consults the table — it does NOT invent its own classification. "Auto-dispatch" dispatches a fresh ephemeral implementer Agent (Engineer / Test Writer / Doc Writer, per the finding's lane) with the single low-depth fix and no user gate; "User gate before dispatching" fires the **routing-decision gate** first. The section is structured as labeled parts (a) routing table, (b) anti-pattern callout, (c) scope-bounding gate, (d) routing-decision gate, (e) backwards-compatibility shim, (f) edge-case handling.

**The routing key above was superseded by `b.nn8`** (see the **Routing table gates every multi-path finding; default to orchestrator picking the highest-quality path, gate only re-architect/scope** feature below). The `(number-of-fix-paths, maximum-depth-across-paths)` tuple is no longer the routing input: part (a) became a two-step **pick-then-route** procedure in which the orchestrator first chooses the highest-quality fix path and then evaluates a six-row first-match-wins condition list against **that chosen path**. Path count dropped out of routing entirely — a multi-path finding no longer gates by virtue of being multi-path. The labelled parts (a)–(f) survive under the same letters and (g), added by `b.pdq`, is unchanged in scope; but the tuple table, the word "auto-dispatch", and the "single low-depth fix" framing above describe the `b.ut9`-era design, not the current one. **The unqualified "it does NOT invent its own classification" claim above survives intact.** Step 1's pick is always one of the paths the reviewer enumerated, so no emitted tag is ever overwritten and the orchestrator never supplies a depth of its own.

**Anti-pattern callout + scope-bounding gate.** Part (b) forbids inlining scope-bounding directives (`"out of scope for this issue"`, `"out of scope for <id>"`, `"prefer option (a)"` / `"prefer (a)"`, and close paraphrases) into a re-dispatched implementer's prompt, because that silently narrows the fix without the user seeing the decision. The behavior that REPLACES the forbidden directives is part (c)'s **scope-bounding gate**: a three-choice `AskUserQuestion` (`Fix properly now` / `Defer to follow-up Issue` / `Accept the limitation`) carrying the finding verbatim plus a one-line "why this gate is firing" context line. There is deliberately **no `Cancel`** at this gate (a per-finding `Cancel` would be ambiguous; `Ctrl-C` remains run-level abort). The **routing-decision gate** in part (d) presents one choice per reviewer-surfaced fix path (each labeled with its depth tag; `(Recommended)` only when the reviewer expressed a preference) plus `Defer to follow-up Issue` and `Cancel` (which aborts the current Issue's fix run in `/quo-fix-issue`, proceeding to the next Issue in batch/`all` mode, or the current Task's execution in `/quo-execute`, not the whole run — `Ctrl-C` remains the run-level abort). Both gates fire through the established two-step `TaskCreate` → `AskUserQuestion` contract.

**`Cancel`'s semantics were superseded by `b.nn8`.** That choice no longer exits on its own terms: it routes through the shared aborted-unit close-out each skill gained in `b.pdq`, and the close-out — not `Cancel` — decides the run's fate. The "proceeding to the next Issue" clause is now wrong in `/quo-fix-issue` batch mode with Issues remaining (the close-out **stops the run**, because the aborted Issue's edits are uncommitted), and "not the whole run" is now wrong in `/quo-execute` (its close-out is always run-ending). Both gates' choice sets also became **severity-aware** in the same change — a `blocker` can never be accepted at either gate, and can be deferred only paired with a narrowing that still covers the unit's stated defect. **The "deliberately no `Cancel`" rule above is now qualified in `/quo-execute`**: that skill offers `Cancel` in a `blocker`'s scope-gate choice set (it has no Analyst to re-dispatch), while withholding it from the `suggestion` / `nit` set on the original reasoning. `/quo-fix-issue`'s gate (c) still carries no `Cancel` at any severity. **The `(Recommended)` marker rule was superseded too:** "only when the reviewer expressed a preference" no longer describes it. The marker now goes on the path the orchestrator itself chose at Step 1 — the gate asks the user to ratify or override a pick already made — and the reviewer's `[preferred]` is only an input to that pick, so when the two diverge the marker names the fuller path and the choice's description states the divergence. Two cases leave **no path marked**: a row-1 entry (no depth tag, or a malformed one), where no Step-1 pick was possible, and a `blocker` whose Defer branch is open, where the marker goes to `Defer` alone. See the `b.nn8` feature below.

**Backwards-compatibility shim + edge cases.** Part (e)'s shim routes any finding emitted **without** a depth tag — a legacy reviewer emission during rollout, or a hand-authored finding from a future call site — as if it carried `re-architect` depth, i.e., to the user gate; the shim errs toward user input whenever depth is unknown. Part (f) extends the same `re-architect`-treatment to malformed tags (a severity tag not exactly `blocker`/`suggestion`/`nit`, or a depth tag not exactly `trivial-tweak`/`refactor-locally`/`re-architect`) AND surfaces the parse failure to the user so the emission can be corrected.

**Session-scoped compromise tracker.** A new per-run scratch file at `<tempdir>/.quorum/compromises-<YYYYMMDD-HHMM>-<short-suffix>.md` (`/tmp/.quorum/...` on POSIX, `%TEMP%\.quorum\...` on Windows) accumulates one `## Compromise <n>` entry per accepted compromise across the whole single/list/`all`-mode run. `<n>` is a 1-based counter scoped to the run's tracker file, not a global identifier. The path is generated once at run start and follows the repo scratch-file convention (under `<tempdir>/.quorum/`, created if absent, never deleted by skill prose). Each entry's canonical shape carries (at minimum) a `Decision:` field naming how the compromise was reached — `User picked path (a|b|...)`, `User picked Defer to follow-up Issue`, `User picked Accept the limitation`, `Auto-routed (a) per single-path refactor-locally rule`, `User overrode auto-route after post-completion challenge (depth misjudgment)`, `User accepted under-enumeration after post-completion challenge` — plus a `Follow-up Issue` field that can be updated in place.

**One enum value was superseded by `b.nn8`, one-in-one-out:** `Auto-routed (a) per single-path refactor-locally rule` is retired and replaced by **`Orchestrator picked path (x) — highest-quality`**, where `(x)` is the chosen path's letter. The retired value named a rule that no longer exists (there is no single-path auto-route to name), and the entry's `Rationale` correspondingly stopped being the rule's name and became the orchestrator's own one-line reason for preferring that path. The other five values are unchanged. See the `b.nn8` feature below for why both values were not kept.

**Four append triggers.** Exactly four moments append to the tracker. Triggers A–C fire from the routing-findings section's gates / auto-dispatch: Trigger A from the scope-bounding gate's `Defer to follow-up Issue` branch, Trigger B from the scope-bounding gate's `Accept the limitation` branch, and Trigger C from the `(1, refactor-locally)` single-path auto-route (no gate — wired into the auto-dispatch step itself). Trigger D fires from the post-completion review's recovery gates (SR-6.7 + SR-4.6). There is deliberately **no** append trigger on the routing-decision gate (part (d)). Each trigger anchors to its gate by name so the write fires from the correct branch.

**Two of the firing sites above were superseded by `b.nn8`; the count of four was not.** Trigger C is now "ungated route (the orchestrator's own path pick)" and fires from the pick-then-route table's **row 6** rather than from a `(1, refactor-locally)` auto-route — row 6 is its only firing site, in both skills alike. Trigger A is retitled "**Defer to follow-up Issue at either gate**" and gained a **second** firing site: the routing-decision gate's own `Defer to follow-up Issue` branch, at **every** severity — unconditionally on a `suggestion` or `nit`, and on a `blocker` only where the Defer-with-narrowing branch is open. So the single-gate anchoring above ("Trigger A from the scope-bounding gate's `Defer` branch") and the "deliberately **no** append trigger on the routing-decision gate" statement are both superseded — a deferral taken at part (d) is recorded exactly as one taken at part (c), same terms, same entry shape. No trigger was added: "four append triggers A/B/C/D" still holds. Trigger B additionally became **unreachable for `blocker`-severity findings**, and Trigger A reachable for one only on the Defer-with-narrowing branch, at either gate. See the `b.nn8` feature below.

**Accepted-compromises summary surface.** The end-of-run summary block gains an **Accepted compromises** surface, rendered by `Read`-ing the tracker file at its run-start path (no shell needed to locate or test it). The surface is **omitted entirely** — no empty heading, no `N/A`, no placeholder — when the file is absent (the common case) or present-but-empty; the two states are treated identically.

**"The common case" was superseded by `b.nn8`.** With an ungated orchestrator path pick appending a Trigger C entry — every one except the lone-`trivial-tweak` carve-out — an absent or empty tracker is now the *uncommon* state — most runs that route any multi-path finding render the surface. The omit-when-empty rule itself is unchanged; only the expectation about how often it fires. The same correction was applied to both execution skills' render steps and to their boundary-checkpoint tracker-absent notes. When entries exist they are surfaced ALL in full with no truncation, summarization, or elision even past ~10 entries (with a short volume prologue in that case), because preserving the signal is the tracker's whole purpose.

**Post-completion review reframe.** The orchestrators' post-completion review (`## 11. Post-completion review` in both) is reordered to **lead with consuming the compromise tracker** (passed to the reviewer as a file path) and challenging each tracked compromise on its merits before the discrete-defect sweep. Two depth-aware plausibility checks are added: an **SR-4.5 / SR-6.7 depth-misjudgment** check that re-evaluates whether an auto-routed `(1, refactor-locally)` fix was truly shallow enough to skip the user gate, emitting a `[compromise-challenge]` finding when the true depth looks like `re-architect`; and an **SR-4.6 under-enumeration** check that re-evaluates whether the reviewer enumerated all available fix paths. Each landed challenge fires a three-choice recovery gate — **SR-6.7** (depth) and **SR-4.6** (under-enumeration) share the gate shape with relabeled choices, but the `File follow-up Issue` branch behaves differently between them: for **SR-6.7**, it updates the ORIGINAL Trigger C tracker entry's `Follow-up Issue` field **in place** (NO new entry, since the depth misjudgment concerns a path that was already surfaced + auto-routed, so an originating Trigger C entry always exists to amend); for **SR-4.6**, it generally **appends a NEW entry** via the Trigger D mechanism, because under-enumeration concerns a path the in-flow reviewer never surfaced (so there is usually no originating Trigger C entry — it updates in place only when one exists). The `append explicit-override tracker entry` choice writes a new entry via the Trigger D mechanism; `pause-and-resume` defers. Gates fire per challenged finding (non-aggregated) in reviewer emission order.

**The depth check's scope was widened by `b.nn8`.** The phase it lives in no longer keys on auto-routed `(1, refactor-locally)` decisions — it evaluates **every** `Orchestrator picked path (<letter>) — highest-quality` tracker entry, on **two** axes: the depth-plausibility axis described above, and a second axis asking whether the chosen path introduced a mechanism that should have been deferred or gated rather than built. SR-6.7 was renamed the **ungated-route recovery gate** and widened to cover both axes; its three choice labels and Trigger D's `Decision` string are unchanged byte-for-byte, and are read generically across the two axes rather than as depth-only. A third challenge class was added at the same time — an accepted or improperly-deferred `blocker` recorded in the tracker, emitted at `blocker` severity — which deliberately has **no** recovery gate. See the `b.nn8` feature below.

**Dispatch-prompt rewrites.** The implementer-Agent dispatch prompts in both orchestrators are rewritten so the routing decision (auto-dispatch vs. gated) and any scope-bound flow through the section above rather than through inlined prose directives, and the post-completion reviewer dispatch prompt is restructured into explicit phases (consume tracker → challenge each compromise → depth/under-enumeration plausibility checks → holistic solution-quality judgment) with the tracker file path embedded.

The new interactive gates, the compromise tracker, and the Accepted-compromises summary are user-observable, so a PRD entry is warranted; the routing-table contract, the depth-emission contract, the tracker file convention and entry shape, the four append triggers, the post-completion reframe, and the dispatch-prompt rewrites are architecture, so this SDD entry is warranted. ### Feature: Pin reasoning effort per role; drop the Sonnet downgrade prompt

**Architecture.** Reasoning effort becomes a per-role property expressed in artifact rather than a single session-wide dial the operator sets before knowing what the run contains. Three moves carry the change: an `effort` key added to all eight `agents/<role>.md` frontmatter blocks, deletion of the run-start "pick Opus or Sonnet for support roles" prompt from the three skills that carried it, and reuse of that prompt's slot for a **conditional session-effort gate**. Model assignment itself is unchanged — every role file was already `model: opus` and stays that way; what disappears is the runtime path that could downgrade three of them.

**Pinned tiers.** The per-role table is authoritative in CLAUDE.md `## Model assignment in execution skills` (pointed to from `## Model assignment in execution skills` above); the tiers themselves are not restated here. The tiering rule is that any role producing or reviewing work runs at `high` minimum, and the two adversarial roles — the one diagnosing root cause before implementation, and the one hunting for what no test covers — run one tier higher. Two non-cost reasons set the ceiling below `xhigh`-everywhere: effort helps most on open-ended search and diagnosis and least on well-specified mechanical work, where it pushes toward over-elaboration; and `xhigh` across eight roles times N Subtasks is a substantial wall-clock cost that is not token spend. The **reviewer invariant** (never pin a reviewer below the role it reviews) constrains any future retune and is recorded alongside the table in CLAUDE.md.

**Override, not cap — an accepted consequence.** Subagent frontmatter `effort` *overrides* the session effort rather than capping it (the default being inherit-from-session), which makes the pins deterministic regardless of how the operator launched. The accepted trade-off is that an operator running a session above `high` sees six of the eight roles *lowered* to `high` once the pins land. Rebasing the whole table upward onto the `max` tier to avoid that was considered and rejected on wall-clock grounds: the tiering rationale holds independently of any individual operator's launch flags, and a per-role table calibrated to one operator's session is not a per-role table. The two roles where reasoning depth pays off most sit above the default either way.

**Deleted: the run-start Opus/Sonnet prompt.** The prompt at the top of `/quo-execute`, `/quo-fix-issue`, and `/quo-breakdown-epic` asked the operator to downgrade "support roles" (Doc Writer, PM, Doc Reviewer) to Sonnet. It is removed along with every downstream reference to the operator's choice, including the `## Model default and runtime override` section in `agents/doc-writer.md`, `agents/pm.md`, and `agents/doc-reviewer.md` — those sections documented the override mechanism itself, so they are deleted entirely rather than edited, and the `model: opus` they described becomes unconditional. Removing the prompt closes a footgun as much as a cost lever: the "support roles" grouping is not cognitively coherent (the PM is a review gate, the Doc Writer is fan-out), so a cost-conscious operator downgrading the group was downgrading a gate without realizing it, and the question arrived at time zero before anyone knew whether the run was trivial or gnarly.

**Conditional session-effort gate (the reused slot).** The same three skills read the operator's current session effort from the `CLAUDE_EFFORT` environment variable via a single literal Bash call and compare it against **that skill's own floor** — `medium` for `/quo-execute` and `/quo-fix-issue` (the orchestrator row: it delegates all implementation rather than producing work, and holds the longest context in the run), `high` for `/quo-breakdown-epic` (the planning row: tiny fan-out, maximal blast radius, errors propagating into every downstream Epic). Design properties that make the gate cheap enough to keep:

- **Floor comparison, not equality.** Only a session strictly *below* the floor fires the gate; at-or-above is silent — no prompt, no output. An operator running hotter than the recommendation is spending wall-clock, not quality, and prompting them is exactly the gate fatigue this design avoids. Ordering is `low` < `medium` < `high` < `xhigh` < `max`.
- **Unset skips the gate.** When `CLAUDE_EFFORT` is absent (older CLI, or a launch path that does not export it), the gate is skipped rather than fired: a spurious prompt on every run is worse than a missed advisory. The variable is populated from resolved session state — it tracks a mid-session `/model` change and is present without an explicit `--effort` flag — so unset is not expected to be the common case.
- **Per-skill rationale line.** The gate body names the current effort, the floor, and a rationale that differs per skill; `/quo-breakdown-epic` dispatches no implementers, so the orchestrator framing is wrong for it. The body also states that subagent effort is pinned per role and unaffected by the setting, so the operator does not conclude the pins are at risk.
- **Two options only** — proceed anyway, or exit cleanly to run `/model` and re-invoke. The skill cannot change the session setting itself. The gate is orchestrator-fired and therefore inherits the two-step `TaskCreate` → `AskUserQuestion` contract.
- **Net gate count is flat.** The rule is to repurpose existing run-start prompt slots and never add new ones. `/quo-plan`, `/quo-status`, and `/quo-file-issue` have no such slot and must not gain one — gating a short skill on a model advisory costs more than the problem it solves. Those skills stay README-documented.

**Advisory surface.** The recommended session settings remain a recommendation the operator applies, and two routes to making them enforceable were rejected:

- **Writing effort into the user's `.claude/settings.json`.** Rejected: quorum's install surface is the skills and agent files it ships and owns, `settings.json` holds the user's permissions, env vars, and hooks, and there is direct precedent for the failure mode (the `## Skill Paths` section of per-machine paths removed at `b.963`).
- **Pinning `effort` in the skills' own frontmatter.** Rejected on semantics, not on reach — this one *is* inside quorum's install surface, and the command/skill frontmatter schema does carry an `effort` key, so a skill could set it declaratively. But frontmatter `effort` is an **override, not a cap**: pinning `effort: medium` on `/quo-execute` would force `medium` on an operator who deliberately launched at `xhigh`, silently downgrading them. What the advisory needs is a **floor** — "at least `medium`; say nothing if you are already above it" — and a floor is not expressible as an override. That is precisely why the gate compares the session value against a floor rather than setting it, and why "the repo cannot enforce this" should be read as "the repo cannot enforce a *floor*," not as an absence of any lever. A future reader with the CLI schema open should not mistake the gate for an oversight.

The README's session-settings section is therefore the durable carrier, and it is the *only* user-visible carrier for the five user-invoked skills that deliberately do not receive the gate. The three orchestrator-only reviewers are out of the table's scope entirely — they never run as the operator's session.

**`xhigh` availability on Opus — confirmed at implementation time.** The Issue body carried an explicit instruction to confirm that `xhigh` resolves on Opus before shipping the two `xhigh` pins. ### Feature: Epic-boundary context-clear discipline instructs an unexecutable action; rewrite as state-externalization + run-state manifest

**Architecture.** The three orchestrator skills previously carried (in `/quo-execute`) or lacked entirely (in `/quo-breakdown-epic` Mode 2 and `/quo-fix-issue` batch mode) a boundary discipline built on an action the model cannot perform — clearing its own context. The rewrite replaces it with a **state-externalization checkpoint** at every unit boundary, backed by a new **run-state manifest** on disk and a **post-compaction reconciliation rule** in each skill's reconciliation loop. Nothing about the orchestration shape changes: the reconciliation loop, the cold-dispatch pattern, the review cycles, and every gate are untouched. What changes is that the boundary discipline now names actions the orchestrator can actually take — run a bees query, walk the TaskList, read a file, write a file — and that the honest owner of token reclamation (the harness, and the user's fresh-session choice) is stated rather than implied to be the skill.

**The checkpoint.** Two named anchors, one per scope, defined once and referenced by name everywhere else:

- **Epic-boundary state-externalization checkpoint** — defined in two places, `skills/quo-execute/SKILL.md`'s per-unit close-out and `skills/quo-breakdown-epic/SKILL.md` Section 7. In both, **every** exit path runs it; neither conditions it on the captured run mode, on a menu answer, or on whether the run continues in this session.
  - In `/quo-execute`, the Epic boundary enumerates the five paths that invoke it by name: branch 2's Mode 1 **accept** path and its Mode 2 auto-continue path (each recording the next Epic's ID as the next unit), branch 2's Mode 1 **decline** path, branch 1's exit for breakdown work, and branch 3's exit to final Bee review (the last three recording `none`). The three `none` paths run it in full rather than skipping it: the run is ending in this session either way, and what the checkpoint verifies and writes is exactly what has to outlive the conversation.
  - In `/quo-breakdown-epic`, it is hoisted to the end of Section 7 and run **unconditionally, as the last thing that section does** — after the menu answer is consumed on every menu-rendering path (Mode 1, and the Mode 2 cases that still render the menu), or immediately after the auto-continue note on the Mode 2 case that skips the menu — including the paths where the run ends there, which run it identically with `none` as the next unit. Being unconditional removes the need to work out which case is in play before deciding whether to run it. An earlier revision gated it on the Mode 2 auto-continue path alone, on the since-falsified premise that this was the only path crossing an Epic boundary without leaving the session; the menu's own fresh-session option explicitly blesses same-session continuation, and the run-ending paths are precisely the ones whose state most needs externalizing.
- **Issue-boundary state-externalization checkpoint** — `skills/quo-fix-issue/SKILL.md`'s Issue boundary, after the deferral-hygiene gate and before the next Issue starts. This closes the gap where `all`/list mode previously declared that "no inter-issue cleanup ceremony is needed" and carried no boundary discipline of any kind.

Each checkpoint is three steps: (1) **verify the carriers** — re-query bees for the just-completed unit's statuses, confirm the per-unit commits landed, `Read` the compromise tracker, walk the lane and obligation ledger — and fix any gap *now* rather than carrying it in conversation; (2) **rewrite the run-state manifest**; (3) **re-derive from here on** — treat the prior unit's conversation as non-authoritative and read every fact the next unit needs fresh from the carriers. The durable carrier set is bees ticket statuses, git commits, the session-scoped compromise tracker (execution skills only — `/quo-breakdown-epic` has none and says so explicitly), the `defer-*` ledger (the TaskList in `/quo-breakdown-epic`; since the orchestrator rewrite, the manifest's `## Obligations` in the two execution skills), and the run-state manifest. Each checkpoint closes with an explicit **what this checkpoint does not do** paragraph: it does not clear, compact, or reclaim context and must never be narrated as if it did.

**Run-state manifest.** A small markdown file under the standard scratch-file convention (`<tempdir>/.quorum/`, `/tmp/.quorum/` on POSIX and `%TEMP%\.quorum` on Windows, created if absent, never deleted), authored with the `Write` tool rather than a shell redirect, with paired POSIX / PowerShell `mkdir` snippets at each definition site. It holds **only the run-scoped values that live nowhere else on disk** — the captured multi-Epic run mode (`/quo-execute` and `/quo-breakdown-epic` only, a user choice with no re-derivation path; `/quo-fix-issue` is Issue-scoped and never fires the multi-Epic gate, so it carries no run-mode field), the unit scope, the run-start SHA, per-unit progress, and the next unit, plus — in the execution skills only — the isolation strategy and the compromise-tracker path including its random suffix (`/quo-breakdown-epic` has no tracker and carries neither field). In `/quo-execute` the run-start write is two-phase, because neither the run mode nor the Epic set is known when run-start step 5 writes the file: that first write emits the literal placeholders `not captured` and `pending Section 4 query` (both listed in the manifest template as first-write-only legal values), and run-start step 8's two-field refresh (formerly `#### Resolve the manifest placeholders`) step rewrites them unconditionally on all three paths through the mode gate, so neither literal survives into any Epic's work. The run-start SHA is named per skill: `Pre-Bee SHA` in `/quo-execute`, `Pre-session SHA` in `/quo-fix-issue`, `Pre-run SHA` in `/quo-breakdown-epic`. Each of the three has a concrete reader, so none is write-only bookkeeping: `/quo-execute`'s and `/quo-breakdown-epic`'s are read back at their Epic-boundary checkpoints as the lower bound for the `git log` that confirms the unit's commits landed (in `/quo-execute` at the first boundary, where no prior Epic's `last commit <sha>` exists to use instead), and `/quo-fix-issue`'s bounds its post-completion review diff and its per-issue commit-SHA lookups. `/quo-fix-issue` additionally records the ordered Issue batch, which is user-supplied, intentional, and unrecoverable from bees. An explicit invariant bounds the contents: nothing already readable from bees, git, the tracker, or the TaskList goes in, so the manifest cannot grow into a shadow ticket store that drifts. Semantics are **live snapshot, not accumulating log** — truncate-and-rewrite at run start and at every boundary.

**Deterministic filename — the load-bearing choice.** Every manifest filename is deterministic: **no random suffix, no timestamp**, deliberately unlike the compromise tracker's `compromises-<YYYYMMDD-HHMM>-<short-suffix>.md`. The difference follows from who reads the file — the tracker's reader is a dispatched Agent handed the path in its prompt, while the manifest's reader is the orchestrator itself, possibly *after* a compaction that dropped the path from the conversation, so a randomly-suffixed path would be unfindable exactly when the manifest is needed most.

**Every key leads with the skill's own name**, and that segment is not decorative: `/quo-execute` and `/quo-breakdown-epic` key on the *same* Bee ID, so without it a `/quo-execute` run started against a Bee whose `/quo-breakdown-epic` session is still live would truncate that session's manifest out from under it — exactly the sequence `/quo-breakdown-epic`'s *"In a fresh session, execute this Epic first; defer downstream breakdown"* menu option invites. **What follows the skill name differs by skill**, because "the most re-derivable discriminator this run has" resolves differently in each:

- `/quo-execute` — `run-state-quo-execute-<bee-id>.md`. The Bee ID is the run's argument and the ancestor of every ticket the run touches, so one bees call recovers it from any in-flight Plans-hive ticket.
- `/quo-breakdown-epic` — `run-state-quo-breakdown-epic-<unit-id>.md`, with an explicit two-step resolution order that writer and reader apply identically: the parent **Bee ID** first (`run-state-quo-breakdown-epic-<bee-id>.md`, the key on every normal invocation), falling back to the **Epic ID** (`run-state-quo-breakdown-epic-<epic-id>.md`) only when no parent Bee resolves at all. Because the order is deterministic, the manifest needs no field recording which key was used.
- `/quo-fix-issue` — `run-state-quo-fix-issue-<repo-dir-name>.md`, keyed on this skill's own name plus the basename of the working-tree root (`git rev-parse --show-toplevel`).

**Why the asymmetry.** A unit-ID key is only viable when the ID is re-derivable without the conversation. That holds for the two Plans-hive skills — a Bee or Epic ID is one Plan-Bee lookup away — and fails for `/quo-fix-issue`, whose natural unit-ID candidate is the batch's first Issue: batch membership and ordering are user-supplied and are recorded *inside this manifest*, so keying on that ID would make the path depend on a value recoverable only by reading the very file the path points at, and it is not recoverable from the run's commit subjects either (those name whichever Issues are already fixed, not which one started the batch). A skill-identity key sidesteps that but, unlike a ticket ID, is not self-discriminating — ticket IDs are minted per bees workspace so separate projects do not normally collide, whereas the literal string `quo-fix-issue` would collide across every repo sharing the machine-wide `<tempdir>/.quorum/` — which is why it carries the repo-directory segment. That segment restores only *normal* cross-project discrimination, not a guarantee: two checkouts whose directories share a basename land on one file. Each skill's SKILL.md states this rationale at its own manifest definition site.

All three keys make the same knowing trade against the scratch-file convention's collision-resistance guidance: two concurrent runs sharing a key (the same Bee/Epic, or the same working directory) already collide destructively over ticket statuses and commits, so it is not a case the workflow supports. `/quo-fix-issue` documents a **second** knowingly-accepted trade its siblings do not have, arising from the same-basename case above: a concurrently-live run in a same-named checkout truncates the manifest, and the concrete consequence is the other checkout's **Pre-session SHA** — a SHA that need not even exist in this repository — reaching the post-completion review and mis-scoping its diff. Sequential runs in such checkouts are harmless (each truncates at run start), the alternative keys are worse (an absolute path is unwieldy and leaks directory structure into `<tempdir>`; an Issue ID is not recomputable at all), and the failure is detectable — a manifest whose Issue batch does not match the run in hand is the tell, and a reader that spots it recovers by ignoring the manifest and taking the same `HEAD~N` fallback Section 8 already defines for a missing one.

**Post-compaction recovery.** Each skill's reconciliation-loop "read state" step gains the manifest as a further source alongside bees and a source that differs by skill (the TaskList remains a read-state source only in `/quo-breakdown-epic`) — git state in the two execution skills, the returned research findings in `/quo-breakdown-epic` — plus two rules shared by all three. The unconditional one: conversation memory is never a substitute for those sources — whatever the orchestrator believes it remembers about ticket status, landed commits, the captured mode, or the pre-run SHA, the sources are the truth and are re-read rather than recalled, on every tick. The conditional one, for the observable case: if a summarization marker is visible in the conversation, treat everything before it as non-authoritative and re-read all sources in full before dispatching anything. `/quo-fix-issue` carries a third, skill-specific rule for the one value with no durable carrier by design: the Analyst gate's approved Design Proposal lives only in the Analyst's returned message. The rule is **functional, not positional** — it is not a window between two points in the run. Whenever the proposal is needed for an Issue (any Engineer dispatch including a Phase C re-entry round, the Phase A Code Reviewer relay, the Phase C PM relay, a re-run of any of these, or the Analyst gate itself standing open on a proposal no reader can see) and it is no longer readable, the orchestrator **re-derives it through the Analyst** and never reconstructs it from a summary. Three branches followed from the TaskList as shipped (since the orchestrator rewrite the same branches key on the manifest's `## Lanes` analyst row and `## Open gate`): an active `analyst-<issue-id>` task (prefix-matched, so `-rev<n>` names are caught) means that re-derivation is already in flight, so wait for it and run the Analyst gate on its return — unless that task is `pending` with no dispatch landed (or none confirmable after the compaction), which is a stranded task no completion notification will ever clear, in which case the Analyst is dispatched now under that same task name using the re-derivation shape below and the wait is on *that* return; otherwise an active Analyst-gate `gate-*` task for the Issue is marked `completed` with the abandonment noted in `metadata.activity` — informational, never a routing input — and the Analyst is re-dispatched; otherwise the Analyst is re-dispatched directly. Every re-dispatch uses the same **re-derivation shape**: the Issue body re-read from bees with the original `reference_materials`, the changed-file list of what is already on disk (an empty list being itself informative), and an explicit statement that the prior proposal was lost — or, when the stranded task is the first Analyst pass under the undiscriminated name, that no proposal has been produced yet — so the Analyst re-derives the design from the codebase and covers the tree as it stands. Because the proposal is re-derived *before* the dispatch that needs it, there is no path in fix mode on which a downstream `## Blast radius` relay heading is omitted for want of a proposal. No manifest field was added: the value is re-derivable, which is the manifest's own admission test.

**False claims corrected.** Four stale assertions travelled with the original defect and were fixed in the same pass: `/quo-execute`'s then-Section 3 claim that flat orchestration is bounded because the skill "clears the orchestrator's context window between Epics" (rewritten to state monotonic in-session growth, harness-owned reclamation, and the checkpoint as the survivability guarantee); the Mode-2 option text in `/quo-execute`'s run-mode gate and the mirrored claims in this SDD and the PRD, which listed the boundary discipline as one of Mode 2's *pauses* (it is neither a pause nor a clear — Mode 2 still *performs* the checkpoint, which is a set of verify-and-write steps that never prompt the user); the "~25-30% of the 1M context window per Epic" budget, retained only as an **unverified working estimate carried over from this discipline's original design note** — no measurement of it exists and nothing in these skills produces one, so it must not be called observed, measured, or benchmarked; it is recorded solely to give downstream tooling a starting number to size against, with an explicit note that the orchestrator cannot read its own token usage and must not gate any branch on one; and `/quo-breakdown-epic`'s claim that returning at Section 7 "releases the orchestrator's working context back to the caller's session" (skills load inline, so returning releases nothing — what bounds growth is the per-Epic scope of the loop and the fresh-session recommendation).

**Generalized as a review criterion.** The case produced the **executable-verb test**, added to CLAUDE.md `## Review criteria for skill changes` alongside the three design rules and the scratch-file convention: every instruction in skill prose must name an action the model can actually take, and prose that *describes* an unavailable mechanism as something the skill does is the same defect in declarative form. The upstream mechanism-availability finding is recorded in `CONTRIBUTING.md` `## Known limitations` as the audit trail, cross-referencing Issue `b.cj2` as the periodic re-probe carrier. Those version-dependent specifics live only there, deliberately — skill-adjacent design prose says just that the harness compacts automatically once the window fills, so a threshold change upstream does not strand stale numbers across four documents.

**Design-philosophy fit.** The replacement matches the preference stated in `## Orchestration in execution skills` above, where hub-and-spoke is achieved through a substrate that does not permit peer comms rather than through a rule the model can drop. A self-clear instruction is the extreme case of a droppable rule — it cannot be executed at all, so the only available compliance is narration. The checkpoint is a set of file reads, bees queries, and file writes; the manifest is a substrate artifact that survives whatever the conversation does not.

**No agent / contract changes.** No agent role files are touched — boundary discipline is orchestrator-scoped and no subagent spans a unit boundary. No `## Build Commands` / `## Documentation Locations` contract keys are added or renamed, no bundled helper scripts are added or modified, and no ticket shapes change. Existing Plan Bees, Epics, and Issues need no migration; the manifest is created at run start, and the two post-completion-review sites that read a prior value back — `/quo-execute`'s `<pre-bee-sha>` lookup and `/quo-fix-issue`'s `<pre-session-sha>` lookup — each document an absent-manifest fallback (a commit-count-derived `HEAD~N`). The checkpoint-side read-backs carry no such fallback: they run inside a run that wrote the manifest at its own start.

**Minimal README change.** The scratch-file section already documents `<tempdir>/.quorum/` generically as the home for transient skill artifacts, and the manifest is one more artifact type under a convention the README already describes; no user-typed invocation surface, flag, or prompt changes. One claim in that section did need narrowing: "safe to delete anytime — skills recreate it on demand" held while the directory carried only regenerable `--body-file` payloads, but the manifest is the sole durable home for the captured run mode and `/quo-fix-issue`'s ordered Issue batch, neither of which is re-derivable. The section now says *safe to delete between runs* and names the mid-run exception.

### Feature: Installed skills reference docs that never ship; pick a reference architecture

**Architecture.** The install procedure copies only `skills/*` and `agents/*` into a user's project; `docs/*`, `CONTRIBUTING.md`, and this repo's own `CLAUDE.md` never ship. Shipped artifacts (`skills/*/SKILL.md`, `agents/*.md`, bundled helper scripts) that cited those repo-only carriers therefore left **dangling cross-repo references** on a fresh install — a citation tail pointing at a doc the installed user does not have. This Issue picks the reference architecture for that boundary and applies it as a portability sweep. The choice among the candidate architectures turned on a finding from the diff itself: the cited content was already **inlined at each shipped site**, so the reference was carrying *provenance* ("this rule also lives in the doc that authored it"), not *dependency* ("go read the doc to know what to do"). That finding is why the dominant fix action was **deleting the dangling citation tail while keeping the operative instruction inlined**, and why "inline + sever" was chosen over the three alternatives — shipping the referenced guide alongside the skills (bloats the install surface and ships repo-internal prose), writing the referenced content into the target repo's `CLAUDE.md` (repurposes a contract-key file for something it does not own), and splitting the guide into a shippable subset (a maintenance seam with no payoff once the content is already inlined). Surviving this-repo ticket-ID citations that are not dangling references were reworded rather than removed.

**Shipping boundary as a permanent review criterion.** The reference architecture is codified — not left as a one-time sweep — by extending CLAUDE.md `## Review criteria for skill changes` rule 3: a shipped-artifact reference to a repo-only doc (`docs/*`, `CONTRIBUTING.md`, or a `CLAUDE.md ## <section>`) is a rule-3 violation to flag, and the remedy is to confirm the operative instruction is inlined and sever the dangling path. The criterion carries an explicit **README carve-out**: a `README.md` → `docs/*` link is legitimate and must not be flagged, because README is read on GitHub or in a checkout where `docs/` sits alongside it and is not installed via `cp -r skills/*`. The concrete blessed instance named in the criterion is README's context-usage-gauge section pointing at `docs/doc-writing-guide.md`. The criterion carries a second carve-out alongside the README one: shipped-artifact references to the two **target-repo contract keys** (`CLAUDE.md ## Documentation Locations` / `## Build Commands`) are also exempt, because those keys resolve in the *installing* project's own `CLAUDE.md` (which `/quo-setup` writes) rather than dangling — matching the guard test's `ALLOWED_SECTIONS` allowlist.

**Manifest-mirror decision.** Only the **shared lead statements** of the `#### Write the run-state manifest` sections are kept **byte-identical** across the three execution skills (`quo-execute`, `quo-fix-issue`, `quo-breakdown-epic`) — the `<tempdir>/.quorum/` path boilerplate, the "values that live nowhere else on disk" / "survives compaction" framing, the "filename is deterministic — no random suffix/timestamp" sentence, the "live snapshot / truncate-at-run-start" semantics sentence, and the cross-skill discriminator sentence. The skill-specific portions legitimately **vary and are exempt**: the durable-carrier enumeration lists three carriers in `quo-breakdown-epic` (which has no compromise tracker) versus four in `quo-execute`/`quo-fix-issue`, the deterministic-filename rule carries a compromise-tracker comparison in `quo-execute`/`quo-fix-issue` that `quo-breakdown-epic` lacks, and the snapshot-semantics paragraph carries per-skill section cross-references. Byte-identical triplication of the lead statements plus a mirror criterion is the deliberate trade: three copies to keep in sync, but zero shipped dangling references.

### Feature: Context-window guard for long orchestrator runs

**Architecture.** The guard is a producer/consumer pair that never communicate directly — they meet only at the gauge-file contract. The **producer** is the status-line command `context_gauge.py produce`, wired up at setup time (the Epic 1/Epic 2 machinery), which captures the context-window usage the harness hands its status line — a reading the model cannot see natively, because the payload is delivered only to the status-line process — and publishes it to a per-session gauge file `<tempdir>/.quorum/context-usage-<session_id>.json`. The **consumer** is a boundary check in the three execution orchestrators (`/quo-execute`, `/quo-breakdown-epic`, `/quo-fix-issue`) that calls `context_gauge.py read --session-id <id>` and maps the result to a routing decision. The two halves share only the gauge-file path and JSON field names; there is no other channel between them, which is why that path/field contract is protected.

**Boundary-gate shape.** The consumer runs at each Epic boundary (execute/breakdown) or Issue boundary (fix) and routes on `read`'s four-value output:

- an **integer percentage** — a genuine measured reading. The orchestrator compares it against the stop threshold and stops the run, recommending a fresh session, when it is at or above the threshold; otherwise it proceeds to the next unit.
- `no-reading` — the gauge file is fresh but the number is not yet populated (early in a session, or just after a compaction). This is transient and a live-producer state; the run proceeds and it MUST NOT be treated as a stop.
- `stale` — the gauge file is older than the freshness window; the producer appears to have stopped updating. Routes to a stop (see the Option A decision below).
- `missing` — no gauge file exists for this session; usually no producer is configured. In `/quo-breakdown-epic`, fires the missing-reading configure-now hard-stop gate unless the persistent opt-out marker suppresses it; in `/quo-execute` and `/quo-fix-issue` (since the orchestrator rewrite) records `no reading` in the manifest and continues.

The landed stop threshold is `STOP_THRESHOLD_PERCENT = 75`. The consumer obtains it from the helper's `stop-threshold` subcommand — the single definition site — rather than restating the literal, so the tunable lives in exactly one place. Design intent behind the value: the original 50% was derived for a smaller context window (a conservative margin below a ~83% auto-compaction point, minus a ~25-30% per-unit working estimate). On the current 1M-token window the auto-compaction buffer sits at the very top of the window, and the Issue/Epic-boundary state-externalization checkpoint is what makes a mid-unit compaction survivable — so the operator raised the stop point to 75% (2026-09-09) rather than leave the middle half of the window unused. The per-unit figure remains an unverified working estimate, not a measured or enforced budget; usage only grows within a session, so a reading at or above the threshold is always a genuine stop.

**Unset/unsupported-session-id silent carve-out vs the missing-reading hard-stop.** The two "no trustworthy reading" situations are handled differently and kept distinct on purpose. When the session identifier is unavailable (`CLAUDE_CODE_SESSION_ID` unset), the guard is skipped **silently** — no session id means no gauge file can be keyed, so there is nothing to read: no diagnostic, no gate. When a session id IS present but the reading is `missing` (a configured session whose producer is not publishing), `/quo-breakdown-epic`'s guard fires the **hard-stop configure-now gate** offering `/quo-setup --configure-gauge-producer`, while the two rewritten orchestrators record `no reading` and continue. `no-reading` is neither of these: a fresh-but-unpopulated gauge means the producer is live and simply has no number yet, so it is transient and must never be treated as a stop.

**Option A stale-routing + freshness-window bump.** The landed decision is that a `stale` reading STILL stops the run. A stalled producer's last write is untrustworthy no matter what it holds, and because usage only grows within a session a stale number biases low — toward the banned "looks like there's headroom" direction — so it cannot be trusted as available headroom. To avoid misreading a normally-refreshing-but-quiet producer as stalled, the freshness window is bumped to `FRESHNESS_WINDOW_SECONDS = 1200` (20 minutes): the status line does not refresh mid-turn (tool calls within a turn trigger no refresh), so a healthy session's gauge can legitimately be many minutes old by the time a boundary is reached, and a sub-turn window (the prior 120s) would flag such a gauge stale even with a healthy producer and a valid reading. The alternative of reworking `read` to emit a monotonic-floor `stale:<n>` value — carrying the last-known number alongside the stale flag — was considered and REJECTED, to keep `read`'s protected four-value output contract (`integer` / `no-reading` / `stale` / `missing`) stable. Both figures above are taken from the landed `context_gauge.py` constants, not the plan-time projections.

**Relationship to b.ja9.** b.ja9 made any un-prevented compaction **lossless** by externalizing run-scoped state to durable carriers (bees ticket state, git commits, the run-state manifest), so a compaction that does fire loses no authoritative state. This guard is the complementary half: it **prevents** ill-timed compactions from firing mid-unit in the first place. The two are independent and additive — b.ja9 makes a compaction survivable when it happens; this guard makes it less likely to happen at a bad moment.

**Decomposition.** The feature shipped across Bee `b.55r`'s Epics 1-3: Epic 1 built the producer/gauge-file machinery and folded in only the README gauge-file contract; Epic 2 added the `/quo-setup` producer-configuration how-to; Epic 3 wired the consumer boundary check into the three orchestrators and made the Option A stale-routing + freshness-window decision. This single cumulative record (PRD and SDD `### Feature:` subsections) is authored by Epic 3's doc Task **after** the acting half landed, so every threshold and window figure reflects what was actually built rather than a plan-time projection. Categorization: user-facing (new stop behavior + configure-now gate) AND an architecture change, so it warrants entries in both the cumulative PRD and this SDD.

### Feature: Sequence lanes strictly: Engineer + code review to clean before Test Writer / Doc Writer run once; ask reviewers for second-order effects

**Architecture.** The change narrows one stated orchestration invariant and adds one reviewer output contract. `/quo-fix-issue`'s Reconcile step stops fanning an Issue's implementer lanes out together and becomes an ordered **phase ladder**; `/quo-engineer-review` gains a required narrative subsection reporting what the change set newly exposes. Everything else about the orchestration shape is untouched — the reconciliation loop, cold dispatch, hub-and-spoke via substrate, the routing table, the compromise tracker, and every gate work exactly as before. What changes is *when* a lane may be dispatched, and what a code review is asked to look for.

**The Phase A / B / C ladder** (`skills/quo-fix-issue/SKILL.md`'s phase ladder in `## 4. The loop`; the former standalone review loop is now Phase C):

- **Phase A — source to clean.** The Engineer is dispatched alone; on its return the Code Reviewer is dispatched alone; the pair loops until the Code Reviewer emits its clean shape (`No code issues found.`) **or** every remaining finding has been routed — accepted into the compromise tracker, recorded as a `defer-*` task, or gated to the user. Those three exits are what keep the loop from being unbounded. An Issue needing no source change has an empty Phase A.
- **Phase B — writers once, in parallel.** Test Writer (when tests need changing) and Doc Writer (always), concurrently, reading a diff whose source half is already review-clean. This is the only forward-path dispatch of either role.
- **Phase C — remaining reviewers plus PM.** Test Reviewer, Doc Reviewer, and PM. The Code Reviewer is not dispatched again; it ran to closure in Phase A.
- **Re-entry.** A Phase C finding whose fix changes source re-enters Phase A and, once Phase A re-closes, re-dispatches **only** the writer lanes the source change invalidated. A finding confined to a writer's own lane re-dispatches that writer alone with no Phase A round.

**The freeze is a precondition to check, not a state to remember.** The rule the phase ladder rests on — no Engineer for this Issue while any writer, reviewer, or PM lane for it is active — is expressed as a **TaskList-derived predicate**: no task whose name begins with `test-writer-<issue-id>`, `doc-writer-<issue-id>`, `test-reviewer-<issue-id>`, `doc-reviewer-<issue-id>`, `pm-<issue-id>`, or `analyst-<issue-id>` may be `pending` or `in_progress`. (The `analyst-<issue-id>` prefix was added by `b.q3f` below, which gave an in-flight Analyst something to suspend Phase A for; as shipped at `b.pdq` the list was the first five.) Deriving it from the TaskList rather than from orchestrator memory is the point: TaskList is already one of the four authoritative read-state sources every tick reads, so the rule survives a compaction. Three qualifications are load-bearing and are stated once, at the precondition, with every other site referring back to it: the match is on the name **prefix** plus status (so round-discriminated names are still caught); the **Code Reviewer is deliberately excluded**, because Phase A alternates it with the Engineer by construction so the test could never fire, and listing it would read as licence to run the two concurrently at some future site where it could; and a **`pending` task with no dispatch behind it is not waited on** (nothing will ever notify, and there are no clock primitives to time it out) — it is either dispatched now or marked `completed` and cleared.

The two Phase C reviewers and the PM are covered, not only the writers, because a reviewer that is mid-read when Engineer edits land returns a verdict describing a diff that no longer exists — a wholly spent round, which is worse than a writer's redone one.

**Movement report and the `aborted-*` obligation marker.** Both writer role files instruct a writer to stop and report when the source it was working against moved underneath it (the Test Writer detects this with a `git rev-parse HEAD` + `git hash-object` fingerprint taken at start and again before finishing; the Doc Writer, which has no `Bash`, re-reads with `Read` / `Grep` and stops when material it documented no longer matches). That return needs a receiver, or the orchestrator marks the task `completed`, advances, and reviews a half-written lane. The receiver's mechanism is **obligation-as-pending-task**, the pattern `defer-*` and `gate-*` already use: the writer's own task is marked `completed` (its Agent *has* exited — `completed` on an Agent task means "this Agent is gone", not "this work shipped") and a new `aborted-<role>-<issue-id>` task is created `pending` in its place, carrying the writer's "how far I got" report in `metadata.activity`. Phase C must not begin while any `aborted-*` task for the unit is `pending`; the marker is closed when the re-dispatched lane returns a normal deliverable.

`aborted-` is a **distinct name class**, and that is what keeps these markers out of the Engineer-dispatch precondition without an exemption clause — an Engineer can settle the source while the redelivery stays owed. The alternative considered and rejected was annotating the aborted writer's own task and exempting it, which would have made an Engineer dispatch depend on `metadata.activity`; that string is informational and is never a routing input, a property this design preserves rather than erodes.

**Mover classification and the unexplained-movement gate.** Re-dispatching into a still-moving tree reproduces the abort, so the rung classifies the mover first: an **Engineer** (Phase A must re-close before the writer is re-dispatched); the **sibling Phase B Test Writer's discrimination experiment** (attributable and already restored — re-dispatch with no gate, and when a dispatched Test Writer has not returned yet, wait for its notification and classify then rather than gating on a live dispatch); or an **external actor**. Unexplained movement fires a three-option `AskUserQuestion` through the two-step `TaskCreate` → `AskUserQuestion` contract — **Re-dispatch now** / **Wait** / **Abort this Issue** — carrying the writer's report verbatim. The Wait branch re-fires only on the operator's reply, never on a sibling lane's completion notification; that rule is derivable from the tick's trigger and therefore needs no bookkeeping, which is what keeps it out of `metadata.activity`.

Attribution depends on the Test Writer's return listing every source path it perturbed in place under a required `## Perturbations` heading (`None` when there were none). That heading is the whole attribution channel: an unlisted perturbation is indistinguishable from an external edit and costs an operator gate on an edit the workflow inflicted on itself.

**Aborted close-out.** Two branches route through a shared `#### Aborted-Issue close-out` rather than "moving on to the next Issue" — the unexplained-movement gate's **Abort this Issue** choice and the Analyst gate's **Cancel** choice. (**Two more routers landed in `b.nn8`:** the routing-decision gate's own `Cancel`, which previously exited on its own terms and skipped the close-out entirely, and — in `/quo-execute` only — the scope-bounding gate's `Cancel`, which that skill offers in a `blocker`'s base pair. Each skill therefore has **three** entering branches today: in `/quo-fix-issue` the movement gate's Abort, the Analyst gate's `Cancel`, and the routing-decision gate's `Cancel`; in `/quo-execute` the movement gate's Abort and **both** gates' `Cancel`, which behave identically there.) An aborted unit is still a unit boundary, and skipping it strands exactly the things a boundary exists to settle — a `pending` `aborted-*` marker that would hold Phase C shut on a later re-entry, a `defer-*` entry with no durable carrier, and a manifest still naming a unit the run has left. The close-out runs the same prefix sweep the fixed path runs, the deferral-hygiene gate, and the state-externalization checkpoint on its aborted path, then **reads the working tree with `git status --porcelain` and branches on mode**. An aborted Issue lands no commit, so the Engineer's edits — and any Phase B writer's partial work — stay uncommitted, and the run does not carry that tree into another Issue: in single-issue mode, and in batch mode with the batch exhausted, it names the aborted Issue and the uncommitted paths and proceeds to the post-completion review; in batch mode **with Issues still remaining it stops the run**, naming the aborted Issue, the uncommitted paths, and the fresh-session resume command for the still-unfixed subset. Continuing would hand the next Issue a dirty tree that its Doc Writer reads as "the Engineer's diff", that its Test Writer's fingerprint fallback sweeps up, and that its per-issue commit could absorb. Being run-ending, that branch deliberately skips the context-window guard, per the guard's own no-run-ending-path rule. `/quo-execute` carries the same shape as `#### Aborted-run close-out`, with per-Task and Bee-scoped sweeps, two aborted **Progress** line shapes, and the same name-the-uncommitted-tree stop — which there always ends the run, since execute mode has no batch to advance into. (**Re-keyed in `b.nn8`:** because a gate `Cancel` aborts no lane and opens no `aborted-*` marker, every site that had keyed on "the aborted lane's scope" — the sweep scopes, the Progress-line shapes, the Epic-boundary checkpoint's qualification lead and Progress-write selector, and the invoker enumeration — now keys on **the scope the close-out resolves from its entering branch**: the aborted lane's scope on the movement-gate branch, the review site the gate fired from on the `Cancel` branch. Execute's **Bee-scope** sweep also gained the `gate-*` task that fired the branch routing here: the pre-rewrite Bee-level TaskList close-out, which that scope otherwise reused wholesale, enumerated no `gate-*` name, so a `Cancel` fired at the Bee-level review would have stranded its own gate task `pending`. Nothing about the two shapes themselves changed; only what selects between them, and that one added name.)

**Round discriminators.** Phase A runs N rounds and a Phase C finding can re-dispatch a writer, so repeat dispatches of a role against the same scope take a `-r<n>` suffix (`engineer-<issue-id>-r1`, `code-reviewer-<issue-id>-r1`, `doc-writer-<issue-id>-r1`), following the existing `analyst-<issue-id>-rev<n>` precedent with a different discriminator because the two count different things. Because it is a **suffix**, every rule that tests these names matches on the prefix and catches discriminated and undiscriminated names alike. Close-out sweeps by prefix for the same reason, and "clear from the active set" always means mark `completed`, never delete — the round count is derived by counting recorded rounds, so a deleted task silently frees a name that is already spoken for.

**Why the `/quo-execute` mirror is deliberately narrow.** Execute mode adopts part (g), a Reconcile-receiver for movement reports, the aborted close-out, `-r<n>` discriminators on every repeat dispatch of an already-named role (Subtask-, Task-, and Bee-scoped), plus the narrow movement-abort carve-out on post-completion names, the `**Second-order effects**` summary fields, and the writer-dispatch wording rule below (scoped to the Subtask's implementation dependency or to the Bee rather than to an Issue) — but **not** the phase ladder. Its forward per-Subtask fan-out stays concurrent, and part (g) states that scope limit explicitly so a future reader does not "finish" the mirror. The reason is structural: an Epic's ticket graph already sequences forward work into units whose diffs do not overlap, so an Engineer on Subtask N+1 and a Test Writer on Subtask N are not reading the same diff and neither invalidates the other. An Issue is one undivided implementation pass where every lane reads the same diff, so nothing external orders it. Serializing execute mode's fan-out would trade its designed parallelism for a guarantee the ticket graph already provides.

Part (g) therefore carries **two clauses** in `/quo-execute`, because it routes findings from two review sites with different diff extents: **Clause 1** (per-Task site, scoped to the Task under review, with the per-Task PM in the prefix list because it is the actor *running* the review that Engineer edits would invalidate) and **Clause 2** (the Bee-level site, scoped to the whole Bee, with the Bee-level Code Reviewer **in** the list — unlike the fix-mode ladder's exclusion — because the Bee-level review dispatches its three reviewers concurrently, so a Doc Reviewer finding can route to an Engineer while the Code Reviewer is still reading. No deadlock follows: the wait is on live dispatches that will each notify).

**Second-order effects: a required subsection plus a double-emission rule.** `/quo-engineer-review` gains check category #8, *Second-Order Effects* — "for each change in the diff, state what it newly exposes, weakens, or can now fail, not only whether it is correct" — scoped to the whole change set including first-party dependencies the same team owns (a second-order effect frequently surfaces only at the seam between the primary package and such a dependency); third-party dependencies are out of scope. Both emission shapes carry a `### Second-order effects` subsection, placed after the numbered work-item list and immediately above the routing trailer, **unconditionally** — a clean review emits the heading with the fixed line `No second-order effects identified.` rather than omitting it, because a section that appears only when the reviewer had something to say degrades into one nobody can rely on being asked for.

The **double-emission rule** is what keeps the new subsection from becoming a second routing surface: anything actionable it surfaces MUST also appear as a numbered, severity- and depth-tagged finding, because the orchestrator's routing reads the numbered findings' severity tags, enumerated fix paths, and per-path `[depth:<...>]`, `[preferred]`, and `[introduces-mechanism]` tokens, **and nothing else**. (The parse-input clause was reworded by `b.nn8`, which retired the `(num-paths, max-depth)` tuple and made severity and the `[introduces-mechanism]` tag routing inputs; the rule itself is unchanged, and the wording here mirrors the shipped constraint in `skills/quo-engineer-review/SKILL.md`.) Emitting an actionable effect twice is the intended shape, not redundancy to optimize away. (`b.q3f` below carves one exception into this rule: a record of work **owed to another lane** lives in the narrative subsection only, because this review's numbered list cannot route it — see the check-#8 paragraph in that entry.) The corollary the ladder depends on: **the Phase A exit test reads the numbered list only** — a non-empty narrative alongside a clean numbered list does not hold Phase A open, since anything actionable in it is already a numbered item.

The narrative needs a destination or it reaches the orchestrator and stops. The relay chain is `/quo-engineer-review` → the Code Reviewer wrapper (`agents/code-reviewer.md` relays the subsection verbatim) and/or the PM (`agents/pm.md` relays it into its Final report) → a `**Second-order effects**` field in the per-issue summary (`/quo-fix-issue`), the per-Task summary, and the `## Bee Execution Complete` summary (`/quo-execute`). That field collects every relayed narrative, attributes each block when several sources contributed, de-duplicates exact repeats, and — unlike `**Accepted compromises**` — renders `None identified.` rather than omitting itself when there is nothing.

**Sweep completeness evidence, and its carriers.** `agents/engineer.md` requires, on any assignment directing a change at *every site* where some property holds, a completeness check **with evidence**: the patterns run verbatim, every hit those patterns produced, and per hit either the change made or the reason it is deliberately untouched. That is the `b.pdq`-era trigger; `b.q3f` below adds a second, independent one — a supplied **non-empty** upstream site list (relayed under `## Blast radius`) triggers the reconcile-and-disposition obligation on its own, whatever the assignment's shape, while an upstream list that explicitly states it enumerates no sites triggers nothing and owes no evidence. Since that relay rides every fix-mode Engineer dispatch, the second trigger is in practice the one that usually fires. `/quo-engineer-review` verifies the diff against that list rather than rediscovering the sites, and reports a shortfall as a **gap in the list** — so an incomplete sweep is caught once rather than one newly-discovered site per round. The missing-list case is deliberately asymmetric: an absent list is a finding **only when the invocation itself named the assignment as sweep-shaped**, because a caller that never relayed the list produces exactly the signal an Engineer who never wrote one produces, and inferring sweep-shapedness from the diff would make this fire on every repetitive-looking diff. That is why the dispatch prompt states the assignment was sweep-shaped independently of whether a list came back.

Two orchestrator-side carriers make the evidence usable. The completeness list has no durable home — the Engineer Agent has exited and its return lives only in the conversation — so the Phase A Code Reviewer dispatch prompt embeds it verbatim as text (not as a scratch-file path) under a labelled heading. Separately, `agents/engineer.md` now requires a `## Files changed` list on **every** return, sweep-shaped or not, because the orchestrator carries that list forward as the Test Writer's `## Source paths to fingerprint` set: unioned across every Phase A round, test paths dropped. An explicitly-empty list is a list, not a missing one — it contributes nothing to the union and does not trigger the working-tree-wide `git diff --name-only HEAD` fallback, which is avoided where possible precisely because it sweeps in anything else uncommitted in the tree and every extra path is one the writer will stop on.

**Writers verify; the orchestrator promises only what it controls.** Both execution skills carry this rule, scoped per mode: the writer dispatch prompts may state the claim the orchestrator's own dispatches actually make good on — in fix mode *"no Engineer Agent will be dispatched for this Issue while you are running"*, enforced by the precondition above; in execute mode *"…for your Subtask's implementation dependency"* for a Subtask-scoped writer (a sibling Subtask's Engineer may legitimately be running) or *"…for this Bee"* for a Bee-scoped one — and in neither mode may they claim the source tree is frozen. The orchestrator cannot prevent the user, a second session, or a background process from editing the tree, so a freeze promise names a lever it does not hold. Both writer role files scope their stability rule per mode and carry the writer-side recovery path themselves, so it does not depend on the dispatch prompt getting the wording right. `agents/test-writer.md` additionally forbids `git checkout` / `restore` / `stash` / `reset` against any non-test path — those silently discard uncommitted work another role may be holding, and the loss is invisible to its owner — and prescribes the sanctioned substitute for a discrimination experiment: copy the file into `<tempdir>/.quorum/` under a collision-resistant name, perturb the original in place, restore by writing the copy back, and verify the restore by comparing against the copy (not `git status --porcelain`, which reads ` M` before, during, and after the perturbation because the Engineer's fix is already uncommitted).

**Design decisions this run recorded.**

- **No lane-phase field in the run-state manifest.** "Did the last code review come back clean?" is *not* a value that lives nowhere else on disk — it is re-derivable at any moment by asking the Code Reviewer again. So the manifest gains no phase field, and the post-compaction recovery inside Phase A is to **re-dispatch the Code Reviewer**: a cold fresh-eyes pass over the current diff is idempotent and cheap, and is strictly better than guessing the prior verdict. The manifest's shared lead statements are unchanged by this feature; only a skill-specific Progress-shape paragraph was added in `/quo-execute` and `/quo-fix-issue` for the aborted line shapes.
- **`metadata.activity` stays informational.** Every new routing test keys on a task's **name prefix and status**. The aborted writer's report, the abort reason, and the gate's choices ride in `metadata.activity` as context for a re-dispatch prompt or a later reader, and nothing branches on them. This is why the aborted lane got its own name class instead of an annotation on the existing task.
- **`agents/code-reviewer.md` stays a criteria-free wrapper.** The second-order-effects criteria live in `/quo-engineer-review`, which the wrapper invokes; the wrapper's only additions are relays: the Engineer's completeness evidence *into* that invocation, the `### Second-order effects` body back *out*, and — added by `b.q3f` below — the upstream `## Blast radius` block *into* the invocation under the same heading it arrived under. All three are relay only; duplicating the criteria into the role file would create a second definition site that drifts from the skill.

**Categorization.** Both user-facing and architecture-affecting. Fewer rewritten docs and tests per issue, second-order effects surfaced a round earlier and rendered into every summary, sweep-completeness evidence, and a new unexplained-movement gate are all observable to the operator, so a PRD entry is warranted; the phase ladder, the TaskList-derived precondition, the `aborted-*` obligation marker, the narrow execute-mode mirror, the double-emission rule, and the evidence carriers are architecture, so this entry is warranted. The user-typed slash-command surface is byte-for-byte unchanged — no new flags or arguments — but the README's "Parallel by construction" claim and the `/quo-fix-issue` catalog row both needed qualifying, and the `## Orchestration in execution skills` cold-dispatch invariant above was narrowed rather than left to contradict the ladder.

**Decomposition.** Shipped as a standalone Issue (`b.pdq`) on branch `fix/b.pdq`, with no Plan Bee in `reference_materials` or `up_dependencies`, so this subsection's heading uses the Issue's own title verbatim per the `agents/doc-writer.md` standalone-Issue fallback provision — the same provision the `b.bq4` entry above records. Eight program-source files changed in one pass: the ladder and its rungs in `skills/quo-fix-issue/SKILL.md`, the narrow mirror in `skills/quo-execute/SKILL.md`, category #8 and the required subsection in `skills/quo-engineer-review/SKILL.md`, and the role-contract halves in `agents/engineer.md`, `agents/test-writer.md`, `agents/doc-writer.md`, `agents/code-reviewer.md`, and `agents/pm.md`. The evidence behind it came from a worked reference run whose later rounds happened to follow the proposed ordering and produced zero writer rework, which is why the ladder shipped as an ordering rule rather than as a heuristic. Two sibling Issues carry the complementary work this one deliberately did not take: a front-loaded Analyst blast-radius sweep (which would remove rounds rather than make them cheaper — shipped as `b.q3f`, the next subsection) and a routing-table default.

### Feature: Analyst must produce a blast-radius sweep and name implied policy decisions at the design gate

**Architecture.** The design analysis `/quo-fix-issue`'s Analyst pass already produces is made to carry two things it previously left to discovery: the enumerated set of sites an invariant change touches, and the yes/no policy questions the change forces but the Issue body never settles. Both become **unconditional sections** of the Analyst's structured-output contract, both are surfaced at the existing Analyst gate so one Approve ratifies design *and* policy answers, and the first travels a relay chain into the two `/quo-engineer-review` callers, where check #8 verifies the diff against it. A fourth change is the Engineer's counterpart obligation: rather than inventing a mechanism the approved design did not enumerate, the Engineer stops and returns the question, which **on the forward fix path** the Analyst gate receives as a Revise (the same question raised after the Issue is closed out, under the post-completion review, routes to a filed follow-up Issue instead — see below). No new gate, option, TaskList name class, marker, or run-state-manifest field is introduced anywhere in the change.

**The two new contract sections** (`agents/analyst.md` `## Structured-output contract (Analyst → orchestrator)`). Both headings are emitted on every proposal — a section that appears only when there was something to say degrades into one nobody can rely on being asked for, so each carries a **fixed empty line** for the nothing-found case rather than being omitted. The Blast radius's line — `No invariant added, removed, or weakened.` — is emitted when the recommendation adds, removes, and weakens no invariant **and introduces no mechanism**, so the mechanism half of the section's remit is covered by the same nothing-found test as the invariant half; the Policy-decisions line is `None — the recommendation leaves no policy question open.`

- **`### Blast radius`** — for every invariant the Recommended approach adds, removes, or weakens: the invariant on one line, then the sites where it is observable or assumed, grouped by kind (source logic / logs / traces / metrics / error and exception text / comments and docstrings / configuration and deployment manifests / customer docs / internal docs / tests). Each entry carries a `file:line` **plus the verbatim search pattern that found it**, so the sweep is re-runnable and the patterns themselves are auditable; `None found` is acceptable inside a group only when it names the pattern that was tried. Three rules constrain how the sweep is run. **Pattern choice targets the property, not the machinery**: a pattern matching only the added or removed identifier finds the sites that already agree with the change and misses the consumers that assume the old behavior under other names, so the contract requires a pattern for the observable effect (the log field, the attribute key, the error-message fragment, the config key) alongside any identifier pattern, and requires **both spellings** — old and new — to be run and recorded on any rename or removal. **Scope** extends to first-party dependencies the same team owns (another workspace member, a sibling checkout, a vendored internal library); third-party dependencies are out of scope. And a **lifecycle axis** applies to every *mechanism* the approach introduces: where it is created, read, mutated or invalidated, torn down, observable, and documented — in every scope the change touches and on every exit path — with `file:line` for legs that exist and an explicit `new` for legs the change adds, a missing leg in any scope being a design gap reported at the gate rather than discovered one leg per round. The lifecycle paragraph is the **single canonical home** for the definition of "mechanism" (any new state, configuration surface, persisted or wire field, background task, exception or error type, metric / log / trace attribute, name or identifier class, gate, or retry / fallback path); other files reference it rather than restating it normatively, so widening the list stays a one-place edit. The section also carries the **scope-split recommendation** — whether a concern the sweep surfaced that is distinct from the Issue's stated defect should be folded in or filed separately and only documented here.
- **`### Policy decisions this change implies`** — one entry per yes/no question the recommendation forces and the body leaves open, each giving the question, the consequence of yes, the consequence of no, and the Analyst's **recommended answer**. A **grounding rule** governs any decision that asserts what possessing or observing a value grants: the answer must not be derived from the one mechanism the change removes. The Analyst enumerates, with `file:line`, every check the system still applies on that value's path (authentication, coarse authorization, per-principal filtering, per-principal caches, input validation), states what remains true after them, and phrases the conclusion in those terms — "any authenticated principal that obtains X can …, subject to its own permissions" — rather than as an unqualified "secret" or "capability". The Recommended approach must use that same grounded phrasing, and reviewers check the claim against the enumerated checks rather than against the other surfaces that repeat it.

**Double emission for the scope-split recommendation.** A scope-split lives in `### Blast radius` because that is what the user reads at the gate, and is **mirrored** as a `### Deferred refinements` bullet with the matching destination annotation (`addressed-now` for a fold-in, `defer-to-new-Issue` for a split) because that block is what the orchestrator turns into a durable `defer-*` carrier at Approve. The two-place emission is the same shape `b.pdq`'s second-order-effects rule uses, and for the same reason: the user-facing narrative surface and the routing surface are different surfaces. It also constrains the verdict — a scope-split is itself a refinement, so a converged verdict carrying one is at least `recommend-with-refinements`; and on `escalate-to-user`, where `### Deferred refinements` is structurally `None`, no scope-split is issued at all (the concern folds into the escalated open questions in `### Why`) rather than being stated with no carrier behind it.

**The relay chain, and why it is one heading string.** `## Blast radius` is the heading at *every* hop after the Analyst's own `###`-level emission: the Analyst gate's Approve captures it as directive; the Engineer dispatch embeds it under `## Blast radius` as the **enumerated site list** `agents/engineer.md` already reconciles its completeness evidence against; the Phase A Code Reviewer dispatch and the Phase C PM dispatch each embed it under the same heading; and `agents/code-reviewer.md` and `agents/pm.md` forward it verbatim under the same heading into their `/quo-engineer-review` invocations. A renamed heading anywhere on that chain silently drops the check, which is why the string is fixed rather than described. Two properties make the chain total. The **fixed empty line is relayed too** — "swept and found nothing" and "not supplied" are indistinguishable once the heading is omitted, and the review routes them differently. And the relay is embedded **as text in the prompt, never as a scratch-file path**, matching how the Issue body and the completeness evidence already travel. The PM relay is a second, independent hop rather than a redundancy: the PM and the Phase A Code Reviewer are different Agents with no channel between them, and the PM reviews a wider diff (it includes Phase B's test and doc changes).

**Check #8's two asymmetric outcomes** (`skills/quo-engineer-review/SKILL.md`). The upstream list's whole value is that the implementer did not write it — a sweep verified only against the Engineer's own list cannot surface an entry that list never had — so when both lists are present the diff is verified against both, and the two shortfalls route differently:

- **A listed site the diff neither changes nor dispositions** is a normal finding **against the Engineer**, emitted as a numbered, severity- and depth-tagged work item through the ordinary routing table.
- **A diff-touched site on neither list** is a **gap in the upstream list**, recorded as narrative under `### Second-order effects` and deliberately *not* emitted as a numbered work item, whenever the diff already handles it correctly. The numbered list is the sole routing surface and is reserved for actionable items; a site the diff already handles needs no fix round. (A site the diff handles *incorrectly* is a finding on its own merits under the other categories.)

That subsection therefore now receives **two** entry kinds from this check — the list gap above, and an **out-of-lane upstream site left with no disposition**, recorded as owed to the lane that owns it (see the lane rule below). The second kind is the one exception `b.q3f` carves into `b.pdq`'s double-emission rule: it is a record of work owed to another lane, which this review's numbered list cannot route, so it lives in the narrative subsection only rather than being mirrored as a numbered finding. `skills/quo-engineer-review/SKILL.md`'s compatibility constraint states the carve-out at the same site as the rule.

### Feature: Routing table gates every multi-path finding; default to orchestrator picking the highest-quality path, gate only re-architect/scope

**Architecture.** The routing key in both orchestrators' `### Orchestrator discipline: routing review findings` section moves from a **property of the finding** to a **property of the path the orchestrator chose**. `b.ut9`'s part (a) mapped the `(number-of-fix-paths, maximum-depth-across-paths)` tuple to a decision, which made "the reviewer enumerated more than one path" sufficient on its own to fire a user gate. Reviewers almost always enumerate two or three paths, so almost every substantive finding became a prompt whose answer was an engineering call the orchestrator already had the context to make. Part (a) is now a two-step **pick-then-route** procedure, and path count is no longer a routing input at all.

**Step 1 picks; Step 2 routes on the pick.** Step 1 is the orchestrator's own judgment: choose the highest-quality fix path among those the reviewer enumerated. The reviewer's `[preferred]` token is an **input** to that choice rather than a verdict — preferred when it is also the most complete, overridden by the fuller path when `[preferred]` marks a narrowing and a fuller path is still the smallest internally-consistent complete change. Step 2 is deterministic given that pick: a six-row, first-match-wins condition list, every row evaluated against **the chosen path**.

```
| # | Condition (first match wins)                                    | Routing                            |
|---|-----------------------------------------------------------------|------------------------------------|
| 1 | No depth tag, or a malformed severity/depth tag                 | Treat as `re-architect` → gate (d) |
| 2 | Chosen path introduces a mechanism                              | Scope-bounding gate (c)            |
| 3 | Chosen path moves a published contract surface beyond the       | Scope-bounding gate (c)            |
|   | unit's ticket, or is breaking                                   |                                    |
| 4 | Chosen path is narrower than the smallest internally-consistent | Scope-bounding gate (c)            |
|   | complete fix                                                    |                                    |
| 5 | Chosen path's depth tag is `re-architect`                       | Routing-decision gate (d)          |
| 6 | Otherwise                                                       | Dispatch the chosen path, no gate  |
```

Ordering the pick before the route is what makes the rest expressible. Rows 2–4 are all statements *about a path* — a path cannot be tested for "introduces a mechanism" or "narrower than the complete fix" until one has been selected — so a tuple-keyed table had no place to put them. Row 1 stays first so parts (e) (the no-depth-tag shim) and (f) (malformed tags) remain reachable unchanged. **Rows 2–4 deliberately precede row 5**: a mechanism-introducing or scope-moving path must reach gate (c) *regardless of its depth tag*, so ordering them after the depth row would let a `re-architect` mechanism arrive at the wrong gate — the one that asks "which path?" rather than the one that asks "should this be built here at all?".

**The pick is always one of the paths the reviewer enumerated.** Step 1 is confined to the reviewer's list, so the section lead's never-invent rule holds without a carve-out: no emitted depth tag is overwritten, and no depth is originated. When *no* enumerated path is the smallest internally-consistent complete change — every one leaves the stated defect partly unfixed — Step 1 picks the **most complete of them anyway** and Step 2 routes it. Rows 2, 3 and 4 all send it to gate (c), where `Fix properly now` dispatches the complete fix; the exception is a finding whose depth tag is absent or malformed, which row 1 sends to gate (d) instead, and that gate carries no `Fix properly now` — the user picks among the paths as emitted. Either way the incomplete menu becomes visible **in session**: a gate fires where row 6 would otherwise have dispatched silently, and the user sees the menu it fired on. A **durable** record reaches the post-completion review only when the user defers or accepts — Trigger A on `Defer to follow-up Issue`, Trigger B on `Accept the limitation` — while `Fix properly now` writes none, so an incomplete menu resolved that way leaves no trace past the run. That is the limit of what this routing does with an under-enumerated finding; the orchestrator does not absorb the gap by writing a path of its own.

**A composed-path allowance was applied during the run and then stripped.** After the PM observed that this run's own tracker had recorded orchestrator-composed paths **twice**, Step 1 was widened mid-run to let the orchestrator compose the complete fix when the menu held none and assign it a depth from the reviewer's three-value vocabulary. The post-completion review challenged the branch as an **authority extension beyond this Issue's table** — the Issue asked for a routing default, not a new class of orchestrator-authored fix path — and the operator directed it **stripped** (2026-09-08), leaving nothing of it in the shipped prose. The design is filed **verbatim** as Issue **`b.kxx`** for the operator to decide as policy.

The tracker's `Fix paths surfaced by reviewer` field therefore stays exactly what its name says — a faithful record of the reviewer's emission, down to `none` when the reviewer enumerated no path at all, which Trigger A writes on the zero-path deferral the routing-decision gate makes reachable (its `Defer` choice is offered whatever the path count) — and **PHASE 4** can read it as the reviewer's menu when judging under-enumeration without discounting any line in it. Both skills' Accepted-compromises render steps surface four entry fields (`Finding (verbatim)`, `Decision`, `Rationale`, `Follow-up Issue`) and deliberately omit that fifth one, on the grounds that the operator-facing surface shows the path that was chosen rather than the full menu; the paths field is a machine-read record for the post-completion phases.

**Two definitions were made explicit, and only one of them lives here.** *"Highest-quality"* is defined **inline** in both skills, because it is the criterion Step 1 applies on every finding and a pointer would be one indirection too many at the decision site: the smallest change under which the code compiles, the tests pass, and every surface agrees with the invariant the unit's ticket names; total-system complexity counts against a path; effort is never the tiebreaker between paths of equal completeness; "adds a mechanism" is a reason to route to gate (c), not a reason to build; and for a prose-only change set the compile-and-pass clause degenerates to "every surface that states the invariant states it consistently". *"Introduces a mechanism"* is **not** restated — this feature consumes it by pointer so there is one definition site rather than four. **That definition site landed with the sibling change `b.q3f`**, whose Amendment 3 specified it: the lifecycle-axis paragraph of `agents/analyst.md`'s `### Blast radius` section is the single canonical home, and both orchestrators, `/quo-engineer-review`'s `[introduces-mechanism]` bullet, and `agents/code-reviewer.md`'s relay of that tag all point at it. Siting it there rather than duplicating it here was the right call — the alternative was four copies drifting apart. The pointer was forward-looking while the two changes were in flight concurrently; a strict expected-failure pin in the test suite held that gap visible, and `b.21w` retired the marker once the definition merged. The single exception is the two post-completion reviewer prompt skeletons, which **inline the enumeration**: their reader is a cold fresh-eyes Agent composing its judgment from the prompt text, and a pointer to a role file that Agent has no reason to open would silently degrade the check to whatever the reader already believed.

**No new gate.** All three of the new conditions (rows 2–4) route to the **existing** scope-bounding gate (c), whose choice set — `Fix properly now` / `Defer to follow-up Issue` / `Accept the limitation` — already asks exactly the question they raise: is this in scope for this unit, or does it belong in a follow-up? Part (c) therefore states **four** entry conditions rather than one, and the pre-existing part-(b) scope-bound condition is declared to be **read as row 4** downstream — it is the same condition stated twice, so every later rule that enumerates "row 2, 3, or 4" covers it without naming it separately. Adding a fourth gate for mechanism-introduction would have added a name class, a two-step-contract site, and a tracker trigger to keep coherent, for a decision the existing gate already frames.

**Gate (c)'s `Defer to follow-up Issue` now defines "the soft fix", and the definition is dispatch-direct on purpose.** That branch had always said "proceed with the soft fix this round" without saying what the soft fix *is*, which under part (b)'s never-narrow prohibition left the orchestrator with no sanctioned filler. On a `suggestion` or `nit` it is now **the most complete of the enumerated paths remaining once the deferred one is set aside**, dispatched **directly** rather than re-entered into Step 2. The directness is load-bearing: a remaining path is by definition narrower than the one just deferred, so Step 2 would match row 4 and route it straight back to the same gate — an unproductive loop. When the deferred path was the only one enumerated, there is **no fix this round** — the same end state as `Accept the limitation`, with the follow-up Issue filed — and never an invented narrowing. Both of those last clauses are scoped to a non-blocker, and the severity paragraph below says so explicitly, since a blocker's Defer branch always ships the narrowing the orchestrator authors for it. **Trigger A's `Rationale` carries the other half**: it names **which remaining path shipped as the soft fix, by letter, or that none did** — the `none did` case covering the single-path deferral at this gate *and* **any** deferral at gate (d), whose `Defer` branch ships nothing against the finding however many paths the reviewer enumerated — and, on a `blocker` deferral, the **narrowing record** takes that slot instead (what was scoped down, and why the blocker no longer describes anything that ships), since that branch ships a narrowing rather than one of the reviewer's remaining paths. The deferral and what shipped in its place are one decision, and an entry recording only the deferral leaves a later reader unable to tell a soft-fixed finding from an unfixed one.

**Severity-aware gates: a `blocker` is never accepted, and is deferred only paired with a narrowing.** Both gates withhold choices from a `blocker` finding, under one rule shared by the two skills and one structural divergence between them.

`Accept the limitation` is **unreachable for a blocker unconditionally** — do not offer it, do not mark it, do not route to it by any other path, because accepting a blocker ships the blocker. What a blocker always gets instead is a **base pair**, which is its floor at gate (c) and the whole set whenever the Defer conditions below do not hold: `Fix properly now` plus, in `/quo-fix-issue`, **`Re-dispatch the Analyst with this finding`** for the case where the finding shows the *approved design directive itself* is wrong rather than its implementation (reusing the Analyst gate's Revise-branch re-dispatch shape, after which the gate's approval gate re-fires); and, in `/quo-execute`, which has **no Analyst**, **`Cancel`** through the shared aborted-run close-out — the same *stop and re-plan* answer expressed with the lever that skill has. Two choices is a real decision, so gate (c) fires normally in both skills. An earlier shape in `/quo-execute` withheld `Cancel` as well, leaving that gate a single option and therefore dispatching a blocker's fix with **no gate at all** — the post-completion review challenged that as under-enumerating the choices actually available to a skill with no Analyst, and it was removed on the same 2026-09-08 pass. No **gate** in either skill now degenerates into an ungated dispatch on a blocker, which is why Trigger C has one firing site per skill rather than two in execute mode. Row 6 is severity-agnostic and always was — a blocker whose chosen path clears rows 1–5 dispatches ungated like any other finding, with a Trigger C entry recording the pick unless its sole path was a lone `trivial-tweak`; what the removal changed is that no *gate* fire ends that way.

`Defer to follow-up Issue` is added as a **third** choice only when **both** hold: (i) the fix path the finding *needs* introduces a mechanism — the reviewer's `[introduces-mechanism]` tag, or the orchestrator's own reading against the definition in `agents/analyst.md` — **and** (ii) that mechanism serves a case **outside the unit's stated defect**, so the change narrowed to the stated defect is still complete and the blocker no longer describes anything that ships. **The guard on it is an operator directive**: a narrowing may never reduce coverage of the stated defect, so a blocker that cannot be made inapplicable to what ships without leaving that defect partly unfixed is **in scope** and takes the base pair, never `Defer`. Condition (i) tests the path the finding *needs* rather than the path Step 1 chose, so the branch can open on a row-3 or row-4 fire as readily as on row 2. When it opens, the deferral is **paired with the narrowing and never shipped alone**: file the follow-up Issue first, carrying the reviewer's sketched design verbatim, and dispatch the narrowing only once `/quo-file-issue` has returned an Issue ID — a failed filing forbids shipping the narrowing, the one place part (f)'s re-prompt bullet is load-bearing on a blocker. That narrowing is dispatched **directly**, not by re-entering Step 2, which would match row 4 and route it straight back to the gate; it is the same terminality the non-blocker soft fix carries, applied to the blocker's narrowing. The pairing is marked `(Recommended)` whichever row fired the gate, and at gate (d) that marker **takes precedence over every other choice's** — each fix-path choice's Step-1 marker, and the base pair's second choice — so exactly one choice carries it, and a zero-path row-1 blocker whose Defer branch is open shows `(Recommended)` on `Defer` alone. **Trigger A fires at either gate** and its entry must carry the narrowing record.

Gate (d) otherwise keeps its per-path list plus `Cancel`, with `/quo-fix-issue` adding the Analyst re-dispatch alongside — in `/quo-execute` the base pair's second choice *is* `Cancel`, so there is nothing extra to add there. On a row-1 blocker the per-path list may be **empty** — that is what a malformed or absent tag emission looks like — and the gate still fires on it: in `/quo-fix-issue` the Analyst re-dispatch is marked `(Recommended)` there, because a blocker with no shape to route is precisely what a fresh design pass is for; in `/quo-execute` the listed choice is `Cancel` alone, the question text states that the reviewer enumerated no fix path, and a prose direction the user types into `AskUserQuestion`'s free-text slot is dispatched as the fix — writing no Trigger C entry, a user-directed fix not being an ungated route — while **no** direction re-fires the gate rather than inventing a dispatch for a shapeless emission.

**The Analyst re-dispatch reaches back into the Analyst gate from two phases, and that has consequences.** The choice is reachable from a **Phase A** code-review finding and from a **Phase C** reviewer or PM finding, so the fresh cold `analyst-<issue-id>-rev<n>` dispatch can go out with writer, reviewer and PM lanes for this Issue still open. Those are swept `completed` **on `Approve`**, immediately before the run re-enters the phase ladder — not at the moment the Analyst is dispatched, so a `Revise` at the re-fired gate leaves them untouched, while a `Cancel` there sweeps them through `#### Aborted-Issue close-out`, whose own step 1 covers exactly those names. The Engineer-dispatch precondition is what forces the sweep: it forbids a fresh Engineer while any of them is `pending` or `in_progress`, and on a Phase A fire there may be none to sweep. A lane still **in flight** is marked `completed` anyway, since a dispatched background Agent cannot be terminated, with `metadata.activity` recording that it was live at the re-dispatch; when its notification lands, **its findings are discarded rather than routed**, because they were raised against the directive the re-dispatch just superseded. **The discard is scoped to the directive, not to the sweep**: it covers every finding raised under the superseded one, including the sibling findings co-emitted by the very reviewer return that fired this gate (they sit in the orchestrator's context on no TaskList task of their own, so no sweep reaches them) and any lane that returned between the gate answer and the sweep (already `completed`, so an every-active-task sweep passes over it). None of them are routed; the revised directive is what the next round reviews against. The same Approve carries a `defer-*` ledger consequence: the Analyst gate's `### Deferred refinements` consumption step now names this gate's re-fire as a **third** route into Approve alongside the original proposal and a Revise iteration, so the re-fired Analyst's block is walked at that approval like any other. What supersession clears is deliberately narrow — **only the `defer-*` tasks of an iteration the user never approved**, a Revise chain's, each rejected in favour of the next; those are marked `completed` and annotated superseded before the approved block is consumed. **Tasks banked at an earlier `Approve` survive the re-fire** and stay in the active set, because that approval still stands over the refinements it banked: the re-fired Analyst is briefed on the reviewer's finding rather than on those deferrals, so its block may legitimately be `None`, and nothing downstream recovers them — the deferral-hygiene gate's Step 1 enumerates only still-active tasks and its Step 0 walks only the latest Analyst block. Clearing on *any* re-dispatch, as an earlier revision of this rule did, would have destroyed every banked refinement at the first re-fire. On `Approve` the run re-enters Phase A with the revised directive against the **current working tree** — the edits already landed stay in it, uncommitted, and the revision is applied on top of them rather than to a clean base. The same reachability changes what the Analyst gate's own `Cancel` can land on: it is no longer only the pre-implementation exit it was, so `#### Aborted-Issue close-out` reads the tree with `git status --porcelain` rather than asserting it is empty, and may find a Phase A round's Engineer edits or a full Phase A/B pass sitting there.

**The first reading of the directive was stricter, and it is what drove most of this run's review rounds.** `Defer` unreachable for *every* blocker was applied first; with no Defer route an open blocker had nowhere to go but another fix round, and the run exceeded the three-round review cap set for it (sixteen code-review rounds before the first close-out, each a fresh cold full-diff pass). The post-completion review refined the rule to the mechanism-plus-outside-the-defect conditions above, with the coverage guard as the backstop that keeps the refinement from becoming a way to ship an unfixed defect.
