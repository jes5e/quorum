# quorum — Product Requirements

## Existing scope

quorum is a portable Claude Code skill set for engineers who want an end-to-end SDLC running on top of [bees](https://github.com/gabemahoney/bees) tickets — plan, break down, execute, review, fix, repeat. Distributed as markdown skills plus a small number of Python helpers and installed into `~/.claude/skills/` (global) or `<repo>/.claude/skills/` (per-project), the skills are invoked via `/<skill>` slash commands inside Claude Code. The project is open-source under MIT license and is in active maintenance.

## Why

quorum exists as an alternative to [Apiary](https://github.com/gabemahoney/apiary), the original bees skill set. Apiary remains a great fit for many projects; quorum is shaped by a different set of priorities:

- **Cumulative project-level docs.** The project requirements doc (PRD) and internal architecture docs (SDD) named under CLAUDE.md `## Documentation Locations` accumulate sections as features ship, and become the source of truth that agents (`quo-execute`, `quo-fix-issue`) read for spec-drift detection. `/quo-setup` can bootstrap baseline docs from an existing codebase via guided Q&A. At plan time, `/quo-plan` does not mutate the project-level PRD/SDD — per-feature spec content lives as Spec Bee `t1=Doc` children referenced from the Plan Bee. Cumulative project-level entries are appended post-implementation by the `doc-writer` agent so the on-disk docs reflect what actually shipped. `/quo-plan-from-specs --feature "<title>"` retains an express path for users who already maintain finalized cumulative PRD/SDD files on disk.
- **Language-agnostic.** Works on Rust, Node, Python, Go, Java, polyglot, or unknown stacks. Stack-specific commands (compile, format, lint, narrow test, full test) are detected at setup and stored in CLAUDE.md contract keys, then read by skills at runtime — no skill-editing needed when switching projects.
- **Cross-platform.** Native macOS, Linux, and Windows PowerShell (or WSL/Git Bash). Every shell snippet in skill prose ships as labeled OS-conditional blocks; the helper scripts that need cross-platform filesystem behavior ship as Python.
- **Plain-English statuses.** Plan-hive bees use `drafted` / `ready` / `in_progress` / `done`; issue-hive bees use `open` / `done`; spec-hive bees use `drafted` / `ready`. No translation layer or insect-metaphor jargon to remember.
- **Two entry points.** `/quo-plan` is the interactive scope-discovery path — used both for ideas without finalized specs and for new features being added to an already-cumulative PRD/SDD. It authors per-feature PRD and SDD content as Spec Bee `t1=Doc` children attached to the Plan Bee rather than mutating the project-level docs at plan time; the cumulative on-disk entries are appended post-implementation by the `doc-writer` agent. `/quo-plan-from-specs` is the express path when a finalized **single-feature** PRD and SDD already exist on disk; it hard-fails on multi-feature cumulative docs to avoid re-planning previously-planned features. Experienced users with finalized cumulative specs can also pass `/quo-plan-from-specs --feature "<title>"` to scope an express re-plan to a single `### Feature:` subsection inside the cumulative docs. Both entry points produce the same Plan Bee shape.
- **Idempotent.** Every state-mutating skill (`quo-setup` especially) detects existing configuration and only prompts where something is missing or the user asks to change it. Re-runs are safe.

## Out of scope

- **tmux-dependent skills in the portable core.** Skills that need terminal session multiplexing (`bees-fleet`, `bees-worktree-add`, `bees-worktree-rm`) are explicitly out-of-scope for the cross-platform core and live elsewhere as optional later-installs.
- **Stack-specific helpers.** Changelog tooling, license attribution generation, dependency auditing, and similar single-stack utilities are routed to companion repos rather than added to the core.
- **Infrastructure-specific helpers.** Pastebin clients, cloud storage uploaders, and similar platform-coupled features stay out of the core.
- **Replacing Apiary.** quorum lives alongside Apiary, not as a replacement. Users who want Apiary's lightweight, ephemeral-spec, async-team-spawning style should use Apiary.
- **Maintaining a translation layer to legacy bee-themed terminology.** The status rename from `larva` / `pupa` / `worker` / `finished` to `drafted` / `ready` / `in_progress` / `done` is permanent.

## Acceptance criteria (project-level)

- **End-to-end chain works on any supported stack.** On a fresh repo of any supported language (Rust, Node, Python, Go, Java, or unknown), the full chain `/quo-setup` → `/quo-plan` (or `/quo-plan-from-specs`) → `/quo-breakdown-epic` → `/quo-execute` runs to `done` status across all Epics without per-language skill edits.
- **Cumulative-PRD scoping holds end-to-end.** When a Plan Bee is authored via `/quo-plan-from-specs --feature "<title>"` against cumulative PRD/SDD docs, the single-feature scope is enforced through every downstream skill: `/quo-breakdown-epic` decomposes against only the matching `### Feature: <title>` subsection, and the per-Task PM in `/quo-execute` (and the PM role in `/quo-fix-issue` when an Issue derives from a scoped Plan Bee) compares implementation against the scoped subsection only. Other features in the same cumulative docs do not surface as spec drift.

## Per-feature scope

### Feature: Side-effect-free /quo-plan and /quo-file-issue with preserved context

**What.** Redesign `/quo-plan` and `/quo-file-issue` so that neither skill mutates the project's cumulative PRD, SDD, or README at plan time or filing time, and so that the rich context of pre-skill-invocation conversations is preserved end-to-end through downstream execution agents. Per-feature spec content is now authored as `t1=Doc` children (PRD and SDD, differentiated by exact title-match) of a new top-level Spec Bee in a new **Specs** hive; the Plan Bee's `reference_materials` field points at the Spec Bee via a new `bees` resolver of the form `[{"value":"<spec-bee-id>","resolver":"bees"}]`. Two new composable sub-skills — `/quo-write-prd` and `/quo-write-sdd` — author and revise the per-feature PRD/SDD ticket bodies; `/quo-plan` invokes them inline via the Skill tool when initial specs are being authored, and they remain solo-invokable for later revisions (`/quo-write-prd <spec-bee-id>`). The cumulative project-level PRD/SDD continue to exist but are appended to *after-the-fact* by the `doc-writer` agent during execution, reflecting what was actually built rather than forward intent. `/quo-file-issue` is mid-conversation aware (no re-asking discovery questions when context already exists) and supports optional `## Background and rationale` and `## Decisions and rejected alternatives` sections in the body template; doc-divergence observations are now captured in a `## Doc divergence noted` section in the Issue body for `/quo-fix-issue`'s doc-writer to act on, rather than mutating docs at filing time.

**Why.** Three classes of problem motivated the redesign. (1) Drafting a plan that may never execute — or won't execute for weeks — was writing future-state design into project docs that nominally describe current behavior, with manual and error-prone reverts; parallel planning compounded the problem by layering future state for two unbuilt features on top of one another. (2) The "every session is cold" principle forced thorough planning conversations through a "2-3 sentence summary" funnel into the Plan Bee body, losing rationale, rejected alternatives, and constraints; downstream PM agents and engineers re-litigated decisions or re-introduced rejected approaches because no record survived. (3) `/quo-file-issue` had a smaller analog of both — the former filing-time doc-mutation step (since folded into the body-authoring step's optional `## Doc divergence noted` capture) mutated `docs/prd.md` / `docs/sdd.md` when an issue surfaced doc divergence, and the body's shallow template lost the analytical depth of the originating discussion.

**Acceptance criteria.**

- `/quo-plan` no longer writes to the cumulative PRD, SDD, or README. Running it on a Plan that's never executed leaves project docs untouched.
- `/quo-plan` creates a Spec Bee with PRD and SDD `t1=Doc` child tickets, plus a Plan Bee with Epic children whose `reference_materials` is `[{"value":"<spec-bee-id>","resolver":"bees"}]`.
- `/quo-write-prd` and `/quo-write-sdd` exist as composable sub-skills — invokable solo for spec revisions and inline by `/quo-plan` for initial authoring.
- `/quo-plan` distills pre-invocation conversation context into the PRD/SDD child tickets when invoked mid-conversation, instead of restarting discovery from scratch.
- PRD and SDD child-ticket bodies include explicit sections for decisions, rejected alternatives, and rationale — not just requirements.
- `agents/pm.md` and `skills/quo-breakdown-epic/SKILL.md` perform two-hop lookup: read `reference_materials`, follow the `bees` resolver to the Spec Bee, walk the Spec Bee's `t1=Doc` children for PRD/SDD content. The existing `file-path` resolver path and the body-as-spec fallback (when `reference_materials` is null/empty) remain functional.
- `agents/doc-writer.md` is responsible for appending or updating `### Feature: <title>` subsections in the cumulative project PRD and SDD post-implementation, reflecting what was actually built.
- The doc-divergence step in `/quo-file-issue` that previously mutated `docs/prd.md` / `docs/sdd.md` at filing time no longer mutates docs (in the post-redesign flow it is folded into the body-authoring step's optional `## Doc divergence noted` capture); doc-divergence observations are captured in a `## Doc divergence noted` section in the Issue body for `/quo-fix-issue`'s doc-writer to act on.
- `/quo-file-issue` is mid-conversation aware and supports optional `## Background and rationale` / `## Decisions and rejected alternatives` body sections.
- `/quo-setup` colonizes the Specs hive on new repos and detect-and-adds it on existing repos; `/quo-execute`, `/quo-fix-issue`, and `/quo-breakdown-epic` hard-fail with `Run /quo-setup first.` (with a trailing `— Specs hive is not colonized for this repo.` clause) when the Specs hive is missing.
- `/quo-plan-from-specs` continues to work unchanged for the file-based PRD/SDD path, including the `--feature "<title>"` cumulative-spec scoping flow. The Scoped-marker / `scoped_marker_resolver.py` infrastructure is retained — only `/quo-plan` no longer emits markers (because it no longer co-mingles feature content into shared cumulative docs).

**Out of scope.**

- A `/quo-spec-review` quality-review pass over PRD/SDD ticket bodies, parallel to `/quo-engineer-review`, `/quo-test-writer-review`, `/quo-doc-writer-review`. Useful eventually, but separable from the bug fix this feature delivers — deferred to a follow-up Issue.
- A `/quo-file-issue --from-github <url>` (or generic `--reference <url>`) external-reference mode symmetric with `/quo-plan-from-specs`. Real gap, but separable from this feature — deferred to a follow-up Issue.
- Migrating the existing Plan Bees `b.5tm`, `b.9xr`, `b.gar`, `b.kw3` to the new Spec Bee structure. They remain on the old shape; the new flow applies forward.
- Building a GitHub-issue resolver or any other new resolver. The design accommodates them via the existing `reference_materials` abstraction; concrete resolvers are separate work.
- A formal Issue-to-Plan promotion path. The manual workaround (close the Issue, file a Plan referencing it) remains.

### Feature: Add /quo-spec-review skill (apiary /req-review analog)

**What.** Add a `/quo-spec-review` skill that performs a fresh-eyes review pass over the PRD and SDD ticket bodies authored by `/quo-write-prd` and `/quo-write-sdd` under a Spec Bee. Mirrors the shape of the existing `/quo-engineer-review`, `/quo-doc-writer-review`, and `/quo-test-writer-review` skills (severity-tagged work-item list shape; the existing three are now orchestrator-only while `/quo-spec-review` remains dual-mode). Apiary's `/req-review` is the conceptual analog. Default scope reviews both the PRD `t1=Doc` child and the SDD `t1=Doc` child; `--doc PRD` or `--doc SDD` narrows to one child. The skill does not mutate any ticket — it returns a list of improvement work items for the caller (human or orchestrator) to act on.

**Why.** The "Side-effect-free /quo-plan and /quo-file-issue with preserved context" feature (`b.31f`) deferred this work to observe real failure modes from `/quo-write-prd` and `/quo-write-sdd` output before building the reviewer. With those skills now in steady use, this skill closes the four-reviewer parallel (`/quo-engineer-review`, `/quo-doc-writer-review`, `/quo-test-writer-review`, `/quo-spec-review`) and provides a quality gate for Spec Bee `drafted → ready` transitions when spec-authoring or planning skills wire it in as a post-write hook. Standalone use also serves ad-hoc spec-review needs after revisions.

**Acceptance criteria.**

- `skills/quo-spec-review/SKILL.md` exists with frontmatter `name: quo-spec-review` and a precise `description` covering both standalone and orchestrator-invoked modes.
- The skill takes one positional argument `<spec-bee-id>` and one optional flag `--doc PRD|SDD`.
- The skill resolves the Spec Bee's PRD and/or SDD `t1=Doc` children via `bees execute-freeform-query` (regex-anchored exact title match), reads each child's body via `bees show-ticket`, and returns a numbered list of work items in the same severity-tagged shape as the other three review skills (`blocker` / `suggestion` / `nit`).
- The skill carries explicit per-document checklists (PRD: 8 categories tied to the twelve `/quo-write-prd` sections; SDD: 10 categories tied to the seven `/quo-write-sdd` sections) plus a cross-document consistency pass run when both PRD and SDD are in scope.
- The skill does not mutate any ticket; output is text-only.
- The skill hard-fails with `Run /quo-setup first.` when the Specs hive is not colonized.
- README.md skill catalog lists the skill in a row parallel to the other three reviewers, the surrounding "three reviewers" prose is updated to "four reviewers", and the running portable-core skill count is bumped to reflect the new total.

**Out of scope.**

- Wiring `/quo-spec-review` into `/quo-write-prd`, `/quo-write-sdd`, or `/quo-plan` as a post-write gate. The skill is invokable standalone today; orchestrator integration is a separate change those skills can adopt when the integration shape is settled.
- A `## Spec review guide` doc under CLAUDE.md `## Documentation Locations` (parallel to the Test review guide and Doc writing guide entries). The skill's checklists live inline in its `SKILL.md` for now; if a separate guide is warranted later, that's a follow-up.
- Auto-fix or auto-revise behavior — the skill returns findings only, never edits PRD or SDD bodies. The caller decides whether and how to address each finding.
- Spec review of the cumulative project-level PRD/SDD on disk — `/quo-doc-writer-review`'s territory. This skill scopes strictly to Spec Bee `t1=Doc` children.

### Feature: /quo-file-issue: add --reference URL mode for external sources (GitHub, Linear, etc.)

**What.** Add an external-reference invocation mode to `/quo-file-issue` symmetric with `/quo-plan-from-specs` on the planning side. The skill now accepts `--reference <url>` (generic) or `--from-github <url>` (friendlier alias for the GitHub Issues case) alongside the existing in-conversation capture path. In external-reference mode, the Issue body is a thin 2-3 sentence summary and `reference_materials` carries `[{"value":"<url>","resolver":"<name>"}]`, where `<name>` is selected by URL pattern (`github-issue` for GitHub Issue URLs, `linear-issue` for Linear ticket URLs, `url` otherwise). Downstream, `/quo-fix-issue`'s Engineer and PM fetch the upstream content via `WebFetch` and treat it as the spec source — the bees CLI does not yet ship concrete resolver implementations for these names, so the canonical resolver name is written regardless and a real resolver can land later without migrating existing Issue tickets.

**Why.** Today's `/quo-file-issue` only supports the in-conversation capture path: the user describes a bug interactively, the skill creates an Issue with body-as-spec content. This is right for in-conversation discoveries, but it's a gap when the user already has the bug described elsewhere — a GitHub Issue, a Linear ticket, a Slack thread, an internal bug tracker — and just wants quorum to point at it. The redesign work shipped under `b.31f` ("Side-effect-free /quo-plan and /quo-file-issue with preserved context") explicitly deferred this external-reference capability to a follow-up Issue because folding it in would have expanded scope without addressing the original problem any better. This Issue closes that gap, completing the symmetry between the planning side (`/quo-plan` for in-conversation, `/quo-plan-from-specs` for external-reference) and the issue side (`/quo-file-issue` default for in-conversation, `/quo-file-issue --reference` for external-reference).

**Acceptance criteria.**

- `/quo-file-issue --reference <url>` and `/quo-file-issue --from-github <url>` are first-class invocation modes alongside the default in-conversation capture path; the `argument-hint` advertises all three forms (`[<description> | --reference <url> | --from-github <url>]`).
- When an external-reference flag is present, the skill skips the body-template authoring step (Description / Current behavior / Expected behavior / Impact / Suggested fix) and instead writes a thin body containing a single `External reference: <source-class> <url>` convention line plus a 2-3 sentence summary distilled from prior conversation, `WebFetch`-fetched URL content, or — as a last resort — a user-supplied prose summary.
- The skill writes `reference_materials` as `[{"value":"<url>","resolver":"<name>"}]` where `<name>` is `github-issue` for GitHub Issue URLs, `linear-issue` for Linear ticket URLs, and `url` otherwise (URL-pattern heuristic, host-then-path).
- `/quo-fix-issue`'s dispatch prompt embeds the Issue's `reference_materials` JSON value alongside the (thin) body when the field is non-empty, so the worker can read the resolver name and URL.
- The Engineer and PM subagents (`agents/engineer.md`, `agents/pm.md`) fetch the upstream content via `WebFetch` when `reference_materials` carries an external-URL resolver and treat the fetched content as the spec source; both have `WebFetch` in their tool allowlists.
- The README skill catalog row for `/quo-file-issue` documents both invocation modes and explicitly names the external-URL resolvers and the `WebFetch` fallback.
- The `Reference materials` entry in `docs/doc-writing-guide.md` `## Project terminology` lists external-URL resolvers as a third resolver class alongside `file-path` and `bees`.

**Out of scope.**

- Building specific external resolvers (a real `github-issue` resolver, a real `linear-issue` resolver, a generic `url` resolver) in the bees CLI — those are separate Issues filed against `bees` itself or `quorum` as their owners materialize. This Issue establishes the canonical resolver names and the `WebFetch` fallback path; concrete resolver implementations land independently.
- Migrating existing in-conversation-filed Issues to external-reference mode.
- Promoting an Issue to a Plan Bee — the manual workaround (close Issue, file Plan referencing it) remains for now.
- An `--from-linear` / `--from-jira` / per-source CLI alias for every external bug tracker. The current set is `--reference` (generic) plus `--from-github` (alias). Any future per-source aliases fold into the same code path; the resolver-name selection in the URL-pattern heuristic is what differentiates them downstream.

### Feature: Wire /quo-spec-review into /quo-plan, /quo-write-prd, /quo-write-sdd as automatic quality gate

**What.** Wire the previously-standalone `/quo-spec-review` skill into the spec-authoring flow as an automatic quality gate at three sites: `/quo-plan` (post both writer-skill invocations, pre Spec Bee promotion), `/quo-write-prd` invoked solo (post the Step 6 user-approval gate, pre the PRD child's `drafted → ready` promotion), and `/quo-write-sdd` invoked solo (post the Step 7 user-approval gate, pre the SDD child's `drafted → ready` promotion). When a writer is invoked inline from `/quo-plan` it skips its own per-writer review — Site 1 covers both children plus the cross-document consistency pass end-to-end. The skill's frontmatter description and SKILL.md prose now name orchestrator-invoked use as the primary path; standalone use remains supported for ad-hoc spec audits.

**Why.** The "Add /quo-spec-review skill" feature shipped the reviewer as standalone-only — its `## Out of scope` list explicitly deferred orchestrator integration to a separate change "when the integration shape is settled". In practice that meant the quality gate only fired when humans remembered to type `/quo-spec-review` after authoring or revising specs, which is half a feature: PRDs and SDDs were promoting `drafted → ready` (and being consumed by downstream `/quo-breakdown-epic`, `/quo-execute`, and `/quo-fix-issue`) without any fresh-eyes review pass. Auto-invocation closes that gap and brings the spec side into line with the code/doc/test side, where `/quo-execute` and `/quo-fix-issue` already auto-run their reviewers.

**Acceptance criteria.**

- `/quo-plan` invokes `/quo-spec-review <spec-bee-id>` (no `--doc` flag) after Step 4b's writer-skill invocations and before Step 4c's Spec Bee `drafted → ready` promotion. Both children plus the cross-document consistency pass run in this single end-to-end review.
- `/quo-write-prd <spec-bee-id>` invoked solo runs `/quo-spec-review <spec-bee-id> --doc PRD` after Step 6's user approval and before the PRD child's `drafted → ready` promotion.
- `/quo-write-sdd <spec-bee-id>` invoked solo runs `/quo-spec-review <spec-bee-id> --doc SDD` after Step 7's user approval and before the SDD child's `drafted → ready` promotion.
- `/quo-write-prd` and `/quo-write-sdd` invoked inline from `/quo-plan` skip the per-writer review (Site 1 in `/quo-plan` covers it end-to-end) so a single planning run does not pay for two redundant reviews.
- Findings are surfaced to the user via `AskUserQuestion` with severity-aware default options (Revise / Proceed (acknowledge findings) / Proceed anyway (override blockers)). The Recommended option flips with severity — `blocker`-only findings recommend Revise; `suggestion`/`nit`-only findings recommend Proceed.
- Blockers gate `drafted → ready` by default; the override path is supported but recorded in the end-of-skill report so the user has a single view of what was intentionally not addressed before promotion.
- The review-fix-review loop applies a time-budget short-circuit after roughly 10 surfaced items or 3 review turns, mirroring the bound the other three reviewers already enforce in `/quo-execute` / `/quo-fix-issue`.
- `/quo-spec-review`'s frontmatter description and SKILL.md prose reflect that orchestrator-invoked use is now the primary path; standalone use is documented as the secondary path.
- README.md skill-table row for `/quo-spec-review` and the surrounding "four reviewers" prose are updated to drop the "once those wire it in" qualifier and name the three orchestrators that auto-invoke the skill. The workflow diagram annotates the auto-gate inline in the `/quo-plan` branch.

**Out of scope.**

- Wiring `/quo-spec-review` into `/quo-plan-from-specs`. The express path consumes finalized PRD/SDD content from on-disk files, not a Spec Bee's `t1=Doc` children — there is no Spec Bee parent for `/quo-spec-review` to scope to. Spec quality on that path is the user's responsibility before invoking the skill.
- Auto-revising PRD or SDD bodies in response to findings. The reviewer remains text-only; the writer-skill loop-back path is the mechanism for applying findings.
- Persisting overridden-blocker decisions to the PRD or SDD bodies. The end-of-skill report captures them for the user; downstream skills do not read this metadata.
- Changing the severity ladder, checklist contents, or output shape of `/quo-spec-review` itself. The skill's review logic is unchanged — only the invocation surface is.

### Feature: Auto-detect URLs in /quo-file-issue and /quo-fix-issue (no flag required)

**What.** Bare URL tokens (`^https?://`) are now accepted as first-class positional arguments to both `/quo-file-issue` and `/quo-fix-issue`, alongside the existing flag-based forms. URL detection is automatic at argument tokenization — no `--reference` or `--from-github` flag required. `/quo-file-issue <url>` routes to the existing External-reference branch and produces an Issue identical in shape to today's `/quo-file-issue --reference <url>` (thin body with the `External reference:` convention line, `reference_materials: [{"value":"<url>","resolver":"<name>"}]` where `<name>` comes from the existing URL-pattern resolver-name table — `github-issue` / `linear-issue` / `url`). `/quo-fix-issue <url>` files the URL via `/quo-file-issue` (Skill-tool dispatch) and runs the per-issue fix flow against the resolved ticket; `/quo-fix-issue` list mode supports mixed `<id>` + `<url>` argument lists and substitutes URL tokens *in place* in the working list so the user-supplied prerequisite ordering survives. Existing flag forms (`--reference <url>`, `--from-github <url>`) continue to work unchanged as silent no-op aliases on top of detection. A new dedupe path queries open Issues by `reference_materials.value` before filing and surfaces a `Use existing` / `File new` / `Cancel` `AskUserQuestion` on a hit, so re-running `/quo-fix-issue <url>` after a failed run does not silently mint a duplicate Issue.

**Why.** The flag-required model from the previous `/quo-file-issue` external-reference feature was friction: a URL in argument position is unambiguous, no other plausible interpretation exists, and forcing the user to remember `--reference` or `--from-github` is documentation noise. The two-step manual workflow when starting from a URL (file the Issue first, capture the ID, then invoke `/quo-fix-issue <id>`) was the dominant friction point as quorum is adopted into projects with external trackers (GitHub Issues, Linear tickets, Slack archive links, internal bug-tracker URLs) — the URL is the natural artifact to hand to the workflow, and any friction at that boundary translated directly into adoption friction. This feature closes that gap and makes URL-tracker entry points first-class on both issue-side skills.

**Acceptance criteria.**

- `/quo-file-issue https://github.com/owner/repo/issues/123` (no flag) produces an Issue identical in shape to today's `/quo-file-issue --reference <url>`: thin body with the `External reference:` line, `reference_materials` set to `[{"value":"https://github.com/owner/repo/issues/123","resolver":"github-issue"}]`, status=`open`.
- `/quo-file-issue --reference <url>` and `/quo-file-issue --from-github <url>` continue to work — flags accepted as backward-compat no-ops, producing identical Issue shapes to the bare-URL path.
- `/quo-fix-issue https://github.com/owner/repo/issues/123` (no flag) files the Issue (or reuses an existing match per dedupe), then runs the per-issue fix flow end-to-end, producing one git commit on the chosen branch.
- `/quo-fix-issue b.cnb https://github.com/owner/repo/issues/123 b.xet` processes three items in the user-supplied order. The URL token at position 2 becomes a new ticket ID (call it `b.<new>`); the working list resolves to `[b.cnb, b.<new>, b.xet]` and is processed sequentially.
- Before filing a URL, the skill queries open Issues for one whose `reference_materials.value` matches the URL. On a hit, the skill surfaces the existing ticket via `AskUserQuestion` with `Use existing` / `File new` / `Cancel` choices. The matched ticket's ID, title, and status appear in the prompt body so the user can decide intelligently. On multiple matches, all candidates are surfaced with one `Use existing (b.<id>)` option per candidate plus `File new` and `Cancel`.
- Resolver name selection uses the existing URL-pattern table in `quo-file-issue/SKILL.md` — no copy of the table appears in `quo-fix-issue/SKILL.md`. `/quo-fix-issue` delegates URL filing to `/quo-file-issue` via the published `## Inline invocation via the Skill tool` contract section.
- README skill-table rows for both `/quo-file-issue` and `/quo-fix-issue` mention URL mode in the description column.
- Existing `/quo-file-issue` / `/quo-fix-issue` invocation forms (against bees IDs, against `all` mode, against `--reference` and `--from-github` flags, against in-conversation `<description>` strings) continue to work without modification.

**Out of scope.**

- Implementing concrete bees-CLI resolvers for `github-issue`, `linear-issue`, or `url`. The agent-side `WebFetch` fallback in `agents/engineer.md` and `agents/pm.md` already covers it and remains the canonical fetch path.
- Changes to agent role contracts (`engineer.md`, `pm.md`, `doc-writer.md`, etc.) — they already handle external-URL `reference_materials` end-to-end.
- Adding URL handling to other skills (`/quo-plan`, `/quo-plan-from-specs`, `/quo-execute`, `/quo-breakdown-epic`). This feature is scoped to the issue-filing-and-fixing pair only.
- Removing the `--reference` and `--from-github` flag literals from skill prose. They remain documented as accepted alias forms.
- Changes to the external-reference Issue body shape (thin 2-3 sentence summary, optional `## Doc divergence noted`, `External reference:` convention line, `reference_materials` JSON shape).
- Authentication-gated URL handling (private GitHub Issues, Linear tickets behind SSO). The `WebFetch` fallback path already covers public URLs; auth-gated URLs continue to fall back to the "Ask the user" branch in `/quo-file-issue`'s external-reference flow.

### Feature: Fast-path eligibility — canonical-hive completeness check

**What.** `/quo-setup`'s fast-path detector (`skills/quo-setup/scripts/detect_fast_path.py`) gains a fourth eligibility criterion: the on-disk hive set must be a **superset** of the canonical set `{issues, plans, specs}`. **Acceptance criteria.**

- A repo with the canonical three plus extra non-canonical hives (e.g., `.bees/ideas`) remains fast-path eligible — only a strict subset disqualifies.
- The detector's JSON output gains a new diagnostic field, `on_disk_hive_names_superset_of_canonical` (boolean), reflecting the new criterion. `fast_path_eligible` is true iff all four criteria hold (non-empty on-disk hives, no scope already registered for the repo, both CLAUDE.md sections populated, on-disk hive names are a superset of canonical).
- `skills/quo-setup/SKILL.md`'s eligibility-criteria list reads "all four" with the new criterion 4 documented inline; the example JSON payload includes the new field.

**Out of scope.**

- Changes to the slow path's Hive Configuration walkthrough. The existing prompt-to-colonize-missing-hive behavior already handles the strict-subset case once the fast path declines; no behavior change there.
- Migration tooling for older repos. Re-running `/quo-setup` is sufficient — the slow path will surface and colonize the missing canonical hive(s).
- Changes to the canonical hive set itself. The set `{issues, plans, specs}` is fixed by `## Valid configuration` in `quo-setup/SKILL.md`; this fix only ensures the fast path enforces it.

### Feature: Surface a one-time Mode 1 (stop per Epic) vs Mode 2 (work through all) choice at start of /quo-breakdown-epic and /quo-execute runs

**What.** When `/quo-breakdown-epic` or `/quo-execute` runs against a Bee with more than one Epic in scope, the skill surfaces a one-time multi-Epic run mode choice at the start of the run via `AskUserQuestion`, replacing the previous behavior of re-prompting at every Epic boundary. - The captured choice persists for the rest of the run; neither skill re-prompts at subsequent Epic boundaries.
- Mode 2 still pauses on the orchestrator-enforced stops listed in each skill's prose: `/quo-execute`'s drafted-or-blocked-on-drafted Epic stop at the Epic boundary and any `Cancel` at a routing gate; `/quo-breakdown-epic`'s drafted-siblings-with-reshape-risk case in Section 7 and any final reviewer-surfaced blocker.

**Out of scope.**

### Feature: Phase skills silently drop "defer to next session" items at session handoff

**What.** All four phase skills (`/quo-plan`, `/quo-breakdown-epic`, `/quo-execute`, `/quo-fix-issue`) gain a **"Before handoff — deferral hygiene"** gate that fires immediately before the skill yields control at the end of a run. The gate enumerates the active set of `defer-<short-suffix>` TaskList tasks the orchestrator opened during the run (one per item an agent or the orchestrator flagged for "address later", "defer to next phase", "pick up during a follow-up", etc.) and presents the user a three-option `AskUserQuestion`: **Fix in this session** / **File as issue tickets** / **Encode in an existing ticket body**. The gate hard-stops the skill while any `defer-*` task remains `pending` or `in_progress` — the run cannot reach its end-of-skill report / next-steps menu / next-Issue advance / post-completion review until every deferred item lands in a durable inter-session carrier. The three options are mutually-non-exclusive at the active-set level so the user may route different items to different destinations in one reply. `/quo-fix-issue` fires the gate twice in batch mode — once per Issue (scoped to that Issue's deferrals) and once at end-of-batch as a defensive sweep against deferrals surfaced between Issues. When the active set is empty (the dominant case after a smooth run), the gate emits a one-line `Deferral hygiene: no deferred items.` and proceeds without prompting.

**Why.** Before this change, "defer to next session" items surfaced during the run lived only in the assistant's working conversation and were silently lost at session handoff — `/quo-breakdown-epic`, `/quo-execute`, and `/quo-fix-issue` read bees tickets, CLAUDE.md, and source code in their fresh sessions and have zero visibility into the previous session's conversation. Items the PM Agent flagged in its final report, items the Analyst flagged under `### Deferred refinements`, items review skills surfaced that the orchestrator chose not to address inline, and items the user themselves accepted at a gate without authoring an explicit destination all evaporated at the session boundary unless the orchestrator manually translated each one into a ticket-body update or a new Issue before yielding — a discipline that was easy to drop under load. The new pre-handoff gate makes the close-out structural rather than discretionary, and the supporting `defer-*` TaskList convention gives the gate a ledger to read so nothing slips through. The naming convention is **`defer-<short-suffix>`** (e.g., `defer-1`, `defer-2`) to keep it deliberately short and easy to remember across the four skills that emit them.

**Acceptance criteria.**

Deferral hygiene` section of `/quo-execute` and `/quo-fix-issue` carries the "Before handoff — deferral hygiene" gate in the order specified above (between the existing report / commit step and the existing next-steps menu / post-completion review). The gate cannot be skipped — every run of each phase skill executes it before yielding.

The options are mutually-non-exclusive — the user may route different items to different destinations in one reply.

### Feature: Narrate-instead-of-do failure mode persists after b.fpm's prose-strengthening fix

**What.** Workflow gates that fire a prescribed tool call (today the dominant form is `AskUserQuestion`, used at spec-review loop-backs, plan-review verdicts, post-Analyst approval, deferral-hygiene close-outs, and similar finite-choice user prompts) now go through a two-step contract: the orchestrator first creates a `gate-<kind>-<short-suffix>` TaskList task (e.g., `gate-askuserquestion-abc`) via `TaskCreate`, then calls the prescribed tool in the same turn. The two-step shape is wired into the four review skills' output trailers (`/quo-spec-review`, `/quo-engineer-review`, `/quo-test-writer-review`, `/quo-doc-writer-review`), the spec-authoring skills (`/quo-write-prd`, `/quo-write-sdd`), and the four consuming orchestrator skills (`/quo-plan`, `/quo-breakdown-epic`, `/quo-execute`, `/quo-fix-issue`); the contract is anchored in `docs/doc-writing-guide.md` `## The two-step TaskCreate → prescribed-tool contract` and cross-linked from CLAUDE.md `## AskUserQuestion usage`. A new **yield-control discipline** mirrors the existing `defer-*` rule from `b.dgq`: no consuming skill yields control to the harness with active `gate-*` tasks remaining in `pending` or `in_progress` status. Orchestrator-driven gates that fire `AskUserQuestion` without a dispatched-skill trailer (the Analyst-approval gate in `/quo-fix-issue` Section 3, the plan-reviewer verdict gate in `/quo-plan` Step 5e, etc.) are explicitly covered by the same two-step obligation. The user-visible surface shift is brief — a transient `gate-*` TaskList entry visible in the Claude Code UI at the moment the orchestrator is about to fire the prescribed tool call — and the existing `defer-*` ledger surface from `b.dgq` is unchanged. A new **known-limitations** section in `CONTRIBUTING.md` documents the residual failure surface the two-step contract does not close (the orchestrator can still fail to fire the *first* tool call, `TaskCreate`, before yielding) and names the harness / API mechanisms (Anthropic API `tool_choice`, Claude Code harness re-prompt) that would close it definitively.

**Why.** Three layers of remediation against the narrate-instead-of-do failure mode preceded this one: `b.sfy` shipped the `**Next action for the orchestrator:**` routing trailer convention on the four review skills' output (third-person framing, leakage observed in production); `b.fpm` strengthened the trailer to second-person imperative, added counter-anchor clauses (`Do not produce a text response describing this gate — call the tool directly.`), and added pre-commitment lines at each Skill-call site (continued leakage observed). The pattern of evidence — two progressively stronger prose-only variants failing to close the failure mode under load — established that prose-only mitigations are demonstrably exhausted: the failure is a model-adherence phenomenon, not a prose-clarity phenomenon. The structural improvement is that `TaskCreate` is itself a tool call — the orchestrator cannot silently yield a `TaskCreate` invocation the way it can silently yield an `AskUserQuestion` invocation. A missed `gate-*` task is recoverable by next-turn TaskList processing (the next reconciliation tick walks the active set and re-fires the prescribed tool call); a silent prose yield is only recoverable by the user noticing the orchestrator stalled. The new contract narrows the failure surface; the known-limitations note in `CONTRIBUTING.md` records that the b.sfy → b.fpm → b.wii evidence chain has exhausted prose-only remediations so future maintainers do not ship a fourth prose variant against the same problem.

**Acceptance criteria.**

- `docs/doc-writing-guide.md` carries a new `## The two-step TaskCreate → prescribed-tool contract` section that names the two-step obligation, the `gate-<kind>-<short-suffix>` naming convention, the yield-control discipline, the `TaskCreate`-as-tool-call rationale, and the trailer-less-gates carve-out for orchestrator-prose-driven gates.
- The four review skills' routing trailers prescribe the two-step shape inline at every trailer-emit site (findings-present and no-findings shapes alike), naming `gate-askuserquestion-<short-suffix>` as the first-step TaskList task.
- The two spec-authoring skills (`/quo-write-prd`, `/quo-write-sdd`) carry the two-step obligation at the post-user-approval spec-review gate (the gate that fires the dispatched `/quo-spec-review` call).
- The four consuming orchestrator skills (`/quo-plan`, `/quo-breakdown-epic`, `/quo-execute`, `/quo-fix-issue`) honor the yield-control discipline at the same sites their existing `defer-*` discipline lives, and each orchestrator-driven gate that fires `AskUserQuestion` without a dispatched-skill trailer (Analyst-approval, plan-reviewer verdict, deferral-hygiene close-out, multi-Epic run-mode choice, etc.) surfaces the two-step obligation in its prose.
- CLAUDE.md `## AskUserQuestion usage` carries a cross-link to the new contract section so future skill authors land on the load-bearing specification.
- `CONTRIBUTING.md` gains a `## Known limitations` section documenting the residual failure surface, the `b.sfy → b.fpm → b.wii` evidence chain, and explicit guidance that further prose-only variants (more imperative trailers, layered counter-anchor clauses, additional pre-commitment lines, third-person re-framing) are considered-and-rejected.
- The user-typed slash-command surface of every affected skill is byte-for-byte unchanged; no new flags, no new prompts beyond what existing gates already showed.

**Out of scope.**

- Definitive closure of the failure mode at this layer. The two-step contract narrows the failure surface but does not eliminate it — the orchestrator can still fail to fire the *first* tool call (`TaskCreate`) before yielding. Closure requires harness-level enforcement (Anthropic API `tool_choice`, Claude Code harness re-prompt on detected un-fired prescribed tool calls) that this repo cannot author.

The contract is scoped to **gate-firing** tool calls — the ones whose absence stalls the workflow on a user-visible prompt. Non-gate tool calls do not surface the narrate-instead-of-do failure mode in the same way and are not in scope.
- Persisting the `gate-*` TaskList ledger across Claude Code sessions. The ledger is intra-turn (the lifecycle is created-and-completed within a single turn under normal operation), and persistence would not address the failure mode the contract exists to mitigate.

### Feature: Depth-aware finding routing and compromise tracking in /quo-fix-issue and /quo-execute

**What.** Review findings now carry a per-fix-path **depth** dimension alongside their existing severity, and the two execution orchestrators (`/quo-fix-issue`, `/quo-execute`) route findings through a deterministic, depth-aware gate instead of silently absorbing them into a re-dispatch prompt. Three depth tags — `trivial-tweak`, `refactor-locally`, `re-architect` — describe how invasive each proposed fix path is; reviewers also enumerate every fix path they see rather than collapsing to one. The orchestrator turns the `(number-of-fix-paths, maximum-depth)` tuple into exactly one routing decision: a single low-depth fix (`trivial-tweak` or `refactor-locally` on one path) auto-dispatches the implementer with no interruption, while a single `re-architect` path or any multi-path finding stops at a **routing-decision gate** that presents the user one choice per surfaced fix path (with the reviewer's preferred path marked Recommended when it expressed a preference), a `Defer to follow-up Issue` choice, and a `Cancel` choice. A separate **scope-bounding gate** fires whenever the orchestrator would otherwise narrow a fix — replacing the previously-silent "out of scope for this issue" / "prefer option (a)" dispatch-prompt directives with an explicit three-choice prompt (`Fix properly now` / `Defer to follow-up Issue` / `Accept the limitation`) so scope narrowing is always a decision the user sees and makes.

**When the gates fire was superseded by `b.nn8`** (see the **Routing table gates every multi-path finding; default to orchestrator picking the highest-quality path, gate only re-architect/scope** feature below). "Any multi-path finding stops at a gate" is no longer true, and the `(number-of-fix-paths, maximum-depth)` tuple is no longer what decides. The orchestrator now picks the highest-quality fix path itself and gates only on the chosen path's properties — `re-architect` design direction, scope beyond the ticket or breaking changes, a path that introduces new machinery, a path narrower than the complete fix, or an unreadable emission. Everything else dispatches without a prompt. The scope-bounding gate and the routing-decision gate both still exist, except that a `blocker` can no longer be accepted at either one, and can be deferred only paired with a narrowing that still covers the reported defect.

Every time the user (or an auto-route) accepts a less-than-ideal outcome, the run records it in a **session-scoped compromise tracker** — a per-run file under `<tempdir>/.quorum/` that accumulates one entry per accepted compromise across the whole single/list/`all`-mode run. At the end of the run, an **Accepted compromises** surface in the end-of-run summary lists every tracked compromise in full (the section is omitted entirely when the run accepted none, which is the common case — **`b.nn8` inverted this**: because an ungated orchestrator path pick is now recorded — every one except a finding whose sole fix path is a trivial tweak — most runs render the surface rather than omitting it). The post-completion review is reframed to **lead with challenging the accepted compromises on their merits** — re-asking whether each compromise was actually the right call, including plausibility checks on whether an auto-routed `refactor-locally` fix was really shallow enough to skip the user gate (depth-misjudgment) and whether a reviewer under-enumerated the available fix paths (under-enumeration) — before sweeping for fresh discrete defects. When a challenge lands, a recovery gate lets the user file a follow-up Issue, record an explicit override, or pause to address it, updating the original tracker entry rather than minting a duplicate.

**Why.** Before this change, the orchestrators flattened every review finding into a single re-dispatch with the fix inlined, and routinely narrowed scope by writing directives like `"out of scope for this issue"` or `"prefer option (a)"` straight into the implementer's dispatch prompt. Two failure modes followed. First, **invasiveness was invisible**: a finding that genuinely required re-architecting was dispatched with the same ceremony as a one-line tweak, so the user never got a say on the expensive ones while being un-interrupted by the cheap ones — exactly backwards from where attention is worth spending. Second, **scope narrowing was silent**: the inlined "out of scope" directives quietly shrank fixes without the user ever seeing the decision, and the resulting compromises evaporated at run end with no durable record, so nobody revisited whether they were the right calls. Making depth a first-class reviewer-emitted dimension lets the orchestrator spend user attention proportionally (auto-handle the shallow, gate the deep), turning scope-bounding into an explicit gated decision closes the silent-narrowing hole, and the compromise tracker plus the reframed post-completion review give every accepted compromise a durable ledger and a structured second look before the run closes.

**Acceptance criteria.**

- The in-flow review skills (`/quo-engineer-review`, `/quo-doc-writer-review`, `/quo-test-writer-review`) and `/quo-spec-review`, plus `/quo-plan` Step 5e's plan-review emission, tag each fix path with a depth (`trivial-tweak` / `refactor-locally` / `re-architect`) alongside the existing severity tag, and enumerate every fix path rather than collapsing to one. The three reviewer-wrapper subagents (`agents/code-reviewer.md`, `agents/doc-reviewer.md`, `agents/test-reviewer.md`) name the depth dimension in their output contracts and defer the shape to the wrapped skill.
- `/quo-fix-issue` and `/quo-execute` each carry an "Orchestrator discipline: routing review findings" section with a deterministic routing table keyed on `(number-of-fix-paths, maximum-depth-across-paths)` that maps every tuple to exactly one decision: single-path `trivial-tweak` or `refactor-locally` auto-dispatches the implementer with no user gate; single-path `re-architect` or any multi-path finding fires the routing-decision gate. **(Superseded by `b.nn8` — the section survives, but the tuple key does not: the orchestrator picks a path first and routes on the chosen path's own properties. See that feature's acceptance criteria below.)**
- The orchestrator MUST NOT inline scope-bounding directives (`"out of scope for this issue"`, `"prefer option (a)"`, and close paraphrases) into a re-dispatched implementer's prompt — that anti-pattern is called out explicitly. ### Feature: Pin reasoning effort per role; drop the Sonnet downgrade prompt

**What.** Reasoning effort is now a property of each role rather than a single session-wide dial. Every subagent quorum dispatches carries its own effort level in its `agents/<role>.md` file: the two adversarial roles run at `xhigh` — the Analyst, which diagnoses root cause before any code is written, and the Code Reviewer, which hunts for what no test covers — and the remaining six (Engineer, Test Writer, Doc Writer, PM, Test Reviewer, Doc Reviewer) run at `high`. All eight stay on Opus. These pins override the operator's session effort rather than inheriting from it, so run quality no longer depends on whatever each engineer happened to have set in `/model`.

The run-start prompt that offered to downgrade "support roles" (Doc Writer, PM, Doc Reviewer) to Sonnet is deleted from `/quo-execute`, `/quo-fix-issue`, and `/quo-breakdown-epic`. Its slot is reused for a **conditional session-effort gate**: each of those three skills reads the session's current effort and compares it against its own floor — `medium` for the two execution orchestrators, `high` for `/quo-breakdown-epic`. The gate fires **only** when the session is strictly below that floor, naming the current setting, the floor, a per-skill rationale, and a reminder that subagent effort is pinned and unaffected; it offers to proceed anyway or to exit so the operator can change the setting and re-invoke. At or above the floor it produces no output at all, and when the session effort cannot be read the gate is skipped rather than fired. Running hotter than the recommendation is never prompted on. The README gains a section giving the recommended session setting for every skill a user invokes directly — including the five planning and spec-review skills that deliberately carry no gate, for which it is the only user-visible carrier — plus the statement that subagent effort is pinned per role. The three orchestrator-only reviewers (`/quo-engineer-review`, `/quo-test-writer-review`, `/quo-doc-writer-review`) get no row: they never run as the operator's own session, so there is no session setting to recommend.

**Why.** Two problems, both in the direction of quality rather than cost. First, effort had no per-role expression: one `/model` setting governed root-cause analysis, implementation, adversarial code review, and doc prose identically, so an operator on `medium` got medium-effort root-cause analysis feeding every downstream Engineer dispatch. Pinning per role puts reasoning depth where it pays off and makes the choice a reviewable diff instead of invisible per-machine state. Second, the one model lever that did exist was a cost control on a workflow whose stated objective is output quality, and it doubled as a footgun — one of the three roles it downgraded was the PM, which is the spec-traceability and scope-creep gate, so a cost-conscious operator was downgrading a gate without realizing it. It also asked a question the operator could not answer at time zero, before knowing whether the run was trivial or gnarly, over a grouping that was not cognitively coherent. Replacing it with a floor-comparison advisory keeps the net gate count flat while surfacing something the operator can actually act on.

**Acceptance criteria.**

- All eight `agents/<role>.md` files pin both model and effort: Analyst and Code Reviewer at `xhigh`, Engineer, PM, Test Writer, Test Reviewer, Doc Writer, and Doc Reviewer at `high`, with `model: opus` unchanged on every one. No reviewer is pinned below the role it reviews.
- The run-start Opus/Sonnet prompt is gone from `/quo-execute`, `/quo-fix-issue`, and `/quo-breakdown-epic`, along with every downstream reference to the operator's model choice; `model: opus` on the Doc Writer, PM, and Doc Reviewer is unconditional.
- Those same three skills fire a session-effort gate only when the session is strictly below their floor (`medium`, `medium`, `high` respectively), and are otherwise silent. The gate offers exactly two paths — proceed, or exit to change the setting — and states that subagent effort is pinned and unaffected. When the session effort cannot be read, the gate is skipped.
- No other skill gains a run-start prompt. `/quo-plan`, `/quo-status`, and `/quo-file-issue` are unchanged.
- The README carries a session-settings section with the recommended setting per surface and the pinned-per-role statement.
- The user-typed invocation surface of every skill is unchanged — no new flags or arguments.

**Out of scope.**

- Per-project effort overrides. The pinned table is global, so a docs-heavy project and a docs-light one get identical tiers, and the only escape hatch is hand-editing installed agent files. A CLAUDE.md contract key for per-project overrides is the natural follow-up; adding a contract key is a larger change than this warranted.
- Making the session-setting recommendation enforceable. Two routes were considered and both were cut. Writing the operator's effort into their Claude Code settings is a categorically more invasive act — quorum's install surface is the skills and agent files it ships, and per-machine config in a shared file has broken collaboration here before. Pinning `effort` in a skill's own frontmatter is technically available but solves the wrong problem: it *overrides* the session, so it would pull an operator who deliberately launched hotter back down to the recommended level. The recommendation is a floor, and a floor is not expressible as an override. The most the workflow can legitimately do is name the floor and prompt when the operator is under it.
- Downgrading any role to a cheaper model. Moving the fan-out roles to Sonnet was considered and cut: it is a cost optimization, and cost is not this workflow's objective — against a quality goal those moves are regression risks with no offsetting benefit.
- Escalating a role's effort automatically when review fails. Re-dispatching an implementer at a higher tier after repeated reviewer findings is sound in principle but unproven, and depends on a capability not verified here (whether effort can be overridden per dispatch rather than only pinned in frontmatter).
- Measuring whether the tiering helped. There is no eval harness in this repo, so every tier reflects reasoning about what roles do rather than evidence about what they produce. That gap is real and is separate work.

### Feature: Context-window guard for long orchestrator runs

**What.** The three long-running orchestrators — `/quo-execute`, `/quo-breakdown-epic`, and `/quo-fix-issue` — now stop themselves before context usage climbs high enough to trigger an ill-timed automatic compaction partway through a unit of work. At each Epic boundary (execute/breakdown) or Issue boundary (fix), the orchestrator checks how much of the context window is in use, and when that has climbed far enough that starting another unit would risk an auto-compaction mid-unit, it stops and recommends the operator begin a fresh session and re-invoke. Stopping cleanly at a boundary — where all work is committed and ticket state is externalized — is strictly better than a compaction landing in the middle of a unit.

**Configure-now gate.** The usage reading is supplied by a per-session status-line gauge. When no reading is being published in the environment — the guard sees a `missing` state — the orchestrator fires a hard-stop gate offering to configure the producer inline via `/quo-setup --configure-gauge-producer`, so the operator can turn the guard on without abandoning the run.

**Persistent opt-out.** An operator who wants to run without the missing-reading hard stop can write the persistent run-unguarded marker (via `/quo-setup`; its per-OS location and its delete-to-re-enable behavior are documented in the README rather than restated here). That opt-out is deliberately narrow: it suppresses ONLY the hard stop that fires when no reading is available. It never suppresses a genuine over-threshold stop — when a real reading is present and crosses the stop point, the orchestrator still stops regardless of the marker.

**Silent carve-out.** When the session identifier is unavailable (`CLAUDE_CODE_SESSION_ID` unset), the guard is skipped silently — no gauge file can be keyed to a session without it, so there is nothing to check, and no gate and no diagnostic fire.

**Why.** The harness compacts context automatically once the window fills, and a compaction that lands mid-unit is disruptive even though a companion change (see the b.ja9 feature) makes it lossless. The model cannot read its own context usage, so it cannot self-govern; the gauge bridges that gap by publishing a reading the orchestrator can consult at a natural stopping point and act on before the harness would.

**Acceptance criteria.**

- Each of the three orchestrators performs the boundary check at every Epic/Issue boundary and stops with a fresh-session recommendation when the reading is at or above the stop threshold.
- A `missing` reading fires the configure-now gate offering `/quo-setup --configure-gauge-producer`, unless the persistent opt-out marker is present.
- The opt-out marker suppresses the missing-reading hard stop only, never an over-threshold stop.
- An unset session identifier skips the guard silently.

**Out of scope.**

- Reading context usage without the status-line gauge. The model has no native access to its own usage, so the producer/consumer gauge is the only available signal; there is no fallback measurement.
- Auto-continuing in a fresh session on the operator's behalf. The guard stops and recommends; starting the new session stays a deliberate operator action.

### Feature: Sequence lanes strictly: Engineer + code review to clean before Test Writer / Doc Writer run once; ask reviewers for second-order effects

**What.** `/quo-fix-issue` no longer dispatches the Engineer, Test Writer, and Doc Writer against an Issue at the same time. It walks each Issue through three ordered phases instead: the Engineer and the Code Reviewer loop until the code review comes back clean (or every remaining finding has been explicitly routed), *then* the Test Writer and Doc Writer run once against that settled diff, *then* the Test Reviewer, Doc Reviewer, and PM review what landed. A later finding whose fix changes source re-enters the Engineer loop, and only the writer lanes that source change actually invalidated are re-run. The visible effect is fewer rewritten docs and tests per issue: previously every code-review round that touched source obsoleted the documentation and the test assertions written against the older diff, so the same doc and test work was redone once per round.

`/quo-execute` keeps its forward per-Subtask fan-out concurrent — an Engineer working Subtask N+1 still overlaps a Test Writer on Subtask N, because the ticket graph already sequences that work — and adopts only the ordered re-dispatch rule: a review finding whose fix changes source goes Engineer, then code review, then the affected writer, rather than all at once.

**Reviewers now report second-order effects.** Code review answers a second question alongside "is this correct?" — for each change in the diff, what does it newly expose, weaken, or allow to fail? A new log line on a path that previously could not fail, a rename that changes an externally-observable metric or span label, a statement that moved across a validation boundary: consequences that were previously only discovered a round later, once the fix had landed. The check covers the whole change set including first-party dependencies the same team owns, not just the primary package, and every review emits the section — including clean ones. Anything actionable it surfaces is also raised as an ordinary numbered finding, so it is routed like any other. Each issue's (and each Task's, and the Bee's) end-of-run summary carries a **Second-order effects** field, so the narrative reaches the person reading the summary rather than stopping at the orchestrator.

**Sweep completeness evidence.** When an assignment tells the Engineer to change *every site* where some property holds, its return must now carry the evidence — the search patterns it ran, every hit those patterns produced, and for each hit either the change made or the reason it was deliberately left alone. The reviewer checks the diff against that list instead of rediscovering sites itself, so an incomplete sweep surfaces once as a gap in the list rather than as one newly-found site per review round.

**Writers report instead of guessing when the tree moves.** A Test Writer or Doc Writer that notices the source it is working against changed underneath it stops and reports rather than finishing against half-landed behavior. The run does not silently drop that work: the redelivery is recorded as an outstanding obligation, the lane is re-dispatched once the source settles, and the review phase does not begin until it delivers. When the orchestrator cannot account for who moved the source — it dispatched no Engineer, and no concurrently-running Test Writer's recorded experiment explains it — it stops and asks, offering to re-dispatch now, wait while the change is resolved, or abort the issue. Test Writers also no longer reach for `git checkout` / `git stash` / `git restore` on files outside their lane when temporarily perturbing a source file to prove a test fails; they copy the file aside and restore from the copy, so an Engineer's uncommitted work is never transiently discarded.

**Why.** A worked run of the previous design (an issue fixed across seven Engineer rounds) showed the costs directly. The Doc Writer ran three times and the Test Writer three times, once aborting mid-run because a concurrent Engineer round landed in the source after the orchestrator had promised it a stable tree — every one of those extra runs existed only because the writers had been handed a diff that code review was about to change. Rounds later in the same run that happened to follow the ordering proposed here produced zero writer rework. Separately, a code-review round found that a log line added two rounds earlier could raise on a lapsed credential after a resource had been declared — a consequence of the earlier fix that nobody had been asked to look for, so it cost a full extra round to surface. And four consecutive Engineer rounds each closed "the last" site of a sweep and declared it complete, with the next review showing one more each time; asking for the evidence instead of the claim collapses that into a single round.

**Acceptance criteria.**

- `/quo-fix-issue` dispatches an Issue's lanes in three ordered phases — Engineer looping with the Code Reviewer until clean, then the Test Writer (when tests need changing) and Doc Writer (always) once, then the Test Reviewer, Doc Reviewer, and PM — and never dispatches an Engineer while a writer, a reviewer, or the PM for that Issue is still working.
- A review finding whose fix changes source re-enters the Engineer loop in both execution skills, and only the invalidated writer lanes are re-run afterwards. A finding confined to a writer's own lane re-dispatches that writer alone.
- `/quo-execute`'s forward per-Subtask fan-out remains concurrent; only its review re-dispatch path is ordered.
- Code review emits a second-order-effects section on every review, clean ones included, covering first-party dependencies as well as the primary package; anything actionable in it is also emitted as a numbered finding. The per-issue, per-Task, and end-of-run summaries each carry a **Second-order effects** field, which is rendered even when nothing was found.
- An Engineer return on a sweep-shaped assignment carries the patterns run, every hit, and a per-hit disposition; every Engineer return carries an explicit list of the files it changed.
- A writer that detects source movement stops and reports; the run records the owed redelivery, holds the review phase until the lane delivers, and asks the user what to do when the movement cannot be attributed to work the run itself dispatched.
- Test Writers do not run `git checkout` / `git restore` / `git stash` / `git reset` against any path outside the test lane.
- The user-typed invocation surface of both skills is unchanged — no new flags or arguments.

**Out of scope.**

- Ordering `/quo-execute`'s forward per-Subtask fan-out. Overlapping an Engineer on one Subtask with a writer on another is a designed property of dependency-ordered execution, not the failure this change addresses.
- Promising writers a frozen source tree. The orchestrator cannot stop the user, a second session, or a background process from editing files, so what it states is the rule it actually controls — that it will not dispatch an Engineer for this unit while the writer runs — and the writer verifies rather than trusting.
- Terminating an in-flight Agent. There is no mechanism for it, so an aborted unit marks its tasks closed and ignores the stray completion notification when it arrives.
- Front-loading the analysis that would remove these rounds entirely. A broader up-front blast-radius sweep is tracked separately; this change makes the rounds cheaper rather than eliminating them. (That sweep shipped next — see the following feature.)

### Feature: Analyst must produce a blast-radius sweep and name implied policy decisions at the design gate

**What.** The design proposal `/quo-fix-issue` shows you before it writes any code now carries two more things, on every issue.

The first is a **blast radius**: for each invariant the proposed fix adds, removes, or weakens, the enumerated list of places that invariant is visible or assumed — source logic, log lines, trace attributes, metric labels, error and exception text, comments, configuration and deployment manifests, customer docs, internal docs, tests — each with a file and line and **the search pattern that found it**, so you can re-run the sweep yourself and judge whether it was wide enough. The sweep follows the change into first-party dependencies your team owns, not just the package the issue names. When the fix introduces something new — a state, a setting, a persisted or wire field, a background task, an error type, a metric / log / trace attribute, a name class, a gate, a retry or fallback path — the sweep also names where that thing is created, read, changed, torn down, observed, and documented, on every exit path; a missing leg is reported to you as a design gap at the gate instead of being found one leg per review round.

The second is **the policy questions the fix forces but the issue never settled** — "is this value sensitive once the change lands?", "does this validation apply on every surface or only the one the issue names?" — each with what a yes costs, what a no costs, and the analyst's recommended answer. Approving the proposal ratifies the design, those recommended answers, and any recommendation to split a distinct concern out into its own issue, in the one decision you were already making. There is no second prompt and no new option.

Both sections appear on every proposal, including when there is nothing to report: you see `No invariant added, removed, or weakened.` rather than a missing heading, so "swept and found nothing" never looks like "never swept".

Downstream, the site list is handed to the engineer as the list the fix is expected to cover, and to code review, which checks the diff against it: a listed site the fix neither changed nor explained is raised as a normal finding, while a site the fix touched that the list never had is recorded as a gap in the analysis rather than sent back for another fix round, when the fix already handles that site correctly — a site the fix gets wrong is raised as a normal finding like any other.

**Engineers stop instead of inventing.** When implementing the approved design would require adding something the design did not enumerate, the engineer implements everything else, stops, and returns the question. In `/quo-fix-issue`, on the forward fix path — before the issue is closed out — that comes straight back to you as the same design gate on a revised proposal: the analyst re-reads the codebase with the partial fix already on disk and returns a proposal that accounts for the new piece. You approve, revise, or cancel exactly as before, and implementation resumes from what already landed. The same question raised later, while fixing a post-completion review finding, takes the other route — there is no analyst left to revise anything by then, so it is filed as a follow-up issue carrying the question, and the report tells you which of that finding's edits already landed.

**Why.** On a worked reference run, a design approved at round one still cost five engineer rounds, three test-writer rounds, three doc-writer rounds, and three code reviews across roughly thirty files — because the sites the change touched were discovered one per review round, and because a policy question nobody asked ("is this value a secret now?") got settled implicitly, mid-stream, by whichever role tripped over it first, each time obligating an unplanned sweep behind it. Every one of those sites was findable by search before implementation. A second run in this repo showed the other half of the pattern: three of six rounds went to the lifecycle of one new mechanism being designed piecewise by review, each round finding the one leg the previous fix had missed. Asking for the sweep and the questions once, at the gate, replaces that with a single up-front pass — and asking for the *patterns* rather than the conclusion is what makes the sweep auditable, since the same run showed reviewers verifying a claim's consistency across surfaces rather than its truth.

**Acceptance criteria.**

- Every design proposal `/quo-fix-issue` surfaces carries a blast-radius section and a policy-decisions section, both shown to the user in full, and both present with a fixed "nothing found" line rather than omitted when there is nothing to report.
- Blast-radius entries are grouped by kind and carry a file/line reference plus the verbatim search pattern that found them; a "none found" entry names the pattern that was tried; a rename or removal records both the old and the new spelling; the sweep covers first-party dependencies the team owns.
- Anything the fix newly introduces has its full lifecycle enumerated — created, read, changed, torn down, observed, documented — in every scope the change touches and on every exit path, with a missing leg reported at the gate.
- Each policy question carries the consequence of yes, the consequence of no, and a recommended answer. Any claim about what holding or seeing a value grants is stated in terms of the checks the system still applies to it, with evidence, rather than as an unqualified "secret".
- Approving covers the design, every recommended policy answer, and any scope-split recommendation. No new gate, option, or prompt is added.
- The blast radius reaches code review, which raises an unaddressed listed site as a normal finding and records a diff-touched site missing from the list as a gap in the analysis rather than a new fix round when the fix already handles that site correctly.
- An engineer that would have to invent something the approved design did not enumerate returns the question instead. In `/quo-fix-issue`, on the forward fix path before the issue is closed out, the question comes back to the user as the same design gate on a revised proposal, and implementation continues from the partial work already on disk; the same question raised while fixing a post-completion review finding is filed as a follow-up issue carrying it, rather than reopening the gate.
- The user-typed invocation surface of `/quo-fix-issue` is unchanged — no new flags, no new arguments.

**Out of scope.**

- Bringing the design gate to `/quo-execute`. Execute mode handles design analysis upstream at plan time and has no analyst; the stop-instead-of-invent rule binds its engineers, but routing such a question in execute mode is tracked separately, as Issue `b.eid` — recorded there when the fix-mode half shipped, rather than in that issue's original scope.
- Handing the policy decisions to code review the way the blast radius is handed to it, and handing either to the test writer and doc writer. Tracked as follow-up Issue `b.ag8`.
- Tagging findings whose fix would require new machinery, and the convergence brief that would consume the tag. Tracked as sibling Issue `b.nn8`.
- Guaranteeing a one-round fix. The sweep moves discovery earlier and makes it auditable; it does not promise that no review round finds anything.

### Feature: Routing table gates every multi-path finding; default to orchestrator picking the highest-quality path, gate only re-architect/scope

**What.** `/quo-fix-issue` and `/quo-execute` interrupt far less often during review rounds. Previously, any review finding for which the reviewer listed more than one way to fix it stopped the run and asked the user to choose — and reviewers list two or three ways for most substantive findings, so most substantive findings became a prompt. The orchestrator now **picks the fix path itself** and dispatches it, choosing the highest-quality path rather than the cheapest: the smallest change that leaves the code compiling, the tests passing, and every surface consistent with what the ticket says. How much work a path is never breaks the tie. The reviewer's own preference is an input to that choice rather than the answer — when the reviewer prefers a narrowing and a fuller path is still the smallest complete change, the fuller path wins.

**When none of the offered fixes is a complete fix, the run asks rather than inventing one.** The orchestrator only ever picks from the paths the reviewer listed. If every listed path would leave part of the reported defect unfixed, it picks the most complete of them and the **scope gate fires**, where `Fix properly now` dispatches the complete fix — so a short list surfaces as a prompt instead of being absorbed silently — the user sees the menu it fired on, in session. (When the finding is too malformed to carry a usable depth tag, the routing gate fires instead, and the user picks among the paths as the reviewer wrote them.) What survives the run depends on the answer given at the scope gate: deferring the fix to a follow-up Issue, or accepting the limitation, leaves a record in the run's compromise tracker that the end-of-run review reads, while answering "fix it properly" settles the finding in place and leaves no record of the short list behind.

**Deferring a fix says what shipped instead.** When the user defers a fix at the **scope gate** — the one that asks whether a fix belongs in this unit at all — what ships this round is the most complete of the remaining paths the reviewer listed, and if the deferred path was the only one listed, nothing ships this round and the run says so. A deferral taken at the **routing gate** ships nothing against the finding this round however many paths were listed: that gate asks which path to take, and deferring there is the answer "not one of them, now". The orchestrator never invents a smaller fix to fill the gap. The run's record names which remaining path shipped, by letter, or that none did, so a later reader can tell a partly-fixed finding from an unfixed one. On a deferred `blocker` — the one case where deferral ships a narrowing rather than one of the reviewer's other paths — that slot instead records what was narrowed away and why the blocker no longer describes anything that ships.

Gates are now reserved for the decisions that are genuinely the user's, and they are decided by the path the orchestrator chose rather than by how many paths the reviewer listed:

- **Design direction** — the chosen path is a `re-architect`.
- **Scope** — the chosen path moves a published contract surface beyond what the ticket says, or breaks existing consumers.
- **New machinery** — the chosen path adds a mechanism the ticket never asked for (a new state, configuration surface, persisted or wire field, background task, error type, metric or log attribute, identifier class, gate, or retry path). Here the recommended answer is to **defer it to a follow-up Issue** carrying the reviewer's sketched design verbatim, so nothing is lost and the current run does not grow a mechanism with its own lifecycle to design.
- **Narrowing** — the orchestrator would otherwise ship something less than the complete fix. It still cannot narrow silently; that has always been a gate and remains one.
- **An unreadable finding** — no depth tag, or a malformed one. Unchanged: the run still asks.

**Blockers are never accepted, and are deferred only alongside a narrowing.** At either gate, a `blocker`-severity finding loses `Accept the limitation` outright — accepting a blocker ships it. At the **scope gate** it gets a pair it always has, and that pair is the whole set unless the deferral choice below opens: `Fix properly now`, plus **re-dispatching the Analyst** in `/quo-fix-issue` — the right answer when the finding shows the approved design itself was wrong rather than its implementation — or **`Cancel`** in `/quo-execute`, which has no Analyst and expresses the same *stop and re-plan* answer by ending the run. At the **routing gate**, which asks which path to take and so has no `Fix properly now` to offer, it gets one choice per fix path the reviewer listed, plus `Cancel` — and in `/quo-fix-issue` that same Analyst re-dispatch alongside them. At either gate an additional choice, `Defer to follow-up Issue`, appears only when the fix the blocker needs would add machinery **and** that machinery serves something outside the defect the ticket reported — so the change can be narrowed back to the reported defect, still be complete, and leave the blocker describing nothing that ships. The narrowing may never cost coverage of the reported defect: a blocker that cannot be sidestepped without leaving part of that defect unfixed is in scope and gets the choices above, never a deferral. Where deferral is available it is the recommended answer, and it never ships alone — the follow-up Issue is filed first, and the narrowing goes out only once that Issue exists. When the finding was too malformed to carry any fix path at all, `/quo-fix-issue` recommends the Analyst re-dispatch (a blocker with no shape to route being exactly what a fresh design pass is for), and `/quo-execute` offers `Cancel` alongside an invitation to direct the fix in prose. Choosing the Analyst re-dispatch takes the run back through the design-approval gate — it is reachable from either review phase now, so approving the revised design resumes implementation against the work already in the tree, and everything raised against the superseded design is dropped rather than acted on — not just reviews still running, but the other findings from the same review that fired the gate.

The post-completion review treats an accepted blocker — or one deferred with no record of what was narrowed, or with a narrowing that left the reported defect partly unfixed — as a contract violation and raises it at blocker severity — with no recovery gate of its own, since there is nothing to recover from a choice the gates should never have offered; it is dispositioned by the post-completion review's own Fix / File / Skip gate, where fixing it in this session is the recommended answer. The PM reviewing an individual unit raises one too, but only for the unit it is looking at: a violation left behind by an earlier unit is mentioned once in passing rather than re-raised as a fresh blocker in every unit that follows, against a scope that could not fix it anyway. One the diff under review has **already resolved** is mentioned in passing too, for a different reason: the check reads the run's record and never edits it, so a stale entry describing settled work must not keep firing.

**Every ungated pick that was a choice is on the record.** Each path the orchestrator chooses without asking is recorded in the run's compromise tracker with its own one-line reason, why that path was the smallest complete change, and the end-of-run **Accepted compromises** summary therefore renders on most runs rather than rarely. (A finding the reviewer gave exactly one trivially-shallow way to fix is the one exemption; the acceptance criteria below state it.) The fresh-eyes post-completion review challenges each of those picks on two questions: was the depth judgment plausible, and did the chosen path quietly build machinery that should have been deferred or put to the user? Either challenge opens a recovery gate offering to file a follow-up Issue, record the override, or pause and discuss.

**Cancelling at a gate now ends the unit properly.** `Cancel` used to exit on its own terms. It now runs the full close-out an aborted unit gets: outstanding obligations swept, deferred items moved into durable carriers, run state written out. This applies wherever `Cancel` is offered — at the routing gate in both skills, and at `/quo-execute`'s scope gate, where a blocker is offered it. Two consequences the user sees — in `/quo-fix-issue` batch mode with Issues still queued, the run **stops** and names the aborted Issue, the uncommitted files, and the resume command for the rest, rather than carrying a dirty tree into the next Issue; in `/quo-execute`, `Cancel` **ends the run** rather than skipping to the next Task.

**Reviewers flag machinery-introducing fixes.** Code review tags any fix path that requires new machinery, so the orchestrator routes it to the scope gate without having to infer it, and sketches the machinery in the path description so a deferral loses nothing.

**Why.** On a worked reference run, the orchestrator fired one prompt carrying three multi-path findings and the user rejected it outright — *"I have no idea what you're talking about — what's the best approach to fixing this? Remember that we don't care about how much work, we care about best quality outcome."* The orchestrator then picked the most complete path for each and proceeded, and the outcomes were uncontroversial. The gate had cost a turn, produced no information the orchestrator lacked, and asked the user to acquire context they did not want. Path count turned out to carry no signal about whether a decision was the user's.

A second run supplied the other half. Of roughly thirty-five findings after the first review round, only a handful concerned what the ticket had asked for; the rest concerned machinery that had not existed when the run began — a receiver, a marker, a gate, per-scope close-outs. Each new mechanism has a lifecycle across several surfaces, so each one generated further rounds. The old routing had no notion of "this fix adds a mechanism", and the orchestrator, told to pick the highest-quality path, read that as "structurally complete every time" and grew the change set round over round. Defining highest-quality as the smallest *internally consistent* change, and routing mechanism-introduction to a gate whose recommended answer is to defer, is what stops a fix from becoming a design project. Under this rule that run would have closed around round two with two or three follow-up Issues instead of six rounds.

During the run the orchestrator was briefly allowed to write a fix path of its own when the reviewer's list held no complete one — that same second run had recorded two orchestrator-written fixes in its own compromise tracker while the rules said picks were limited to the reviewer's list. The post-completion review judged that an extension of the orchestrator's authority beyond what this change set out to do, and it was removed: the run picks the most complete listed path and lets the scope gate surface the shortfall, whose `Fix properly now` answer dispatches the complete fix anyway. Whether the orchestrator should ever write its own path is filed as a separate decision (`b.kxx`) rather than settled inside a routing change.

**Acceptance criteria.**

- Both execution skills route a review finding by first picking the highest-quality fix path and then evaluating conditions against **that path**, in a fixed order, taking the first match. Path count is not a routing input, and a multi-path finding does not gate by virtue of being multi-path.
- "Highest-quality" is defined in the skill prose rather than left to orchestrator judgment: the smallest change under which the code compiles, the tests pass, and every surface agrees with the invariant the ticket names, with total-system complexity counting against a path, effort never the tiebreaker, and "adds a mechanism" a reason to gate rather than to build. For prose-only change sets the compile-and-pass clause reads as "every surface states the invariant consistently".
- A gate fires when the chosen path is a `re-architect`, moves a published contract surface beyond the ticket or is breaking, introduces a mechanism, or is narrower than the complete fix — and when the finding has no usable depth tag. Otherwise the chosen path is dispatched with no prompt.
- The orchestrator's pick is always one of the paths the reviewer listed. When none of them is the complete fix, it picks the most complete one and a gate fires — the scope gate, whose `Fix properly now` dispatches the complete fix, or the routing gate when the finding carries no usable depth tag — rather than the orchestrator writing a path of its own or narrowing silently.
- The mechanism, scope, and narrowing conditions route to the existing scope-bounding gate (`Fix properly now` / `Defer to follow-up Issue` / `Accept the limitation`), not to a new one. On a non-blocker mechanism-introducing finding, `Defer to follow-up Issue` is the recommended default and the follow-up Issue carries the reviewer's sketched design verbatim.
- On a `suggestion` or `nit` deferred **at the scope gate**, `Defer to follow-up Issue` ships the most complete of the remaining listed paths this round, or no fix at all when the deferred path was the only one listed; **a deferral at the routing gate ships nothing against the finding however many paths were listed**; the orchestrator never invents a narrower fix to fill the slot, and the run's record names which path shipped or that none did. (A blocker's deferral behaves differently — see the criterion below.)
- A `blocker` is never offered `Accept the limitation` at either gate, and no tracker entry can record one as accepted. At the scope-bounding gate it always gets `Fix properly now` plus the Analyst re-dispatch (`/quo-fix-issue`) or `Cancel` (`/quo-execute`); at the routing-decision gate, which offers no `Fix properly now`, it gets one choice per reviewer-surfaced fix path plus `Cancel`, with `/quo-fix-issue` adding the Analyst re-dispatch. Either way the gate fires on a real choice. `Defer to follow-up Issue` is added only when the fix the blocker needs adds machinery serving something outside the reported defect and the change can be narrowed back to that defect without losing coverage of it; the deferral is recommended, paired with that narrowing, filed first, and recorded with what was narrowed away.
- Every path the orchestrator dispatches without a gate is recorded in the compromise tracker with the orchestrator's own one-line reason, and the end-of-run **Accepted compromises** summary surfaces it. A finding whose only fix path is a trivial tweak is the sole exemption; a pick among two or more paths is always recorded, however shallow all of them were.
- The post-completion review challenges every ungated pick on both depth plausibility and unnoticed mechanism-introduction, and flags an accepted `blocker` — or one deferred with no record of what was narrowed, or with a narrowing that left the reported defect partly unfixed — as a blocker-severity contract violation.
- `Cancel` runs the aborted-unit close-out wherever it is offered — at the routing-decision gate in both skills, and at `/quo-execute`'s scope gate on a blocker — stopping a `/quo-fix-issue` batch that has Issues remaining, and ending a `/quo-execute` run, rather than exiting on its own terms.
- Code review tags each fix path that requires new machinery, and both the code-reviewer and PM relays pass the tag through untouched. The tag is additive: an untagged fix path is read exactly as before.
- The user-typed invocation surface of both skills is unchanged — no new flags or arguments.

**Out of scope.**

- Gating on how much work a fix is. Effort is not a reason to interrupt and is not a tiebreaker between paths of equal completeness; the reference run's user said so directly. The gates left standing are about direction, scope, and machinery.
- A new gate for mechanism-introducing findings. The existing scope-bounding gate already asks the right question — is this in scope here, or does it belong in a follow-up — so the condition was added as a fourth entry to it rather than as a fourth gate with its own name class, contract wiring, and tracker trigger.
- Keeping the retired auto-route decision value alongside the new one. No run reads a previous run's tracker — each run writes a fresh file — so there is nothing to stay compatible with, and two strings for one concept would let a later consumer satisfy its check against one and miss the other.
- Emitting the machinery-introduction tag from the test and doc review lanes. Only code review emits it today; on the other lanes the orchestrator reads the fix path's description itself, which is the sole route to the gate there rather than a redundant one.
- Letting the orchestrator write a fix path the reviewer did not offer. It was tried during the run and removed: picking from the reviewer's list keeps a routing change to routing, and an incomplete list is surfaced at a gate instead — reaching the end-of-run review only when the answer at that gate left a record, which deferring to a follow-up Issue or accepting the limitation does and "fix it properly" does not. Whether the orchestrator should ever compose its own path is filed as a separate decision (`b.kxx`).
- Eliminating review rounds by analysing blast radius before implementation starts. That is tracked as a sibling change; this one decides how findings are routed once a reviewer has produced them.

### Feature: Review loops have no termination on nit-severity findings; nits batch into one final implementer pass and never reopen a lane

**What.** A review round whose only findings are `nit`s with trivial fixes no longer costs another full writer round plus another cold review. `/quo-fix-issue` and `/quo-execute` fold such nits into whatever implementer round a weightier finding already forces, and when only such nits remain they apply them in one final pass for that lane and move on, noting the count on the summary's **Reviews** line as applied without re-review. Blockers and suggestions still loop to clean exactly as before, so does a nit whose fix is deeper than a trivial tweak, and a nit whose fix would need a user decision still goes to the gate.

**Why.** Three runs on 2026-09-08 — two on this repo and one on a Python service — spent the majority of their review rounds on comment and docstring wording, each fresh cold pass finding the next nit, because the loop's exit condition read as "clean at every severity." The nit fixes were still reviewed, by the whole-diff post-completion pass, so the extra rounds bought nothing.

**Acceptance criteria.**

- A reviewer return whose findings are all `nit`s with `trivial-tweak` fix paths closes its lane after one implementer pass with no further reviewer round in that lane.
- Every nit applied that way is counted on the summary's **Reviews** line as applied without re-review, and never appears under **Ignored Review Feedback**, which is reserved for work left undone.
- `blocker`- and `suggestion`-severity findings loop exactly as before; so does a `nit` whose chosen fix path is deeper than `trivial-tweak`, and a `nit` whose chosen fix path would fire a routing gate still does.
- The three review skills keep `nit` as an importance tag and tell reviewers not to promote an item to `suggestion` merely to buy another round.

**Out of scope.** Any cap on rounds at any severity, and any narrowing of what a cold pass reads.
